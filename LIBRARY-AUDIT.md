# Что улучшить в vitest-auto-spy

Срез: 27 ноября 2026, версия 5.70.3, ревизия `7edc0b4b`. Это рабочий отчёт, не обещание следующего релиза. Сценарии ниже проверяют поведение библиотеки и её CLI; они не измеряют скорость приложения пользователя.

**Как читать отчёт:** статус рабочего дерева и проверки приведены ниже. Начиная с раздела «С чего начать» сохранены исходные воспроизведения и предложения на `7edc0b4b`; примеры неверного поведения относятся к этой ревизии.

## С чего начать: тест может пройти не по той причине

Первым стоит исправить `mustBeCalledWith`: пользователь явно запросил строгую проверку, а тест принимает вызов с другим ID. Вторым — `resetAutoSpy` на массивах: оставшийся stub делает результат зависимым от предыдущего теста. Исправления не требуют нового публичного API.

### Строгий spy принимает другой ID после большого повторяющегося аргумента

```ts
const part = { body: 'x'.repeat(51_000) };
const key = (id: number) => ({ a: part, b: part, query: { id } });
load.mustBeCalledWith(key(1)).returnValue('one');
load(key(2)); // Returns 'one' instead of throwing.
```

[Сериализатор](src/lib/serialize-args.ts#L300) ограничивает размер ключа, чтобы общий подграф не копировался бесконечно. Повтор `part` исчерпывает бюджет, поэтому следующий `query` попадает в ключ только своей формой. Сам лимит полезен; ошибка — считать совпадение сокращённых ключей доказательством равенства. На сокращённом пути проверять совпадение структурно, не замедляя обычный ключ. Для приёмки нужны два разных ID, равный объект с тем же ID и контроль, что общий подграф не разворачивается экспоненциально.

## Адаптеры: где double расходится с настоящей зависимостью

### Angular 22.2: вначале HTTP и преобразования signal inputs

**Проверка незавершённых HTTP-запросов.** Подписаться на `GET /api/orders`, вызвать `expectRequest('/api/orders', { tick: false })`, но не вызывать `flush` или `error`. `verifyNoPendingRequests()` проходит, хотя подписка открыта и не получила ответа: [поиск запроса](src/lib/angular-http.ts#L487) уже изъял его из контроллера. Angular различает найденные и ненайденные запросы; если библиотека обещает проверить именно **неотвеченные**, ей нужен учёт выданных handle до ответа или отмены. Приёмка: неотвеченный запрос назван по методу и URL; `flush`, `error` и `ignoreCancelled` проверены отдельно.

**Shallow-подмена меняет значение входа.** Родитель передаёт `compact=""` ребёнку с `input(false, { transform: booleanAttribute })`. У настоящего ребёнка `compact()` возвращает `true`, у [стаба](src/lib/component-stub.ts#L225) — `''`. Это противоположные результаты даже в простом `if`. Держать парный тест одной родительской привязки с настоящим и подменённым ребёнком; если transform нельзя восстановить без создания ребёнка, явно сообщать об ограничении или позволить задать transform, не возвращая молча неверный тип.

Для Svelte это расхождения в рецептах, не дефект рендера. Отдельного сбоя React в проверенных операциях со store, checkout и setter не воспроизведено. Живой рендер React/Svelte и интеграция через Nest `TestingModule` в эти пробы не входили.

## Где инструменты дают неверный результат

### 1. `perf --gate` может пропустить медленный тест в одном из двух проектов

Один spec может запускаться в двух проектах Vitest, например в Node и DOM. В первом запуске тело `works` занимает 1 500 мс, во втором — 10 мс. На синтетическом отчёте формата v2 с этими двумя строками `perf --json … --gate --no-confirm` завершился с кодом **1**, как и положено при бюджете 1 000 мс. Изменение только `setup` во второй строке с 0 до 3 000 мс поменяло код выхода на **0**: «nothing over budget». Медленный тест при этом никуда не делся.

Причина: [слияние отчётов](src/cli/perf-merge.ts#L145) оставляет одну строку на путь, выбирая её по сумме фаз, а [gate](src/cli/perf-gate.ts#L143) оценивает тела тестов и тоже индексирует их по пути. Выбор самого длинного запуска не сохраняет самый медленный тест. [Промежуточный отчёт репортера](src/cli/perf-reporter.ts#L549) также различает модули только по пути.

**Исправление:** записывать идентификатор проекта и сохранять `(проект, путь)` до повторного запуска. Для старых отчётов без идентификатора не выдавать безусловно зелёный результат, если отброшенная строка меняет вердикт. **Приёмка:** один spec в двух проектах, разные бюджетообразующие фазы; результат не зависит от порядка строк, а перепроверка запускает нужный проект.

### 2. Отчёт Windows не переносится на macOS так же, как отчёт Linux

Тот же CLI на macOS оценил строку `/ci/repo/src/same.spec.ts` с корнем `/ci/repo` и вернул **1** за тело в 1 500 мс. Для эквивалентных `C:\ci\repo\src\same.spec.ts` и `C:\ci\repo` он вернул **2**: ни один файл не принадлежит проекту. Это не ложный зелёный результат: разработчик вообще не получает вердикт по артефакту CI.

[Определение относительного пути](src/cli/perf-gate.ts#L130) использует правила ОС читателя и для путей автора отчёта. Сохранять путь относительно корня уже в репортере, а для существующего формата выбирать `path.win32` или `path.posix` по записанному корню. **Приёмка:** фикстуры POSIX, Windows drive и UNC на одном хосте; настоящий путь за пределами записанного корня по-прежнему отброшен.

### 3. `doctor` может пропустить каталог, который Git не игнорирует

При правиле `test[!0-9]data/` Git и сканер согласны, что `test-data/` игнорируется. Для `test/data/` проверка `git check-ignore --no-index` вернула **1** (не игнорируется), а `isIgnoredBy` — **true**. Значит, сканер [не спускается в каталог](src/cli/fs-scan.ts#L327) и не проверяет его файлы.

[Конвертер шаблонов](src/cli/gitignore.ts#L139) превращает отрицательный класс в `[^0-9]`, которому подходит и `/`. В Git такой класс не пересекает границу компонента пути. Ограничить классы одним компонентом; в регрессионном тесте проверять оба каталога, а не только строковое представление регулярного выражения.

## Скорость: сначала починить измеритель

**Самая полезная правка для честного сравнения с конкурентами — не ускорение `vi.fn`.** Если у соперника не осталось успешных измерений, [сводка suite-бенчмарка](scripts/bench-suite.mjs#L819) считает отсутствие медианы благоприятным для нашей библиотеки. Ошибки видны отдельной таблицей внизу, но рамка результата уже может быть зелёной. При `--coverage both` поиск ячейки по размеру и участнику также не различает режим покрытия. Группировать по `(размер, coverage, участник)` и не объявлять победителя без заданного числа успешных **парных** раундов. Проверить синтетической таблицей с одним проваленным участником и противоположными победителями при включённом и выключенном coverage.

| Что ещё искажает измерение                                                                                                                                                                                                                                                                  | Что изменить                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [Инвариант очистки](src/invariants/teardown-shape.spec.ts#L137) создаёт наборы на 500 и 2 000 doubles до обоих замеров. `vi.clearAllMocks()` не принимает набор: его вызывают на одном глобальном состоянии. Отношение около единицы не доказывает, что очистка масштабируется.             | Измерять отдельно подготовленные реестры, с одинаковой историей на double. Оставить `resetAutoSpy(double)` отдельным сценарием.                                    |
| [Микробенчмарк `calledWith`](bench/auto-spy.bench.ts#L267) сохраняет историю как минимум 2,4 млн вызовов (3 × 800 000). В отдельной ограниченной пробе 196 608 записей удерживали 36,49 MiB после GC; с очисткой каждые 256 итераций — 0,03 MiB. Это история вызовов, не утечка библиотеки. | Очищать историю **между** измеряемыми пакетами, проверять результат и добавить контроль; иначе замер смешивает диспетчеризацию и накопление истории.               |

[Suite-таймер](scripts/bench-suite.mjs#L556) ждёт завершения RSS-сэмплера после выхода дочернего процесса.             | Сравнивать собранные входы и останавливать wall-clock при выходе процесса. RSS публиковать отдельно. Влияние этих расхождений на старые результаты не установлено. |

### Где есть измеримый кандидат на ускорение

Медиана пакетного времени на один вызов, нс. Локальная сборка `dist`, arm64, Node 26.13.0, Vitest 5.0.2; 16 384 вызова на вариант за раунд, 4 разогрева, 7 измерений, чередование вариантов и очистка истории каждые 256 вызовов. Это микрозамер, не выигрыш пользовательского suite.

| Число настроенных вариантов | Точный примитив, последний совпал | Структурный matcher, последний совпал | Структурный matcher, промах |
| --------------------------: | --------------------------------: | ------------------------------------: | --------------------------: |
|                           1 |                                35 |                                    46 |                          50 |
|                           8 |                                35 |                                   102 |                         110 |
|                          64 |                                35 |                                   573 |                         581 |

[Структурный поиск](src/lib/args-map.ts#L394) перебирает варианты. При 64 регистрациях последнему совпадению нужно около 0,57 мкс; точный ключ от числа вариантов почти не зависит. Следующий шаг — добавить первый/последний hit и miss в бенчмарк и найти потребительский suite с десятками настроек на **один** метод. Только если это заметно в профиле, пробовать отбор по числу аргументов или типу первого точного аргумента, сохраняя порядок matcher. Не оптимизировать точные ключи по этим данным.

Для suite-сравнения добавить два ручных контроля: создать все 100 методов класса и создать только 3 используемых. [Архивный тест памяти](docs-site/core/performance.md#L1249) на 10 000 тестов измерял первый сценарий: 2 103 против 6 366 MB пикового RSS, при выключенной изоляции. Он не доказывает преимущества над ручной подменой трёх зависимостей или над нынешними версиями конкурентов. Для Angular также сравнивать листовой компонент и компонент с дорогими дочерними представлениями отдельно. Уменьшение тела рендера, размера пакета и времени холодного импорта — три разных результата.
