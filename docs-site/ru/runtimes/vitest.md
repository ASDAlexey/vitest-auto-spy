# Vitest

Точка входа по умолчанию, работающая без настройки. Импорт `vitest-auto-spy` регистрирует mock-адаптер
Vitest (`vi.fn()` / `vi.spyOn()`) и открывает всё ядро API.

```ts
import { createSpyFromClass } from 'vitest-auto-spy';

// Vitest (по умолчанию, без настройки)
```

Ядро не привязано к раннеру и работает через `MockAdapter`; точка входа Vitest регистрирует адаптер по
умолчанию прямо при импорте, так что привычный код ничего не меняет. Нативные методы моков (например,
`mockReturnValue`) остаются методами самого Vitest — приводятся к общему виду только хелперы auto-spy.

## Vitest 5 {#vitest-5}

**Одна установка покрывает Vitest от 2.1 до 5.x.** Для нового раннера нет отдельного мажора этого пакета,
нет типов, разведённых по версиям, нет тега `@next`: диапазон peer-зависимости остаётся `>=2.1.0`, поэтому
монорепозиторий, где одно приложение сидит на Vitest 4, а другое на 5, зависит от одной и той же версии
`vitest-auto-spy`, а файл спеки переезжает между ними без правок.

До библиотеки спаев, а не до спеки, в Vitest 5 доходят два изменения — и оба здесь погашены.

`clearAllMocks()` больше не обходит все моки, созданные за прогон. Vitest 5 держит зарегистрированные моки
за `WeakRef` и чистит только те, которые _вызывались_ с прошлой уборки, — это настоящее улучшение и ровно
та причина, по которой движок спаев, отличный от `vi.fn()`, обязан о себе этой уборке заявить. Собственный
движок библиотеки (по умолчанию с 4.1) это делает, поэтому `vi.clearAllMocks()` и новое значение по
умолчанию `clearMocks: true` чистят эти дублёры ровно так же, как чистят собственные моки раннера.

У интерфейса `Matchers` появился второй параметр типа — `Matchers<T>` на Vitest 4 и `Matchers<R, T>` на
Vitest 5, — а TypeScript отказывается сливать декларацию с другим списком параметров. Поставляемые
матчеры (`toHaveFocus`, `toHaveSignalValue`, `toBeLoading`, `toHaveResourceValue`, `toHaveResourceError`,
`toHaveDirectiveApplied` и набор для jasmine) объявляют себя на `Assertion` из Chai, у которого ни в одном
мажоре нет параметров типа, — поэтому они типизируются на обеих версиях, и подключать второй `.d.ts` не
приходится.

### Сколько это стоит, по замерам {#what-it-costs-measured}

40 файлов спек, 800 тестов, 400 подменённых методов на файл, покрытие v8 включено, Node v24.19.0, медиана
пяти прогонов, замерено 06.09.2026 на одном и том же исходнике библиотеки:

| набор                                                        | Vitest 4.1.11 | Vitest 5.0.0 |
| ------------------------------------------------------------ | ------------- | ------------ |
| собственный движок спаев библиотеки (по умолчанию)           | 1383 мс       | **1276 мс**  |
| каждый метод собран через `vi.fn()` (`setSpyEngine('runner')`) | 1473 мс     | 1390 мс      |

Смена одного только раннера даёт **−7,7 %**. Движок стоит **−6,1 %** на Vitest 4 и **−8,1 %** на Vitest 5
по сравнению с тем, чтобы отдавать каждый метод в `vi.fn()`. От самой медленной пары к самой быстрой —
Vitest 4 с моками раннера против Vitest 5 с движком по умолчанию — 1473 мс → 1276 мс, **−13,4 %**.

### Единственное, что всё ещё может сломать ваши спеки {#the-one-thing-that-can-still-break-your-specs}

В Vitest 5 `clearMocks` по умолчанию `true`, поэтому `vi.clearAllMocks()` выполняется перед каждым тестом.
Это изменение раннера, а не библиотеки, и оно ломает один приём: тест, проверяющий вызов, который записал
_предыдущий_ тест или `beforeAll`, теперь видит ноль вызовов. Считайте такие вызовы обычной переменной, а
не историей спая:

```ts
let initCalls = 0;
const init = vi.fn(() => {
  initCalls += 1;
});

beforeAll(() => {
  install({ init });
});

it('asked once for the whole file', () => {
  expect(initCalls).toBe(1); // а не expect(init).toHaveBeenCalledTimes(1)
});
```

`clearMocks: false` возвращает поведение Vitest 4, если править спеки не хочется.

### Единственная возможность, ради которой нужно поменять строчку {#the-one-feature-that-needs-a-line-changed}

`setupAutoSpy({ pruneMockRegistry: true })` запоминает, что возвращал долгоживущий мок, и отдаёт реализацию
обратно тому, кто потерял её из-за случайного `vi.resetAllMocks()`. Такие моки он находит, обходя
собственный реестр `@vitest/spy`, а Vitest 5 этот реестр наружу больше не отдаёт — так что на Vitest 5
автоматический поиск ничего не делает. Явная пометка работает на всех версиях и является решением:

```ts
import { keepMockRegistered } from 'vitest-auto-spy/setup';

// fixtures/logger.mock.ts — импортируется многими файлами спек
export const logger = { channel: keepMockRegistered(vi.fn().mockReturnThis()), info: vi.fn() };
```

## Спека от начала до конца {#a-spec-start-to-finish}

```ts
import { beforeEach, describe, expect, it } from 'vitest';
import { type Spy, createSpyFromClass } from 'vitest-auto-spy';

import { Greeter } from './greeter';
import { UserService } from './user.service';

describe('Greeter', () => {
  let users: Spy<UserService>;
  let greeter: Greeter;

  beforeEach(() => {
    users = createSpyFromClass(UserService);
    greeter = new Greeter(users);
  });

  it('greets the name the service returns', () => {
    users.getName.calledWith(1).mockReturnValue('Ada');

    expect(greeter.greet(1)).toBe('Hello, Ada!');
    expect(users.getName).toHaveBeenCalledWith(1);
  });
});
```

## Что относится к setup-файлу {#what-belongs-in-the-setup-file}

Чтобы создать спай, не нужно вообще ничего. Две вещи глобальны по своей природе, и их место в
`setupFiles`, а не в спеке:

```ts
// vitest.setup.ts
import 'vitest-auto-spy/rxjs';
// один раз — включает nextWith / observablePropsToSpyOn везде
import { setupAutoSpy } from 'vitest-auto-spy/setup';

setupAutoSpy();
```

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    setupFiles: ['./vitest.setup.ts'],
  },
});
```

- **`import 'vitest-auto-spy/rxjs'`** регистрирует слой observable. Без него любой observable-хелпер
  (`nextWith`, `observablePropsToSpyOn`, …) бросает сообщение, называющее ровно этот импорт, — фабрика
  спаев никогда не тянет rxjs сама.
- **[`setupAutoSpy()`](/ru/utilities/setup)** восстанавливает патчи `mock*Prop`, сбрасывает реестр моков и
  роняет прогон, если в дереве оказалась вторая установленная копия пакета.

Регистрация [матчеров для сигналов](/ru/adapters/angular) (`toHaveSignalValue`) — третий кандидат в
setup-файл для Angular-наборов: `registerSignalMatchers()` из `vitest-auto-spy/angular`.

## Изоляция {#isolation}

Vitest по умолчанию изолирует каждый файл, поэтому оставшийся патч свойства или спай, положенный в
переменную уровня модуля, умирают вместе с файлом. Когда изоляцию выключают (`isolate: false`, общее
окружение, один поток) — это ровно тот режим, ради которого существует `setupAutoSpy()`; по этой же
причине пакет гоняет собственный набор в CI обоими способами.

```ts
// vitest.config.ts — режим, в котором нужна осторожность
export default defineConfig({
  test: {
    isolate: false,
    setupFiles: ['./vitest.setup.ts'], // теперь делает настоящую работу
  },
});
```

### Общий патч `TestBed` переживает файл, который его попросил {#a-shared-testbed-patch-outlives-the-file-that-asked-for-it}

Setup-файл — естественное место, чтобы добавить один DI-провайдер в каждый вызов
`configureTestingModule`, поставив его один раз на воркер под флагом. При `isolate: false` этот патч не
заканчивается вместе с файлом, которому был нужен: спеки в никак не связанных библиотеках молча
наследуют провайдер, который никогда не объявляли, — и проходят. Они продолжают проходить до тех пор,
пока прогон не станет изолированным, а именно такой прогон делает CI, потому что покрытие вынуждает
изоляцию, — и тогда они падают с `NG0201: No provider found` в файлах, которых никто не трогал.

Общая форма проблемы — спека, которая проходит только потому, что контейнер настроил _сосед по тому же
воркеру_. Проверить это дёшево, а другого способа найти такое нет: **прогоните любой набор с общим
патчем `TestBed` один раз в изоляции, прежде чем ему доверять.**

### Падение на этапе загрузки записывается на каждый файл воркера {#a-load-time-failure-is-reported-against-every-file-in-the-worker}

Файл, который умирает во время вычисления своего графа модулей, утаскивает за собой остальные файлы
воркера, и отчёт сообщает об этом так, что читается задом наперёд. Четыре подряд полных прогона одного и
того же неизменного дерева отчитались о **0, 95, 104 и 151 упавшем _файле_** при том, что число упавших
_тестов_ оставалось **нулевым**: число отражает, сколько файлов спек случайно оказались в умершем
воркере, а не сколько всего сломано.

Признак — пересечение: за эти четыре прогона списки упавших файлов **не совпали ни в одном файле**. Ни
один файл ни из одного списка не виноват.

Не называет виновника и ни один из каналов вывода. Vitest 4 схлопывает одинаковую необработанную ошибку в
одну строку сообщения, без стека и без исходного модуля, а репортер `json` несёт то же голое сообщение с
`assertionResults: []`. Так что работающее правило разбора — узкое:

> Чините только те файлы, которые упали на **собственных** проверках, и перезапускайте.

Всё остальное в списке — случайные соседи, и именно перезапуск покажет, кто есть кто.

## Подпуть для Angular {#the-angular-subpath}

Angular-набор импортирует из `vitest-auto-spy/angular`: там регистрируется тот же адаптер Vitest и
добавляются хелперы для `TestBed`:

```ts
import { injectSpy, provideAutoSpy, renderShallow, stable } from 'vitest-auto-spy/angular';
```

Ему нужна настройка Vitest, знающая про Angular (например, `@analogjs/vite-plugin-angular` плюс вызов
`setupTestBed()`). См. [Angular](/ru/adapters/angular) — и
[Angular на Bun](/ru/runtimes/bun-angular) для того же набора под `bun test`.
