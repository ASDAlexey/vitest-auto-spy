# node:test

Точка входа `vitest-auto-spy/node` гоняет то же ядро на `mock.fn()` из `node:test`.

```ts
import { createSpyFromClass } from 'vitest-auto-spy/node';

// node:test
```

Публичное API идентично точке входа Vitest. Импорт этой точки входа регистрирует адаптер `node:test`;
хелперы auto-spy (`calledWith`, `resolveWith`, `nextWith`, …) приведены к общему виду, а нативные методы
моков остаются методами самого раннера.

## Готовый к запуску пример {#a-runnable-example}

`node:test` не поставляет `expect`, поэтому используйте его вместе с `node:assert` — поверхность спая от
этого не меняется.

```js
// user.test.mjs
import assert from 'node:assert/strict';
import { describe, it } from 'node:test';
import { createSpyFromClass } from 'vitest-auto-spy/node';

class UserService {
  getName(id) {
    return `user-${id}`;
  }

  async load(id) {
    return `loaded-${id}`;
  }
}

describe('UserService spy', () => {
  it('returns per-argument values and resolves promises', async () => {
    const users = createSpyFromClass(UserService);

    users.getName.calledWith(7).mockReturnValue('seven');
    users.load.resolveWith('ok');

    assert.equal(users.getName(7), 'seven');
    assert.equal(await users.load(1), 'ok');
    assert.deepEqual(users.getName.mock.calls[0].arguments, [7]);
  });
});
```

```bash
node --test
```

## Где нативная поверхность расходится {#where-the-native-surface-differs}

Мок `node:test` не совместим с Jest, и это единственное место, где это заметно. Хелперы auto-spy это
прячут; чтение сырого мока — нет.

| Что вам нужно              | Vitest / Bun                           | `node:test`                                  |
| -------------------------- | -------------------------------------- | -------------------------------------------- |
| Записанные вызовы          | `spy.method.mock.calls[0]` → аргументы | `spy.method.mock.calls[0].arguments`         |
| Заменить реализацию        | `spy.method.mockImplementation(fn)`    | `spy.method.mock.mockImplementation(fn)`     |
| Сброс                      | `spy.method.mockReset()`               | `spy.method.mock.resetCalls()` / `restore()` |
| Прочитать имя спая обратно | `spy.method.getMockName()`             | **отсутствует** — читайте `spy.method.name`  |
| Возвращаемое значение      | `spy.method.mockReturnValue(v)`        | **отсутствует** — см. примечание ниже        |

Кусается именно последняя строка: `spy.method.mockReturnValue('x')` — **нативный** метод Vitest/Bun,
а у `node:test` такого нет, поэтому здесь он `undefined`. Собственный
`spy.method.calledWith(...).mockReturnValue('x')` из библиотеки **работает** на всех трёх средах — он
часть унифицированной поверхности, а не поверхности раннера.

```js
users.getName.calledWith(7).mockReturnValue('seven'); // ✅ везде
users.getName.mockReturnValue('seven'); // ❌ не на node:test
```

Отдавайте предпочтение унифицированным хелперам (`calledWith(...).mockReturnValue(...)`, `resolveWith`,
`nextWith`) — и различия перестанут иметь значение: они читаются одинаково на всех трёх средах.

`mock.settledResults`, который `node:test` нативно не отслеживает, обеспечивается встроенным
полифиллом, поэтому читается так же, как в Vitest (`{ type: 'fulfilled' | 'incomplete' | 'rejected', value }`).
См. [Управляющие хелперы → Разбор итога промиса](/ru/core/control-helpers#settled-results).

## Имена спаев {#spy-names}

`mock.fn()` из `node:test` не принимает имени и не имеет `mockName()`, а возвращаемый им прокси
сохраняет имя переданной функции — поэтому, пока это не было обработано, каждый спай печатался как
`[Function: dispatch]`, по имени внутреннего диспетчера библиотеки, всюду, где спай отрисовывался.

Теперь адаптер отдаёт имя метода _реализации_ в момент её создания, а `mock.fn()` переносит его на мок:
мок `node:test` берёт своё `name` у функции, которую оборачивает. `displayName` тоже проставляется на
моке — для инспекторов, предпочитающих эту конвенцию. Имя переживает `mock.reset()`, `mock.restore()`,
`resetCalls()` и подмену через `mockImplementation()`, потому что мок захватил его при сборке.

Именование при создании, а не переопределение `name` задним числом — решение про память, а не про стиль.
`Object.defineProperty(mock, 'name', …)` работает, но выбивает функцию из быстрой карты V8: по замерам на
200 000 моков на Node 24.19.0 переопределение стоит **+206 Б на каждый** против **+65 Б** при именовании
на создании. Анонимному функциональному выражению под вычисляемым ключом имя даёт сам язык, и — в отличие
от сокращённой записи метода — оно остаётся конструируемым, что нужно `mockConstructor`.

Именно это читают diff'ы `node:assert`, `util.inspect()` и собственные сообщения библиотеки, так что спай
представляется точно так же, как на Vitest и Bun:

```txt
The function 'getName' was configured with 'mustBeCalledWith' and expects to be called with specific arguments.
Wanted: getName(7)
Actual: getName([Function: getName])
```

Двух вещей это по-прежнему не даёт, и починить их с этой стороны нельзя:

- **`getMockName()` у мока `node:test` не существует.** Это метод из семейства Jest, который есть у
  Vitest и Bun и которого нет у `node:test`; читайте там `spy.method.name`.
- **Собственный репортер `node:test` никогда не подписывает мок.** Его вывод называет упавший _тест_, а
  не задействованный мок — имя всплывает только там, где спай реально отрисовывается как значение (diff
  проверки, `util.inspect`, сообщение библиотеки), но никогда не становится заголовком в репортере TAP
  или spec.

## Каждый мок удерживается, пока не выброшен трекер {#every-mock-is-retained-until-the-tracker-is-dropped}

`node:test` регистрирует каждый `mock.fn()` в своём `MockTracker` уровня модуля и держит ссылку всё время
жизни процесса. Из этого списка ничего никогда не удаляется поштучно: очищает его только `reset()`, и он
попутно всё восстанавливает. Так что выброшенный спай остаётся достижимым — а вместе с ним и всё, что он
захватил в замыкание, включая записанные аргументы.

По замерам на Node v24.19.0, 20 000 спаев класса с 10 методами, созданных в 20 тестах, выброшенных, а
затем дважды принудительно собранных: **124,5 МБ** удержано против базовой линии в 5,5 МБ.

### `trackNodeMocks()` {#tracknodemocks}

Вызовите один раз — и библиотека начнёт создавать свои спаи на `MockTracker`, **которым владеет сама**,
заменяя этот трекер новым после каждого теста. Отслуживший экземпляр и его список становятся мусором
вместе.

```js
import { before, describe, it } from 'node:test';
import { createSpyFromClass, trackNodeMocks } from 'vitest-auto-spy/node';

before(() => {
  trackNodeMocks();
});
```

Тот же замер, та же машина, но с хелпером: **5,9 МБ** — сокращение в **21×** и 0,4 МБ сверх базовой линии
вместо 119 МБ.

Это подключается по желанию, и набор, который ничего не делает, сохраняет ровно сегодняшнее поведение.
Три вещи хелпер сознательно не делает:

- **Он никогда не вызывает `mock.reset()`.** Ровно ради этого приватный трекер и стоит написанного кода:
  сброс общего трекера восстанавливает и забывает тот `mock.fn()`, который спека написала руками. Замена
  трекера, которым владеет библиотека, не трогает ни одного спая — мок `node:test` продолжает записывать
  вызовы и хранить реализацию и после исчезновения своего трекера, потому что трекер существует только
  ради restore/reset.
- **Он не переносит уже существующие спаи.** Всё, что создано до вызова, остаётся на трекере среды
  выполнения. Вызывайте его один раз, как можно раньше в файле.
- **Он никогда не бросает исключение.** До класса он добирается через `mock.constructor`, а это не
  задокументированное API, поэтому конструирование проверяется до того, как на него будет направлен хоть
  один спай. Если будущая среда выполнения его не отдаст, `trackNodeMocks()` станет пустышкой, а спаи
  продолжат создаваться там же, где и сегодня.

Вместе с ним идут ещё два экспорта, оба необязательные: `pruneNodeMocks()` подметает вручную — для
набора, который гоняет тесты параллельно, где общий хук на каждый тест даёт неверную гранулярность, — и
возвращает, сколько спаев ушло; `countNodeMocks()` читает текущее число обратно, для набора, который
предпочтёт это проверить, а не поверить на слово.

### Запасной вариант для набора, которому хелпер не нужен {#the-fallback-for-a-suite-that-does-not-want-the-helper}

`mock.reset()` в `afterEach` по-прежнему работает и по-прежнему освобождает всё. Это более грубый
инструмент — он заодно восстанавливает и забывает любой `mock.fn()`, созданный спекой самостоятельно, —
но ему ничего не нужно от этого пакета:

```js
import { afterEach, mock } from 'node:test';

afterEach(() => {
  mock.reset();
});
```

Vitest и Bun сбрасывают собственные реестры между файлами, поэтому ничто из этого не касается
`vitest-auto-spy` и `vitest-auto-spy/bun`.

::: tip Какую среду выбрать
`node:test` не требует вообще никаких зависимостей, кроме самого Node, и потому хорошо подходит
библиотеке без шага сборки. Для набора тестов приложения [Vitest](/ru/runtimes/vitest) или
[Bun](/ru/runtimes/bun) обойдутся дешевле — оба поставляют `expect` и режим наблюдения.
:::
