# Bun (`bun:test`)

Точка входа `vitest-auto-spy/bun` гоняет ровно то же ядро на моках `bun:test`, а не на моках Vitest.

```ts
import { createSpyFromClass } from 'vitest-auto-spy/bun';

// Bun — bun:test
```

Публичное API (`createSpyFromClass`, `calledWith`, `resolveWith`, `nextWith`, …) **идентично** точке входа
Vitest. Своими у раннера остаются только **нативные** методы моков; хелперы auto-spy приведены к общему
виду. Импортируйте точку входа, соответствующую вашему раннеру, — она регистрирует адаптер Bun при
импорте.

У тестирования Angular под `bun test` есть собственная точка входа —
[`vitest-auto-spy/bun-angular`](/ru/runtimes/bun-angular).

## Готовый к запуску пример {#a-runnable-example}

```ts
// user.test.ts
import { describe, expect, it } from 'bun:test';
import { type Spy, createSpyFromClass } from 'vitest-auto-spy/bun';

class UserService {
  getName(id: number): string {
    return `user-${id}`;
  }

  async load(id: number): Promise<string> {
    return `loaded-${id}`;
  }
}

describe('UserService spy', () => {
  it('returns per-argument values and resolves promises', async () => {
    const users: Spy<UserService> = createSpyFromClass(UserService);

    users.getName.calledWith(7).mockReturnValue('seven');
    users.load.resolveWith('ok');

    expect(users.getName(7)).toBe('seven');
    await expect(users.load(1)).resolves.toBe('ok');
    expect(users.getName).toHaveBeenCalledWith(7);
  });
});
```

```bash
bun test
```

Опциональный слой rxjs работает так же — один раз `import 'vitest-auto-spy/rxjs'`, и
`nextWith` / `nextWithValues` / `observablePropsToSpyOn` доступны и на Bun.

## Чем это отличается от Vitest {#what-differs-from-vitest}

Всё, что библиотека приводит к общему виду, читается на обоих раннерах одинаково; остаётся собственное
поведение моков Bun — и стоит понимать, где что.

| Поведение                                | Vitest                            | Bun                                          | Кто с этим разбирается                                     |
| ---------------------------------------- | --------------------------------- | -------------------------------------------- | ---------------------------------------------------------- |
| `mock.settledResults`                    | нативно                           | не отслеживается                             | полифилл — читается одинаково на обоих                     |
| `mockReset()`                            | сохраняет спай, чистит вызовы     | ещё и сбрасывает реализацию                  | адаптер её восстанавливает, поэтому auto-spy выживают      |
| `spyOn(obj, 'prop', 'get')`              | поддерживается                    | бросает — аксессоры пока не поддержаны       | спаи на аксессоры идут через переопределение свойства      |
| Имена спаев в сообщениях об ошибках      | имена `vi.fn()`                   | `mockName()`                                 | проставляются за вас                                       |
| Фейковые таймеры                         | `vi.useFakeTimers()`              | `jest.useFakeTimers()`                       | не унифицированы — `vitest-auto-spy/setup` только для Vitest |
| `expect.any(...)` внутри `calledWith`    | сопоставляется как предикат       | не совпадает никогда — см. ниже              | не унифицировано — на Bun используйте точные аргументы     |

`mock.settledResults` описан в разделе
[Управляющие хелперы → Разбор итога промиса](/ru/core/control-helpers#settled-results).

Строку про матчеры стоит прочитать дважды, потому что она ломается молча. Асимметричные матчеры Vitest —
это обычные объекты JavaScript с методом `asymmetricMatch`, и именно его
[`calledWith`](/ru/core/control-helpers#asymmetric-matchers-in-calledwith) применяет к фактическим
аргументам. У Bun это нативные объекты, не отдающие ни такого метода, ни читаемого состояния, поэтому
конфигурация с таким матчером сохраняется как обычный аргумент и не совпадает ни с чем:
`read.calledWith(expect.any(Number))` отвечает `undefined` на `read(7)` вместо того, чтобы бросить
ошибку. На Bun различайте вызовы по точным аргументам или берите `mockImplementation`, когда ответ
действительно зависит от формы аргумента.

## Флаги тест-раннера Bun 1.4 {#bun-1-4-test-runner-flags}

Bun 1.4 превратил `bun test` в раннер с теми средствами управления расписанием, которые нужны большому
набору тестов. Настраивать под них в пакете ничего не надо — они перечислены здесь потому, что два из них
меняют поведение набора, и ответ библиотеки на каждый флаг свой.

| Флаг                             | Что делает                                                     | Как влияет на ваши спаи                                                                                     |
| -------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `--isolate`                      | свежий глобальный объект JavaScript на файл, в одном процессе  | совпадает с поведением Vitest по умолчанию. Реестры и патчи свойств не могут утечь между файлами            |
| _(без флага)_                    | один общий глобальный объект на весь прогон                    | режим, в котором нужна осторожность: патч свойства или забытый реестр переживают создавший их файл          |
| `--parallel[=N]`                 | распределяет файлы по процессам-воркерам                       | никак: каждый воркер — отдельный процесс, значит у каждого свой реестр                                       |
| `--shard=M/N`                    | делит файлы между раннерами CI                                 | никак                                                                                                        |
| `--changed[=ref]`                | только файлы, задетые вашим диффом                             | никак                                                                                                        |
| `--timings` / `--update-timings` | балансирует шарды по записанному календарному времени          | никак                                                                                                        |
| `--retry <N>` / `{ repeats: n }` | перезапускает нестабильный или нагрузочный тест                | спай, который не сбрасывается между прогонами, копит вызовы — сбрасывайте его в `beforeEach`                 |

Без `--isolate` относитесь к прогону на Bun так же, как к `isolate: false` в Vitest: восстанавливайте всё,
что патчите. `restoreMockedProps()` в `afterEach` закрывает хелперы для свойств; `resetAutoSpy(spy)`
чистит спай, переживающий один тест.

::: tip Какой режим выбрать
`--isolate` — более безопасный вариант по умолчанию и стоит немного; `--parallel` — тот, что делает
большой набор быстрым. Они сочетаются: `bun test --isolate --parallel`.
:::

## Совместимость {#compatibility}

Пакет проверен на **Bun 1.4** и отслеживает `latest` в CI. Собственный набор тестов для Bun лежит в
`src/bun-tests/` и запускается на настоящем `bun:test` — набор на Vitest может проверять адаптер Bun
только против заглушки, поскольку `bun:test` вне Bun не резолвится.
