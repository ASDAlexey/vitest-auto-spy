# Переход с jest-auto-spies

Публичный API намеренно совпадает с
[`jest-auto-spies`](https://www.npmjs.com/package/jest-auto-spies). В большинстве проектов миграция —
это **замена импорта через «найти и заменить»**:

```diff
- import { createSpyFromClass, provideAutoSpy } from 'jest-auto-spies';
+ import { createSpyFromClass } from 'vitest-auto-spy';
+ import { provideAutoSpy } from 'vitest-auto-spy/angular';
+ import 'vitest-auto-spy/rxjs'; // один раз, если пользуетесь спаями на observable
```

Единственное изменение формы API — Angular-хелперы и слой observable живут за подпутями `/angular` и
`/rxjs` (см. [Установка → Точки входа](/ru/core/installation)).

Это же — самая часто повторяющаяся правка в большой миграции: наверху `provideAutoSpy` лежит в
корне, и первое, что просится сделать, — переименовать один токен в спецификаторе модуля. Промах не
всегда падает громко, поэтому искать их лучше разом, а не по одной ошибке компиляции:
`npx vitest-auto-spy doctor` докладывает `helper-from-wrong-entry` на каждый именованный импорт,
взятый из точки входа, которая его не экспортирует, — имя разрешается по карте экспортов самой
установленной версии (подробности — [CLI → doctor](/ru/utilities/cli)).

::: tip Переезжаете с `jasmine-auto-spies`?
Оба пакета сверху — родные братья над одним и тем же `@hirez_io/auto-spies-core`, так что всё на этой
странице применимо и к ним, с одним дополнением и одной ловушкой. Дополнение: наверху асинхронные
хелперы припаркованы на `.and`, поэтому `spy.load.and.nextWith(v)` здесь пишется как
`spy.load.nextWith(v)`, а [`vitest-auto-spy/jasmine`](/ru/migrating-jasmine) возвращает `.and` на
место — сюита становится зелёной ещё до того, как что-либо переписано. Ловушка: у jasmine `spyOn`
**заглушает**, а `vi.spyOn` **вызывает оригинал**, так что переименование молча выворачивает поведение
наизнанку.

**→ [Переход с jasmine-auto-spies](/ru/migrating-jasmine)** — там полное соответствие и для API
auto-spies, и для собственных глобалов jasmine (`createSpyObj`, асимметричные матчеры, `clock()`,
`withContext`, `DEFAULT_TIMEOUT_INTERVAL`, `fdescribe`/`xit`, колбэки `done`).
:::

## Таблица соответствия {#mapping-table}

Это же покрывает и переход с
[`@bugsplat/vitest-auto-spies`](https://www.npmjs.com/package/@bugsplat/vitest-auto-spies) — пакет
реэкспортирует тот же API `jest-auto-spies`, поэтому замена идентична (и сверху вы получаете Bun /
`node:test`, `createAutoMock`, рецепты под фреймворки и спаи на консоль).

| jest-auto-spies                                                       | vitest-auto-spy                                                  | Статус       |
| --------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------ |
| `createSpyFromClass`                                                  | `createSpyFromClass`                                             | ✅ идентично |
| `methodsToSpyOn`                                                      | `methodsToSpyOn` — там дополняющий и здесь дополняющий           | ✅ идентично |
| `provideAutoSpy`                                                      | `provideAutoSpy` (из `/angular`)                                 | ✅ идентично |
| `calledWith` / `mustBeCalledWith`                                     | так же                                                           | ✅ идентично |
| `calledWith(...).returnValue(v)`                                      | так же — работают **и** `.returnValue`, **и** `.mockReturnValue` | ✅ идентично |
| `resolveWith` / `rejectWith` / `resolveWithPerCall`                   | так же                                                           | ✅ идентично |
| `nextWith` / `nextOneTimeWith` / `nextWithValues` / `nextWithPerCall` | так же                                                           | ✅ идентично |
| `throwWith` / `complete` / `returnSubject`                            | так же                                                           | ✅ идентично |
| `accessorSpies.getters/setters`                                       | так же                                                           | ✅ идентично |
| `createObservableWithValues`                                          | так же (из `/rxjs`)                                              | ✅ идентично |
| нижележащий mock                                                      | `jest.fn()` → `vi.fn()`                                          | 🔁 заменено  |

Осталось только убедиться, что тесты идут под Vitest (или под Bun / `node:test` через свою точку
входа), а для Angular — что поднят `TestBed`.

### Достать спай обратно из контейнера {#reading-a-spy-back-out-of-the-container}

`Spy<T>` здесь строже, чем в `jest-auto-spies`, поэтому приведение типа, которым набита перевозимая
сюита, перестаёт компилироваться:

```ts
// jest-auto-spies
devicesService = TestBed.inject(DeviceListService) as Spy<DeviceListService>;
// TS2352: Conversion of type 'DeviceListService' to type 'Spy<DeviceListService>'
//         may be a mistake because neither type sufficiently overlaps with the other.

// vitest-auto-spy
devicesService = asSpy(TestBed.inject(DeviceListService));
```

`asSpy` — типизированная тождественная функция: она утверждает то, что `provideAutoSpy` уже положил в
контейнер, но без приведения. `injectSpy(DeviceListService)` — то же самое, только с вложенным внутрь
`TestBed.inject`. Это самая частая ошибка компиляции в перевезённой Angular-сюите, и выдаётся она по
одной на каждый внедряемый дубль, так что глобальный поиск до первого запуска себя окупает.

Либо оставьте поиск [`prefer-as-spy`](/ru/utilities/eslint-plugin) — правило сообщает о каждом таком
приведении и переписывает их под `--fix`, вместе с импортом.

### Имена типов {#the-type-names}

`vi` — глобал, поэтому единственное, что перевезённая спека импортирует из `vitest`, — это типы. Три
переименования из четырёх прямолинейны, а четвёртое тихо означает противоположное тому, что означало:

| Jest                  | Vitest              | Импорт                                         |
| --------------------- | ------------------- | ---------------------------------------------- |
| `jest.Mocked<T>`      | `Mocked<T>`         | `import type { Mocked } from 'vitest'`         |
| `jest.MockedFunction` | `MockedFunction`    | `import type { MockedFunction } from 'vitest'` |
| `jest.SpyInstance`    | `MockInstance`      | `import type { MockInstance } from 'vitest'`   |
| `jest.Mock<R, [A]>`   | `Mock<(a: A) => R>` | `import type { Mock } from 'vitest'`           |

::: warning `jest.Mock` переставляет свои дженерики местами
Jest пишет **сначала тип возврата, потом аргументы**; `Mock` из Vitest принимает одну сигнатуру
вызова. Переименование, которое оставляет аргументы там, где они были, компилируется без единой
жалобы в тип с обратным смыслом, и ничего не падает, пока с ним не разойдётся какое-нибудь место
вызова:

```ts
// jest — возвращает void, принимает один AdjustedSubscriptionDetails
let callBack: jest.Mock<void, [AdjustedSubscriptionDetails]>;

// vitest — тот же смысл, записанный сигнатурой вызова
let callBack: Mock<(details: AdjustedSubscriptionDetails) => void>;
```

Голый `jest.Mock` без дженериков — безопасный случай: `Mock` сам по себе означает то же самое.
:::

Для всего, что произвела эта библиотека, объявляйте `Spy<T>`, а не `Mocked<T>` —
[`no-mocked-for-spy`](/ru/utilities/eslint-plugin) объясняет почему и входит в пару правил, которые
чинят себя сами.

Импорт типов из `vitest` кладите в группу внешних пакетов, ко всем остальным. Поставить его над
импортами фреймворка соблазнительно — это единственная строка в файле, которая на самом деле не
зависимость, — и тогда у `eslint-plugin-import` появляется мнение о каждой спеке в сюите:

```
error  There should be at least one empty line between import groups        import/order
error  `vitest` type import should occur after import of `@angular/router`  import/order
```

### Вызовы `jest.*`, у которых нет двойника в `vi.*` {#the-jest-calls-that-have-no-vi-twin}

Механическое переименование `jest.` → `vi.` порождает вызовы, которых не существует, а получившееся
`TypeError: vi.requireMock is not a function` читается как «раннер сломался». Вот те, которые стоит
знать до переименования, потому что для каждого честный ответ — другая конструкция, а не другое имя.

| Jest                                                                    | Vitest                           | Что делать вместо этого                                                                                                                             |
| ----------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jest.requireMock(id)`                                                  | **нет**                          | отдать дубль через TestBed / контейнер либо передать аргументом                                                                                     |
| `jest.requireActual(id)`                                                | `vi.importActual(id)`            | через `await` и только внутри фабрики `vi.mock`                                                                                                     |
| `jest.fn().mockImplementation(() => o)` вместе с `new`                  | **не конструктор**               | [`mockConstructor` / `stubConstructor`](/ru/utilities/constructor-doubles)                                                                          |
| `jest.spyOn(global, 'Date')`                                            | **бросает**                      | `mockSystemTime(iso)` — фейковые таймеры уже владеют `Date`                                                                                         |
| `jest.replaceProperty(obj, key, value)`                                 | **нет**                          | `mockValueProp(obj, key, value)` — и он восстанавливает себя сам                                                                                    |
| `fakeTimers: { enableGlobally: true }`                                  | **нет настройки**                | `setupAutoSpy({ globalFakeTimers: true })`                                                                                                          |
| `jest.mock('some-barrel')`                                              | `vi.mock(…)`                     | **молчаливый no-op**, как только спеки собраны в бандл — границы модуля, которую он подменял бы, больше нет                                         |
| `jest.spyOn(barrel, 'exported')`                                        | **бросает**                      | `TypeError: Cannot redefine property` — экспорт из бандла не configurable; [сделайте настоящий шов](/ru/utilities/module-mocks#provide-a-real-seam) |
| `jest.fn().mockImplementation()` без аргумента                          | **аргумент обязателен**          | `mockImplementation(() => undefined)` — Jest подставлял вам no-op сам                                                                               |
| `xit` / `xdescribe`                                                     | **нет**                          | `it.skip` / `describe.skip`; переименование падает как `TS2304: Cannot find name 'xit'`                                                             |
| `testTimeout: 30000` (один бюджет)                                      | **два поля**                     | выставьте `hookTimeout` в то же число — Vitest разрешает его отдельно и по умолчанию ставит 10 000 мс                                               |
| `expect(a).toHaveBeenCalledBefore(b)` между разными семействами шпионов | **неверный вердикт, без ошибки** | сравнивайте два авто-шпиона либо включите `setSpyEngine('runner')` — счётчики не общие, см. ниже                                                    |
| `collectCoverageFrom: [...]`                                            | `coverage.include`               | и **не** `coverage.all`: ключ убрали в Vitest 4, где проход по файлам, которые не импортировал ни один тест, ведёт один только `include`            |

Строка про таймауты — самая тихая из всех. `jest-circus` тратит один `testTimeout` и на хук, и на тело
теста; Vitest разрешает `hookTimeout` сам по себе, поэтому конфиг, перевёзший единственное число из
Jest, оставляет каждый хук на 10 000 мс. А дальше падение записывается не на тот счёт: таймаут
`beforeEach` приписывается **тесту**, длительность теста прибивается к лимиту, и в логе значится
`× should create 10045ms` про тело, которое ни разу не выполнялось.
[`setupAutoSpy()`](/ru/utilities/setup) сообщает об этом в тексте ошибки; починка — одна строка в
конфиге:

```ts
test: {
  testTimeout: 30_000,
  // У Jest был один бюджет на оба; Vitest сам по себе ставит здесь 10_000.
  hookTimeout: 30_000,
}
```

`slowTestThreshold` — из той же семьи и меняет только отчёт: `5` в Jest (**секунды**), `300` в Vitest
(**миллисекунды**), так что перевезённая сюита начинает помечать медленными почти все свои файлы.

Строка про покрытие тоже меняет отчёт, причём двумя способами, к которым стоит быть готовым.
`coverage.all` больше не существует — конфиг, перевёзший `all: true` из Vitest 3, не задаёт ничего, и
отчёт молча сужается до файлов, которые прогон импортировал, пока не объявлен `coverage.include`. А
Jest инструментирует через istanbul, тогда как провайдер по умолчанию у Vitest — `v8`, который считает
каждый объект-функцию, созданный движком, а не те, о которых заявляет source map, — так что процент по
функциям сдвигается на неизменившемся дереве, пока строки и ветки стоят на месте. Порог по покрытию
функций перемерьте заново, прежде чем перевозить; не переносите число.

Последняя строка обходится дороже всего, потому что о ней никто не сообщает. Под сборщиком, который
бандлит тесты, — и под `isolate: false`, где модуль может уже лежать в графе воркера, — `vi.mock()`
barrel-модуля из воркспейса, `@angular/core` или относительного пути либо не делает ничего, либо делает
что-то только на части прогонов. Если мок «работает в узком прогоне и не работает в широком» —
причина именно эта: [замените мок настоящим швом](/ru/utilities/module-mocks#provide-a-real-seam)
(провайдер, аргумент, `vi.hoisted()` для пакета, который действительно необходимо подменить). Строка
ниже — то же самое падение, только со звуком: попытка взять вместо этого `vi.spyOn` по barrel-модулю бросает
`Cannot redefine property`, а спай на аксессор, взятый через этот пакет, перебрасывает эту ошибку,
назвав свойство, цель и выход.

**Строка про порядок вызовов — единственная здесь, которая отвечает, а не падает, и именно поэтому
её стоит прочитать до переименования.** `toHaveBeenCalledBefore` / `toHaveBeenCalledAfter` сравнивают
`mock.invocationCallOrder`, а шпионы методов этого пакета нумеруют вызовы своим счётчиком, тогда как
`@vitest/spy` держит свой в модульной переменной, которую он не экспортирует и подвинуть не даёт. Под
Jest вопроса не возникало: `jest-auto-spies` собирал двойники через `jest.fn()`, так что авто-шпион и
рукописный мок жили в одной последовательности и утверждение значило то, что написано. Здесь — нет, и
две шкалы расходятся ровно на столько вызовов каждого вида, сколько набор уже сделал. Замерено в одном
переведённом наборе: двойник отчитался `[164, 165, 167, 168, 169]`, а стоящий рядом `vi.fn()` —
`[28]` за свой единственный вызов **в том же тесте**, под утверждением, которое до этого проходило.
Трёх более ранних вызовов одного семейства достаточно, чтобы ответ перевернулся.

Две починки, обе в одну строку. Сравнивать два двойника одного семейства — обычно это и есть честное
прочтение, потому что обе стороны утверждения о порядке являются коллабораторами кода под тестом. Или
перевести весь прогон на фабрику раннера:

```ts
import { setSpyEngine } from 'vitest-auto-spy/setup';

setSpyEngine('runner'); // шпионы методов снова vi.fn(), счётчик у обоих семейств общий
```

Это единственное, чего два движка не разделяют, и единственная причина, по которой переключатель
существует.

::: tip Ограничение — отдельная опция
До v1 эта библиотека читала `methodsToSpyOn` как исчерпывающий белый список — противоположно
`jest-auto-spies` и ровно та единственная вещь, из-за которой замена переставала быть заменой:
перевезённая спека, перечислившая пару имён, молча теряла все остальные методы, а падение всплывало
как `… is not a function` внутри конструктора, и ничто в стеке на спеку не указывало. Начиная с v2
опция дополняющая, а белый список живёт под собственным именем — `onlyMethodsToSpyOn`.
:::

## По шагам {#step-by-step}

1. **Поставить и убрать.**

   ```bash
   npm i -D vitest-auto-spy
   npm rm jest-auto-spies   # или @bugsplat/vitest-auto-spies
   ```

2. **Отдайте механические шаги ниже [кодмоду](/ru/utilities/codemod)**, и пусть он доложит о местах,
   где ему пришлось бы гадать. По умолчанию это сухой прогон — первая команда печатает дифф и ничего
   не пишет:

   ```bash
   npx vitest-auto-spy codemod            # прочитать дифф
   npx vitest-auto-spy codemod --write    # применить
   npx vitest-auto-spy codemod --verify   # а затем проверить результат, а не дифф
   ```

   На jest-файле отрабатывают семь трансформов: разделение импорта, описанное ниже,
   `TestBed.inject(X) as Spy<X>` → `asSpy<X>(…)`, `@jest/globals` → `vitest`, члены `jest.*`, у которых
   есть двойник в `vi.*`, перестановка `jest.Mock<R, [A]>`, о которой
   [раздел про имена типов](#the-type-names), псевдонимы jasmine и `mockImplementation()` без
   аргумента. Ещё шесть существуют для [диалекта jasmine](/ru/migrating-jasmine) и выбираются на файл
   через `--from`, у которого значение по умолчанию `auto`; передайте `--from jest-auto-spies`, чтобы
   зафиксировать выбор. Всё из
   [таблицы выше, у чего двойника нет](#the-jest-calls-that-have-no-vi-twin), остаётся ровно как было
   и называется с `path:line` — поэтому прогон выходит с кодом 1, сделав при этом свою работу:
   оставшиеся строки — решения, а не переименования.

   Шаги ниже — это то, что кодмод делает и что он возвращает вам обратно; читайте их в любом случае,
   потому что отчёт на них ссылается.

3. **Перепишите импорты.** Ядро сохраняет своё имя; Angular-хелперы и слой observable уехали за
   подпути.

   ```diff
   - import { createSpyFromClass, provideAutoSpy } from 'jest-auto-spies';
   + import { createSpyFromClass } from 'vitest-auto-spy';
   + import { provideAutoSpy } from 'vitest-auto-spy/angular';
   ```

   То, какое имя за каким подпутём лежит, в кодмод не зашито — оно читается в момент запуска из карты
   `exports` того `vitest-auto-spy`, который вы только что поставили, а
   `npx vitest-auto-spy codemod --list` печатает всю таблицу целиком.

4. **Добавьте импорт rxjs один раз** — в файл настройки, а не в каждую спеку, — если хоть один спай
   пользуется `nextWith`, `nextWithValues` или `observablePropsToSpyOn`:

   ```ts
   // vitest.setup.ts
   import 'vitest-auto-spy/rxjs';
   ```

   Пропуск этого шага не проваливается молча: первый же observable-хелпер бросает сообщение, в котором
   назван ровно этот импорт.

5. **Возьмите точку входа под свой раннер.** `vitest-auto-spy` регистрирует адаптер Vitest, `/bun` —
   адаптер `bun:test`, `/node` — адаптер `node:test`. Один на прогон.

6. **Типизируйте переменные как `Spy<T>`.** Если спека объявляла `let service: MyService = createSpyFromClass(...)`,
   теперь она перестанет компилироваться, когда у класса есть `#private`- или `private`-члены: `Spy<T>` —
   это mapped type, и он их отбрасывает. Починка — `let service: Spy<MyService>` либо
   [`asInstance` / `asSpy`](/ru/core/spy-typing) там, где спай нужно отдать чему-то, типизированному
   самим классом.

7. **Прогоните сюиту.** Больше в API ничего не менялось, так что всё, что падает сейчас, — настоящее.

8. **Необязательно, но окупается, как только всё зелёное:**
   [`setupAutoSpy()`](/ru/utilities/setup) в файле настройки и
   [правила ESLint](/ru/utilities/eslint-plugin), которые уводят сюиту на более новые хелперы.

## Подводные камни по раннерам {#per-runner-gotchas}

**Vitest.** Ничего сверх замены импортов. Если сюита идёт с `isolate: false` или в общей среде,
добавьте `setupAutoSpy()` — Jest изолировал каждый файл, и патч `mock*Prop`, безобидный там, теперь
переживает свою спеку.

**`vi.fn(() => x)` — это не `mockReturnValue(x)`.** То единственное переименование в миграции, которое
выглядит безопаснее всех и при этом неэквивалентно. Фабрика читает `x` в момент **вызова** дубля;
`mockReturnValue` замораживает то значение, которое `x` имел в момент **настройки** дубля. Отличить их
нечем, пока тест не переприсвоит `x` — а самая частая причина так поступить — это свежий `Subject`
после того, как предыдущий получил `error()` или завершился, то есть ровно то, что сюита и проверяет,
когда переприсваивает:

```ts
let source$ = new Subject<Page>();

const api = createSpyFromClass(Api);

api.load.mockReturnValue(source$); // ❌ прибито к тому субъекту, который существовал на этой строке
api.load.mockImplementation(() => source$); // ✅ перечитывается на каждом вызове

source$.error(new Error('boom'));
source$ = new Subject<Page>(); // дубль всё ещё выдаёт мёртвый, тот, что выше
```

В одной спеке это означало, что сервис получал завершённый субъект и молча пропускал модалку, которую
должен был показать, — и тест всё это время был зелёным. Перевозите `vi.fn(() => x)` как
`mockImplementation(() => x)`, а `mockReturnValue` оставьте для литерала; и если вы пишете кодмод, то
вот эта перезапись — та, для которой нужен отдельный случай.

**Bun (`bun:test`).** `mockReset()` на Bun сбрасывает ещё и реализацию (Vitest спай сохраняет) —
адаптер её восстанавливает, так что auto-spies это не задевает, но написанный руками `mock()` в той же
спеке поведёт себя иначе. `spyOn` на Bun отказывается работать со свойствами-аксессорами; здешние
спаи на аксессоры идут через переопределение свойства и работают всё равно. Angular-сюитам нужен
[`vitest-auto-spy/bun-angular`](/ru/runtimes/bun-angular).

**`node:test`.** Здесь нет `expect` — берите в пару `node:assert`. И `spy.method.mockReturnValue` —
это _нативный_ метод Vitest/Bun, которого у `node:test` нет; нормализованный
`spy.method.calledWith(...).mockReturnValue(...)` работает везде. Записанные вызовы читаются как
`mock.calls[0].arguments`, а не `mock.calls[0]`. См. [node:test](/ru/runtimes/node).

**Angular.** `provideAutoSpy` здесь по умолчанию создаёт **ленивые** спаи (`jest-auto-spies` всегда
делал их сразу). Поведение идентично; если вы полагаетесь на то, что каждый спай существует до первого
обращения, передайте `{ lazySpies: false }`.

## Не потеряла ли миграция тест? {#did-the-migration-lose-a-test}

```ts
import { compareTestRuns, formatTestRunComparison } from 'vitest-auto-spy/diagnostics';

const diff = compareTestRuns(JSON.parse(before), JSON.parse(after), '/my-repo/');

expect(diff.missing).toEqual([]);
process.stdout.write(formatTestRunComparison(diff));
```

Счётчики на этот вопрос не отвечают. Под `isolate: false` файл может потерять целую сюиту — файл
спеки, который экспортируется и импортируется соседом, теряет собственный `describe`, — и в том же
прогоне где-то в другом месте может начать проходить нестабильный тест. Итоги сходятся, прогон
выглядит таким же, а сюиты молча нет.

Вопрос в том, **какие** тесты выполнились, поэтому ответ — симметрическая разность двух множеств
`file::full name`. Оба раннера пишут JSON одной формы (`--reporter=json`), так что базовая линия может
приехать из Jest, а текущий прогон — из Vitest; необязательный третий аргумент отрезает всё выше
общего корня пути, так что отчёт из CI сравнивается с отчётом с ноутбука.

Переименованный тест появляется и в `missing`, и в `added` — и это честный ответ, потому что снаружи
переименование и «удалить плюс добавить» — одно и то же событие.

::: tip Что это поймало на самом деле
На миграции, из которой это выросло, сравнение после правок объёмом в семь агентов показало ровно один
пропавший тест — он проверял ключ конфига, который удалили полугодом раньше в никак не связанном
коммите, — и больше ничего молча не потерялось. Только так эту фразу и можно было произнести.
:::

## Кодмод, который правит глобы, проверяется совпадением, а не диффом {#a-codemod-that-edits-globs-is-verified-by-matching-not-by-diffing}

Естественная проверка кодмода — «изменился ли файл так, как я задумал?». Для кодмода, который
переписывает **глобы**, эта проверка проходит при сломанном результате, потому что пустой `include` —
законный `tsconfig.json`, и TypeScript об этом ничего не говорит.

Это не гипотетически. Миграционный кодмод, убиравший `jest.config.ts` из `include`, воспользовался
жадным шаблоном, который заодно съедал `/**/*`, и `src/**/*.spec.ts` превратилось в `src*.spec.ts` —
синтаксически валидно и не совпадает ни с одним файлом. Из 152 tsconfig'ов для спек свои спеки всё ещё
покрывали **девять**. Не упало ничего: `tsc --noEmit` сообщал о нуле ошибок, потому что проверять было
нечего, и единственным, кто об этом узнал, оказался человек, открывший спеку в редакторе и увидевший
`Cannot find name 'vi'`.

Поэтому проверка звучит так: **совпадает ли получившийся шаблон хотя бы с одним существующим
файлом?** И печатать получившийся `include` целиком, а не счётчик — «исправлено: 152» прячет случай, в
котором замена породила две разные неправильные формы, а именно это и случилось при первой попытке
починки.

[`npx vitest-auto-spy codemod --verify`](/ru/utilities/codemod#verifying-by-matching-not-by-diffing) —
это и есть такая проверка, встроенная в описанный выше кодмод. Каждый из тринадцати его трансформов
объявляет шаблон, который он обязан был убрать; `--verify` ничего не преобразует и сопоставляет эти
шаблоны с **результатом**, называя каждого выжившего с `file:line`. Из сопоставления вместо диффа
следуют два свойства, и ни одно из них недоступно проверке, построенной на диффе: она отвечает
одинаково и на файле, которого этот инструмент никогда не касался, — перевезённом руками или
исключённом через `--skip`, — а значит, ей место в CI на уже перевезённой сюите; и она ловит случай,
когда дифф ровно такой, как надо, а в файле по-прежнему написано `jest.`, потому что трансформ не стал
заходить в шаблонный литерал или не смог перебраться через несбалансированную скобку. А отчёт о
прогоне печатает получившиеся **операторы импорта целиком**, а не «6 правок» — по той же причине, что
этот раздел приводит про `include`.
