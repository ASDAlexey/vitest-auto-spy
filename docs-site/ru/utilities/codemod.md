title: Кодмод — npx vitest-auto-spy codemod
description: Тринадцать трансформаций, которые переводят сюиту с jest-auto-spies и Jest или с jasmine-auto-spies и jasmine — раскладывают легаси-импорт по точкам входа, которые установленный пакет реально экспортирует, переставляют jest.Mock<R, [A]> в сигнатуру вызова, которую принимает Vitest, возвращают spyOn заглушку, которую jasmine ставил даром, и рапортуют о каждом фрагменте, который переписать отказались. По умолчанию сухой прогон; --verify проверяет результат сопоставлением, а не дифом.

# Кодмод

```bash
npx vitest-auto-spy codemod            # сухой прогон: печатает диф, ничего не пишет
npx vitest-auto-spy codemod --write    # применить
npx vitest-auto-spy codemod --verify   # сверить результат с тем, чего быть уже не должно
```

[Переезд](/ru/migrating) — это find-and-replace ровно до того места, где он им быть перестаёт, а
места, где перестаёт, не падают — они компилируются. `jest.Mock<void, [Order]>`, переименованный на
месте, превращается в мок, который принимает `void` и возвращает `Order`. `jest.requireMock`,
переименованный на месте, превращается в `TypeError: vi.requireMock is not a function`, что читается
как «раннер сломался». Легаси-импорт, переехавший на `vitest-auto-spy` целиком, прячет
`provideAutoSpy` за точкой входа, которая его не экспортирует.

А на стороне jasmine у той же фразы есть пример похуже: `spyOn(o, 'm')`, переименованный в
`vi.spyOn(o, 'm')`, инвертирует поведение по умолчанию — jasmine заглушает метод, Vitest вызывает
настоящий, — так что реальная реализация начинает выполняться внутри каждой спеки, которая ставила
спай именно чтобы её остановить, и молча.

Поэтому это кодмод, а не `sed`-скрипт, и бо́льшая часть его работы — **отказываться**: тринадцать
трансформаций, каждая из которых либо переписывает фрагмент, про который может принять решение, либо
оставляет его ровно как был и называет в отчёте.

что сказать.

## Тринадцать трансформаций {#the-thirteen-transforms}

У каждой есть id, и каждую можно отключить по отдельности. Ничего не применяется, пока все
трансформации не посмотрят на один и тот же нетронутый исходник, так что `--skip` убирает правки
одной трансформации и больше ничего — он не может изменить то, что видели остальные.

Они делятся на три семейства. **Четыре общие**, потому что конструкция есть в обоих диалектах:

| Id                          | Переписывает                                                                                          | Отказывается                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `auto-spies-import`         | `import … from 'jest-auto-spies'` / `'jasmine-auto-spies'` → точки входа, экспортирующие каждое имя      | Дефолтный или namespace-импорт; имя, которого не экспортирует никто |
| `inject-cast`               | `TestBed.inject(X) as Spy<X>` → `asSpy<X>(TestBed.inject(X))`, добавляя импорт                          | `as Spy<T>` над чем угодно ещё                                     |
| `jasmine-aliases`           | `xit` / `xdescribe` / `fit` / `fdescribe` / `xtest` → `it.skip` / `describe.skip` / …                    | Одноимённый метод — `shape.fit(box)` не трогается                  |
| `mock-implementation-arity` | `mockImplementation()` без аргумента → `mockImplementation(() => undefined)`                            | Вызов, у которого функция уже есть                                 |

**Три — от Jest:**

| Id                    | Переписывает                                                                                        | Отказывается                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `jest-globals-import` | `from '@jest/globals'` → `from 'vitest'`, переименовывая биндинг `jest` в `vi`                        | Остальную часть клаузы — `describe` / `it` / `expect` называются так же     |
| `jest-namespace`      | `jest.<member>` → `vi.<member>` для 26 членов, у которых есть двойник                                 | Член без двойника и любой член, которого он не знает                       |
| `jest-types`          | `jest.Mock<R, [A]>` → `Mock<(a: A) => R>`, плюс четыре переименования, с импортом имени из Vitest      | Список типовых аргументов, который не удалось разбить по верхнему уровню   |

**Шесть — от jasmine**; что именно каждая из них защищает, см. в
[Переезде с jasmine-auto-spies](/ru/migrating-jasmine):

| Id                    | Переписывает                                                                                                                                       | Отказывается                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `jasmine-and-helpers` | `spy.load.and.nextWith(v)` → `spy.load.nextWith(v)` — десять хелперов auto-spies теряют namespace                                                       | Ни от чего; список закрыт                                                                               |
| `jasmine-strategies`  | `.and.returnValue` / `callFake` / `stub` / `throwError` / `returnValues` / `resolveTo` → двойник `mock*`, а `.withArgs(` → `.calledWith(`               | `.and.callThrough()`, которому нечего вызывать; неизвестную стратегию                                   |
| `jasmine-spy-on`      | `spyOn(o, 'm')` → `vi.spyOn(o, 'm').mockImplementation(() => undefined)`                                                                                | Вызов, к которому уже прицеплена стратегия, — там заглушка была бы лишней                               |
| `jasmine-globals`     | `jasmine.createSpy` / `createSpyObj` / `any` / `clock()` / `addMatchers` → их двойники из `vi`, `expect` и `vitest-auto-spy`                            | `getEnv`, `truthy` / `falsy` / `empty` / `notEmpty`, `DEFAULT_TIMEOUT_INTERVAL`, стратегии спаев        |
| `jasmine-types`       | `jasmine.Spy` → `Mock` из `vitest`, `jasmine.SpyObj<T>` → `Spy<T>` из этого пакета                                                                      | Любое из этих имён, когда таблицу точек входа сгенерировать не удалось                                  |
| `jasmine-matchers`    | `toBeTrue` / `toBeFalse` / `toHaveSize` / `toHaveBeenCalledOnceWith` / `withContext` / `fail` → их написания в Vitest                                   | Ни от чего; каждое — закрытое переименование                                                            |

`auto-spies-import` идёт первой, потому что именно она создаёт импорт `vitest-auto-spy`, в который
`inject-cast` потом дописывает `asSpy`. Всё, что после, от порядка не зависит.

### `--from` выбирает семейство {#from-picks-the-family}

```bash
npx vitest-auto-spy codemod --from jasmine   # или jasmine-auto-spies
npx vitest-auto-spy codemod --from jest-auto-spies
npx vitest-auto-spy codemod                  # --from auto, по умолчанию
```

`auto` читает каждый файл и решает: файл, в котором есть член `jasmine.`, `.and.`, импорт
`jasmine-auto-spies` или `vitest-auto-spy/jasmine`, получает семейство jasmine; файл, в котором
ничего из этого нет, — не получает. Общая четвёрка выполняется всегда.

Голый `spyOn(` сознательно **не** считается маркером. Это единственная конструкция, которую оба
диалекта пишут одинаково и наделяют противоположными умолчаниями — jasmine заглушает, Vitest
вызывает настоящий, — так что догадка о том, что имел в виду файл, и есть та самая молчаливая
инверсия поведения, ради предотвращения которой существует `jasmine-spy-on`. Сюита, у которой из
jasmine-конструкций только `spyOn`, обязана сказать `--from jasmine` вслух. Нераспознанное значение —
это ошибка с перечислением допустимых, а никогда не молчаливый откат: диалект с опечаткой, тихо
запустивший другое семейство, — это переезд, который выглядит завершённым и таковым не является.

Два правила про `import` и `jest-namespace` стоит читать вместе. `jest.dontMock` становится
`vi.doUnmock` — это переименование, а не копия, — а `jest.SpyInstance` становится `MockInstance`.
`vi.mock()` **относительного** пути переименовывается, а затем сопровождается предупреждением:
под тестовым билдером с бандлингом границы модуля, которую он подменял бы, больше нет, и мок молча
превращается в no-op; вместо этого [сделайте настоящий шов](/ru/utilities/module-mocks#provide-a-real-seam).

## Ловушка: у Jest тип возврата стоит первым {#the-trap-jest-puts-the-return-type-first}

```diff
- let hook: jest.Mock<void, [Order]>;
+ let hook: Mock<(order: Order) => void>;
```

Первый типовой аргумент Jest — это **тип возврата**, второй — **кортеж аргументов**. Единственный
типовой аргумент Vitest — это **сигнатура вызова**. Переименование, оставляющее типовые аргументы на
месте — а именно так поступает каждый гист про миграцию, — чисто компилируется в обратный смысл, и
ничего не падает, пока с ним не разойдётся какая-нибудь точка вызова, где-то в другом месте и позже.

Поэтому эта трансформация пересобирает тип, а не переименовывает его, и четыре детали отделяют
безопасный вариант от более медленного способа ошибиться:

- **Сопоставитель скобок проглатывает `=>` целиком.** Без этого `jest.Mock<() => void, []>`
  «закрывает» список типовых аргументов на `>` от стрелки, и переписывание молча забирает половину
  типа.
- **Элементы кортежа сохраняют метки, опциональность и rest.**
  `[id: number, force?: boolean, ...rest: string[]]` превращается в
  `(id: number, force?: boolean, ...rest: string[])`. Элемент без метки нумеруется `arg0`, `arg1` —
  функциональный тип обязан именовать свои параметры, а кортеж Jest этого не делал.
- **Всё, что не литерал кортежа, разворачивается через spread, а не разбирается.**
  `jest.Mock<void, Args>` становится `Mock<(...args: Args) => void>` — именно это второй аргумент
  Jest означает для любого возможного `Args`, и понимать про него ничего не надо.
- **Три и более типовых аргумента дают заметку об ошибке и никакой правки.** Как и несбалансированные
  `<`…`>`. Строка остаётся байт в байт как была, а `jest-mock-type-arguments` её называет.

`jest.Mock` вовсе без типовых аргументов остаётся просто `Mock`: сам по себе он и так означает по обе
стороны одно и то же.

## Таблица точек входа генерируется, а не записана руками {#the-entry-point-table-is-generated-not-written-down}

Чтобы разложить `import { createSpyFromClass, provideAutoSpy, Spy } from 'jest-auto-spies'`, надо
знать, какое имя живёт за какой точкой входа, — а таблица, вбитая в исходник кодмода, верна для той
версии, под которую её писали, и неверна для той, которую поставил потребитель. Точка входа,
добавленная в более позднем миноре, — это имя, которое кодмод оставил бы в корне; переехавшая точка
входа — это переписывание, которое больше не резолвится. И то и другое на строке импорта всё ещё
компилируется.

Поэтому таблицы в исходнике нет. Во время работы команда:

1. **Находит установленный `vitest-auto-spy`**, поднимаясь по `node_modules` до шести директорий
   вверх от рабочей — этого хватает для воркспейса с поднятыми зависимостями, — и в крайнем случае
   откатывается к той копии, из которой запущен сам CLI.
2. **Читает собственную карту `exports` этого пакета** и разрешает каждый subpath в файл, предпочитая
   условие `types`: файл деклараций называет type-only экспорты, которых рантайм-бандл назвать не
   может. Чекаут без `dist` откатывается к исходникам рядом — так монорепозиторий потребляет пакет до
   первого релиза.
3. **Собирает экспортированные имена лексически** — именованные клаузы, объявления и оба написания
   звёздчатого реэкспорта, `export * from './…'` и `export type * from './…'`, проходя по barrel-модулям на
   глубину до восьми — по [представлению с замаскированными комментариями и
   строками](#how-a-pattern-never-matches-a-comment) каждого файла, чтобы имя внутри комментария или
   строки не считалось экспортом.

Результат — справочник «имя → специферы», в котором ложным срабатываниям взяться неоткуда, потому что
это не догадка про API — это _и есть_ API, считанное с копии на диске.

::: warning Два написания `export *` не взаимозаменяемы, и разница не видна
Type-only форма — это то, чем пакет реэкспортирует свою публичную поверхность типов одной строкой, так
что обходчик, знающий только форму для значений, теряет все типы разом — здесь это `Spy<T>` и всё, что
объявлено рядом. Про потерю ничего не сообщается: таблица всё равно строится, всё равно выглядит
полной, а трансформация импорта просто решает, что имя разместить не может, и оставляет импорт на
`jest-auto-spies` с ошибкой остатка. Проявляется это к тому же только на пути через исходники,
поскольку `.d.ts` перечисляет свои экспорты явно, — так что сюита, прогнанная против собранного
`dist`, остаётся зелёной, а та же сюита до сборки падает.
:::

**Порядок разрешения**, когда имя экспортируется больше чем одной точкой входа:

1. **Побеждает корень**, если он экспортирует это имя, потому что корень — это точка входа, которая
   регистрирует mock-адаптер, и она есть у каждого раннера.
2. Иначе **побеждает точка входа самого репозитория** — то же определение раннера и фреймворка, что
   использует [`init`](/ru/utilities/cli), так что `provideAutoSpy` уходит в `/angular` в
   Angular-репозитории и в `/nestjs` в NestJS-репозитории.
3. Иначе побеждает **единственная точка входа, у которой это имя есть**.
4. Две некорневые точки входа и никакого предпочтения — **по файлу не решается**. Имя остаётся
   импортироваться из легаси-пакета и попадает в отчёт как `unmapped-legacy-export`.

Когда установленную копию не удаётся найти вообще, таблицы нет, и четыре трансформации, которым она
нужна, — `auto-spies-import`, `inject-cast` и две jasmine-трансформации, которым надо разместить
`createSpyObj` и `Spy<T>`, — отказываются работать и говорят об этом, а не гадают. Неправильная точка
входа, которая всё-таки компилируется, — ровно тот провал, ради предотвращения которого эта команда и
существует.

## Что он сознательно оставляет как есть {#what-it-deliberately-leaves-alone}

Этот список и есть фича. Каждая запись — фрагмент, для которого существует правдоподобное
переписывание, оно компилируется и оно неверно, — поэтому кодмод вместо правки печатает его, с
причиной и с `path:line`, который редактор превращает в переход.

| Оставлено как есть                                                              | Почему                                                                                                                                        |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `jest.requireActual(id)`                                                        | `vi.importActual(id)` асинхронен и легален только внутри фабрики `vi.mock` — переписывание меняет поток управления вокруг него                   |
| `jest.requireMock(id)`, `jest.setMock(…)`                                       | Двойника `vi` нет; дубль отдаётся через TestBed / контейнер либо передаётся аргументом                                                           |
| `jest.replaceProperty(o, k, v)`                                                 | Ответ — `mockValueProp(o, k, v)` из этого пакета: другой хелпер со своим восстановлением, а не член с новым именем                              |
| `jest.setTimeout(n)`                                                            | Замена — опция конфига `testTimeout` или `vi.setConfig({ testTimeout: n })`; аргумент там уже не просто число                                    |
| `enableAutomock`, `createMockFromModule`, `now`, `retryTimes`, `runAllTicks`, … | Члена `vi` с таким именем не существует, и для каждого честный ответ — другой дизайн                                                            |
| Любой **неизвестный** `jest.<member>`                                           | Никогда не переименовывается в расчёте на то, что у `vi` он есть. Это допущение и есть падение `vi.requireMock is not a function`                |
| `as Spy<T>` над чем угодно, кроме `TestBed.inject(...)`                         | Если значение и правда спай — `asSpy(...)`; если это самодельный дубль — его строит [`createAutoMock<T>()`](/ru/core/auto-mock-by-type)         |
| Дефолтный или namespace-импорт легаси-пакета                                    | Хелперы живут за разными точками входа, а namespace не может стоять сразу на нескольких                                                          |
| Всё, что внутри шаблонного литерала                                             | Каждый паттерн сопоставляется с замаскированным представлением; содержимое шаблонного литерала там пусто                                         |
| Любой фрагмент, где не сходятся скобки                                          | Конец области неизвестен, а угадывать, где он, — это и есть способ забрать половину типа                                                         |

### Как паттерн никогда не попадает в комментарий {#how-a-pattern-never-matches-a-comment}

Кодмод, сопоставляющий паттерны с сырым исходником, переписывает и фразу в комментарии, объясняющем
переезд, и строковый литерал в ассерте, который на неё проверяет. Ни то ни другое не падает громко —
файл всё ещё компилируется, а диф выглядит правдоподобно.

Поэтому каждый паттерн сопоставляется с **маской**: та же строка, той же длины, с теми же переводами
строк, но _содержимое_ комментариев, строк, шаблонных литералов и регулярных выражений заменено
пробелами. Смещения, найденные в маске, валидны и в оригинале — именно это делает безопасным принцип
«найти в маске, вырезать из исходника». Кавычки сохраняются, так что `from 'jest-auto-spies'` всё ещё
находится: кавычка сопоставляется в маске, а специфер читается из исходника между ними.

Проверка остатков ([ниже](#verifying-by-matching-not-by-diffing)) использует второе представление той
же маски, отличающееся ровно в двух местах, и оба раза потому, что искомое живёт внутри литерала:
специфер модуля остаётся видимым, потому что `from 'jest-auto-spies'` — это и _есть_ остаток, и
шаблонный литерал остаётся видимым, потому что трансформации отказываются править внутри него, а
оставленный там `jest.` настоящий. Обычная строка остаётся пустой —
`expect(text).toBe('jest.spyOn(…)')` — это проза про переезд, а не то, что нужно переносить.

## Проверка сопоставлением, а не дифом {#verifying-by-matching-not-by-diffing}

[Заключительная заметка страницы переезда](/ru/migrating#a-codemod-that-edits-globs-is-verified-by-matching-not-by-diffing)
доказывает, что естественная проверка кодмода — «поменялся ли файл так, как я хотел?» — проходит, пока
результат сломан, и что честная проверка — сопоставить **результат** с тем, чего там больше быть не
должно. `--verify` — это та заметка, реализованная в коде.

Каждая трансформация объявляет паттерн `residue` — то, что она должна была убрать. После прогона — или
на сюите, над которой этот инструмент вообще не запускали, — файлы сопоставляются с этими паттернами, и
каждый выживший попадает в отчёт с `file:line`:

```
$ npx vitest-auto-spy codemod --verify
vitest-auto-spy codemod — /work/app
1 files matched against 7 transform patterns.

error  residue/auto-spies-import src/app/service.spec.ts:1
       Still matches after the run: "from 'jest-auto-spies'"
error  residue/inject-cast src/app/service.spec.ts:10
       Still matches after the run: "as Spy<"
error  residue/jest-types src/app/service.spec.ts:7
       Still matches after the run: "jest.Mock"
```

Из сопоставления вместо дифа следуют два свойства, и ни одно из них недоступно проверке, построенной
на дифе:

- **Оно работает на файле, которого этот инструмент не касался.** Спека, которую кто-то перенёс
  руками, спека, которую правил другой агент, фрагмент, исключённый через `--skip`, — все они отвечают
  на один и тот же вопрос одинаково. `--verify` ничего не трансформирует, поэтому его безопасно
  оставить в CI на уже переехавшем репозитории: он выходит с 0 и `Nothing left to migrate.` — и с 1 в
  ту минуту, когда `jest.` возвращается.
- **Диф, выглядящий совершенно правильным, всё равно может оставить паттерн.** Внутрь шаблонного
  литерала трансформации заходить отказываются; в инструкцию с несходящимися скобками они не
  дотянулись. Изменение верное, а в файле по-прежнему написано `jest.`.

Отчёт печатает **итоговые import-инструкции целиком**, а не счётчик — те самые три строки под именем
файла в выводе сухого прогона выше. Это та же мысль, которую заметка про переезд высказывает про
`fixed: 152`, скрывающее случай, когда замена породила две разные неправильные формы. Счётчик говорит,
что блок импортов изменился; сами инструкции говорят, во что именно, — а это ровно то, что ревьюер всё
равно собирался проверить руками.

## Флаги {#flags}

| Флаг           | Что делает                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------- |
| _(нет)_        | Сухой прогон. Напечатать диф, счёт по трансформациям, итоговые импорты и отчёт. Ничего не писать                 |
| `--write`      | Применить правки. Фрагменты, оставленные как есть, так и остаются как есть и по-прежнему попадают в отчёт        |
| `--verify`     | Ничего не трансформировать; сопоставить файлы с паттернами остатков. Выйти с 1, если что-то совпало              |
| `--from <pkg>` | Какой у этой сюиты диалект: `jest-auto-spies`, `jasmine-auto-spies` (алиас `jasmine`) или `auto`                 |
| `--only <ids>` | Запустить только эти трансформации, через запятую                                                               |
| `--skip <ids>` | Запустить всё, кроме этих                                                                                       |
| `--list`       | Напечатать трансформации и сгенерированную таблицу точек входа и выйти с 0                                      |
| `--cwd <dir>`  | Работать в другой директории вместо текущей                                                                     |

Id, который не распознают ни `--only`, ни `--skip`, приводит к выходу с кодом **2** и перечислению
известных id, а не к тихому запуску всего подряд.

## В CI {#in-ci}

```yaml
- run: npx vitest-auto-spy codemod --verify
```

Одна строка, без сети, без конфига, без токена. На переехавшем репозитории это зелёный no-op; он
краснеет, когда снова появляется `jest.`, легаси-импорт или каст `as Spy<…>`, — а в сюите, достаточно
большой, чтобы её переносил кодмод, такие вещи появляются снова.

Порядок, который работает на настоящей сюите:

```bash
npx vitest-auto-spy codemod            # прочитать диф
npx vitest-auto-spy codemod --write    # применить
npx vitest-auto-spy codemod --verify   # затем проверить результат, а не диф
npx vitest-auto-spy doctor             # и то, что переезд оставил после себя
```

`doctor` — вторая половина той же смены: кодмод правит то, что переезд обязан изменить,
[`doctor`](/ru/utilities/cli) рапортует о том, что он оставляет после себя, — include-паттерн в
`tsconfig`, сломанный правкой, `jest.config.ts` для раннера, которого больше нет, setup-файлы, на
которые ссылался только он.
