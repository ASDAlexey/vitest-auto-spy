# Гигиена тестового прогона

```ts
// vitest.setup.ts
import { setupAutoSpy } from 'vitest-auto-spy/setup';

setupAutoSpy();
```

Один вызов вместо тех кусочков гигиены, которые иначе каждый проект собирает руками, — каждый из них
дёшево поставить и дорого диагностировать, когда его нет. Первые три включены по умолчанию,
остальные — переключатели, потому что они меняют то, что видит проверяемый код.

## 1. Восстановление пропатченных свойств {#_1-restoring-patched-properties}

`vi.restoreAllMocks()` знает про спаи, а не про свойства, которые переопределили
[`mockReadonlyProp` / `mockValueProp`](../adapters/angular#signal-readonly-property-mocking). При
`isolate: false` невосстановленный патч на глобале, прототипе или синглтоне утекает прямиком в
следующий файл. `setupAutoSpy()` регистрирует `restoreMockedProps()` в глобальном `afterEach`.

**И подстраховку в `onTestFinished` за ним**, потому что выполнение `afterEach` не гарантировано.
Vitest вызывает хуки `afterEach` в **обратном** порядке регистрации, так что зарегистрированный
setup-файлом оказывается _последним_, а любой хук, зарегистрированный самой спекой, — то есть
выполняющийся первым — утаскивает всю цепочку за собой, когда бросает:

```ts
// в файле спеки, а значит, до хука библиотеки
afterEach(() => vi.restoreAllMocks()); // ← бросает, и уборка под ним не происходит никогда
```

Это не гипотеза. Одна спека годами держала ровно эту строку; переезд на
`provideAutoSpy(LayoutStateService, { gettersToSpyOn: [...] })` сделал так, что восстановленный
геттер начал возвращать `undefined`, `ngOnDestroy` вызвал его как сигнал, и полученный `TypeError`
оборвал хук. Патч уехал дальше, а падение всплыло в **другом `describe`** как ошибка шаблона про
null-профиль. С самодельным `vi.fn()`, который он заменил, восстановленный геттер оставался
вызываемым, так что мина всё это время лежала невидимой.

`onTestFinished` выполняется после цепочки `afterEach` и делает то же, что делала она, так что
подстраховка возвращает свойства на место и предупреждает — называя количество и причину, в том
тесте, где это случилось, а не двумя тестами позже. На обычном пути это стоит одного булева
значения: она ничего не делает, если хук не пропустили.

`countMockedProps()` экспортируется для сюит, которые предпочтут это проверять:

```ts
afterEach(() => expect(countMockedProps()).toBe(0));
```

## 2. Одна копия библиотеки в процессе {#_2-one-copy-of-the-library-in-the-process}

Две копии держат два набора консольных спаев и два реестра, так что ассерт проверяет спай, который
никогда не подменял консоль, вызванную проверяемым кодом, — а симптом читается как «тесты падают в
зависимости от порядка файлов». Проверка роняет прогон отчётом, называющим обе копии и что делать с
каждой из причин: вторая установка либо одна установка, загруженная и в ESM-, и в CommonJS-форме.

```ts
import { describeDuplicateCopies, getPackageCopies } from 'vitest-auto-spy/setup';

getPackageCopies(); // зарегистрированные копии, для собственной отчётности
describeDuplicateCopies(); // человекочитаемый отчёт или undefined, когда копия одна
```

Обе функции экспортируются и из корневой точки входа.

## 3. Очистка реестра восстановления у раннера {#_3-draining-the-runner-s-restore-registry}

Каждый `vi.spyOn` добавляет запись, которую убирает только `vi.restoreAllMocks()`; при общей среде
этот список растёт на весь прогон. `restoreMocks: true` вычищает его после каждого теста.

## 4. Отмена таймеров, переживших свой файл {#_4-cancelling-timers-that-outlive-their-file}

По желанию, и имеет смысл только при `isolate: false` — там каждый файл спеки в воркере делит один
набор глобалов. `setTimeout`, который компонент завёл и не очистил, переживает создавший его файл:
колбэк срабатывает, пока **другой** файл в середине теста, против моков и DOM, которые больше не
совпадают, а раннер обвиняет тот файл, который случайно выполнялся в этот момент.

`requestAnimationFrame` — та половина, которую упускают. Планировщик zoneless change detection в
Angular гоняет таймаут наперегонки с кадровым колбэком, так что у компонента, уничтоженного в конце
одного файла, вполне может остаться поставленный кадр, — а всплывает потом внутренняя жалоба Angular
(планировщик выполняет watch'и во время планирования, чтение сигнала в фазе оповещения), приписанная
ни в чём не повинному коду.

```ts
setupAutoSpy({ strayTimers: true });
```

Это оборачивает четыре планировщика один раз на воркер и подметает всё оставшееся в `afterAll`.
Части экспортируются для сюиты, которая хочет подметать в другом месте — или хочет, чтобы утечка
**роняла** прогон, а не молча прибиралась:

```ts
import { cancelStrayTimers, countStrayTimers, trackStrayTimers } from 'vitest-auto-spy/setup';

const stop = trackStrayTimers(); // идемпотентно; возвращает отмену, которая заодно всё отменяет
afterEach(() => expect(countStrayTimers()).toBe(0));
afterAll(() => {
  const cancelled = cancelStrayTimers(); // сколько пришлось отменить

  if (cancelled > 0) {
    process.stdout.write(`${cancelled} timer(s) outlived this file\n`);
  }
});
```

Каждая принимает необязательный host, по умолчанию — настоящие глобалы, так что тест может
подсунуть свой объект-заменитель. При `isolate: true` это почти no-op — среда всё равно
выбрасывается после каждого файла.

`onStrayTimers` — тот же счёт, но не выходя из `setupAutoSpy`:

```ts
setupAutoSpy({ strayTimers: true, onStrayTimers: ({ cancelled }) => expect(cancelled).toBe(0) });
```

### Вместе с `--detect-async-leaks` из Vitest 4.1 {#with-vitest-4-1-s-detect-async-leaks}

::: warning Они гасят друг друга, и побеждает тихий
`detectAsyncLeaks` запоминает каждый асинхронный ресурс, созданный файлом, и, когда файл кончился,
спрашивает у каждого, держит ли его ещё кто-нибудь. Подметание идёт в `afterAll` — **до** этого
вопроса, — так что каждый отменённый им таймер отвечает «нет», и файл, который течёт таймерами,
считается не текущим вовсе.
:::

Отменять всё же правильнее по умолчанию: колбэк, срабатывающий во время более позднего файла, —
более дорогое падение, и именно ради него существует `strayTimers`. Поэтому, когда включены оба и
`onStrayTimers` не задан, подметание печатает в stderr одну строку с числом унесённого — этого
достаточно, чтобы понимать, что отчёт об утечках не вся правда.

Чтобы узнать, **где** был запланирован каждый забытый таймер, прогоните этот файл ещё раз с
выключенным `strayTimers` и прочитайте собственный отчёт Vitest. Фрейм кода показывает на
`setTimeout` в спеке: обёртки планировщиков в библиотеке идут через `vi.defineHelper`, так что
фреймы внутри `vitest-auto-spy` из стека выбрасываются, а не показываются вместо спековских.

```
⎯⎯⎯⎯⎯⎯⎯ Async Leaks 1 ⎯⎯⎯⎯⎯⎯⎯⎯

Timeout leaking in src/app/cart.component.spec.ts
  12|   it('polls', () => {
  13|     component.startPolling();
  14|     setTimeout(() => refresh(), 60_000);
     |     ^
```

Предупреждение уходит в stderr, а не в `console.warn`, намеренно: подметание идёт после последнего
теста файла, а Vitest приписывает перехваченный вывод консоли той задаче, которая его породила, —
задачи уже нет, и строка теряется.

## 5. Как удержать прогон подальше от сети {#_5-keeping-the-run-off-the-network}

По желанию, и существует оно ради прогона, который зелёный и всё равно падает.

В jsdom нет `fetch`, так что под ней компонент, тянущийся за удалённым ассетом, безвреден и сюита
ничего не замечает. happy-dom его реализует, и тот же компонент начинает слать настоящие запросы —
загрузчик иконок тянет все SVG с CDN, конфиг-сервис опрашивает эндпоинт. Тесты по-прежнему проходят,
потому что ничего из того, что они проверяют, от ответа не зависит. А прогон — нет:

```text
 Test Files  260 passed (260)
      Tests  2257 passed (2257)

Vitest caught 8 unhandled errors during the test run.
DOMException [AbortError]: The operation was aborted.
```

Раннер обрывает всё, что в полёте, когда сносит среду, и эти обрывы прилетают необработанными
реджектами уже после итога. Код возврата 1, и ни одного названного теста — потому что ни один тест не
упал.

```ts
setupAutoSpy({ blockNetwork: true });
```

`fetch` тогда сразу реджектится, называя, что именно запрашивали, — а это как раз то, чего стектрейс
вам не скажет:

```text
[vitest-auto-spy] fetch is stubbed in unit tests — the code under test requested https://cdn.example.test/sprite.svg
```

Ничего не покидает машину, прогон перестаёт зависеть от доступности хоста, а проверяемый код идёт
ровно по той ветке, по которой пошёл бы при неудачном запросе. Спека, которой `fetch` действительно
нужен, подменяет его как и раньше — это пол, а не потолок. Заглушка ставится на каждый тест
(`restoreProps` её снимает), а `blockNetwork()` экспортируется для сюит, которым нужен более узкий
охват.

`fetch` — это только половина сети, а вторую половину jsdom реализует полностью. Множество библиотек
так и не ушли от `XMLHttpRequest` — `rmp-vast` пингует каждый VAST-трекер через самодельный, — так
что сюита с уже включённым `blockNetwork: true` всё равно ходила в интернет, по пингу на квартиль на
рекламу на тест, и печатала jsdom'овский `AggregateError at Object.dispatchError` на каждое
неудавшееся соединение. Печатает ли это зелёный прогон, зависит от того, есть ли у машины маршрут
наружу, — а это не то свойство, которое должно быть у тестовой сюиты.

Каждый канал, который реализует среда, закрыт по умолчанию. Объект сужает это:

| опция    | по умолчанию | что делает                                                                 |
| -------- | ------------ | -------------------------------------------------------------------------- |
| `fetch`  | `true`       | `fetch` реджектится, называя, что запрашивали                              |
| `xhr`    | `'reject'`   | как отвечать на перехваченный `XMLHttpRequest` — или `false`, чтобы не трогать |
| `beacon` | `true`       | `navigator.sendBeacon` отвечает `false`, там где он в среде есть           |

`'reject'` роняет запрос так же, как это делает недоступный хост: `readyState` 4, `status` 0,
событие `error` и маркер в `statusText` — единственном строковом канале, который есть у неудавшегося
запроса. `'empty'` вместо этого отвечает статусом 200 и пустым телом — именно этого хочет запрос,
ответ на который никто не читает:

```ts
setupAutoSpy({ blockNetwork: { xhr: 'empty' } }); // пинги трекера, отвеченные и беззвучные
```

`data:`-URL пропускается, и он единственный: это схема, из которой спека раздаёт собственные
фикстуры, и единственная, на которую DOM отвечает без сокета. **Относительный** URL исключением не
является — DOM разрешает его относительно origin документа, так что спека, которая ходит в `/config`
и проходит, держится на том, что на этом порту никто не слушает.

`WebSocket` и `EventSource` сознательно не трогаются. Их отказ — это событие на объекте, который код
хранит и переподключает, так что нет такого ответа сплошной заглушки, который сам не был бы
изменением поведения; для спеки, у которой такой объект есть, инструмент —
[`stubConstructor`](/ru/utilities/constructor-doubles).

## 6. Как вернуть глобалы таймеров, которые фейки унесли с собой {#_6-putting-back-timer-globals-the-fakes-took-with-them}

Включено по умолчанию, потому что оно может только чинить.

`vi.useRealTimers()` читается как обратная операция к `vi.useFakeTimers()`, и в обычном
Node-реалме так и есть. Под DOM-средой — нет: `@sinonjs/fake-timers` восстанавливает глобал, присваивая
оригинал обратно, **когда тот был собственным свойством глобального объекта**, а иначе удаляет его. В
happy-dom `Date` наследуется из реалма среды, так что деинсталляция убирает его совсем.

При `isolate: true` этого никто не заметит. При `isolate: false` следующий файл того же воркера
встречает реалм без `Date` и умирает внутри собственного `useFakeTimers` Vitest, за несколько файлов
от того, кто фейки поставил:

```text
TypeError: Cannot read properties of undefined (reading 'now')
 ❯ hijackMethod node_modules/@sinonjs/fake-timers/src/fake-timers-src.js
 ❯ Object.useFakeTimers node_modules/vitest/dist/chunks/vi.js
 ❯ src/app/billing/invoice.component.spec.ts:24:6
```

Файл в этом стеке — просто тот, который выполнялся следующим.

Настоящие глобалы захватываются при первом импорте библиотеки — до того, как любая спека успеет
поставить фейки, — и всё, что после теста осталось `undefined`, возвращается на место. Только это:
значение, которое спека подменила намеренно, на месте и остаётся нетронутым, так что починка не может
затереть сознательную заглушку.

```ts
import { getWatchedTimerGlobals, restoreTimerGlobals } from 'vitest-auto-spy/setup';

restoreTimerGlobals(); // безопасно в любой момент и сколько угодно раз
getWatchedTimerGlobals(); // имена, захваченные в этой среде
```

`setupFakeTimers()` делает ту же починку в своём собственном `afterEach`, так что сюита, которая им
пользуется, прикрыта независимо от того, установлен ли `setupAutoSpy()`.

## 7. Как назвать файл, запечатавший глобал {#_7-naming-the-file-that-sealed-a-global}

По желанию, и отвечает на вопрос, на который иначе отвечают грепом по репозиторию.

`Object.defineProperty(document, 'cookie', { value, writable: true })` — это способ времён Jest
заглушить браузерный глобал, а `configurable` по умолчанию `false`. При пофайловой изоляции это
безвредно: среда всё равно выбрасывается. При `isolate: false` свойство больше нельзя ни
переопределить, _ни_ удалить, так что каждый следующий файл в этом воркере его наследует, и падает
какая-нибудь библиотека, через прогон, и ничто не показывает на файл, который это сделал.

```ts
setupAutoSpy({ guardGlobals: 'throw' }); // или 'warn', пока большую сюиту разгребают
```

```text
[vitest-auto-spy] /src/app/diagnostics/app-info.spec.ts redefined document.cookie as a
non-configurable own property, so nothing can put it back — not `restoreMockedProps()`, not
`vi.unstubAllGlobals()`, not the next file's own `Object.defineProperty`. … use
`mockValueProp(document, 'cookie', value)`, which records the descriptor it replaced …
```

`globalThis`, `document` и `navigator` сравниваются до и после каждого теста; в отчёт попадают только
свойства, которые появились _и_ не могут быть убраны. `guardGlobalPatches(reaction)` экспортируется
для сюиты, которой нужен более узкий охват.

## 8. Как падать на реджекте, который проглотил zone.js {#_8-failing-on-a-rejection-zone-js-swallowed}

По желанию, и это единственный переключатель на этой странице, который меняет, говорит ли зелёный
прогон правду.

zone.js подменяет глобальный `Promise`. Отклонённый `ZoneAwarePromise`, который никто не обработал,
вычерпывается в `api.microtaskDrainDone()` и сообщается через `api.onUnhandledError` — а это
`console.error` и больше ничего. Он никогда не доходит до `process.on('unhandledRejection')`, канала,
который слушает Vitest, так что раннеру ничего не сообщают: файл, отклонивший сотню промисов, всё
равно выходит с 0.

Прячет это обычный код:

```ts
it('renders once compiled', () => {
  TestBed.compileComponents().then(() => expect(component.ready).toBe(true)); // никогда не выполнится
});
```

Тест кончается раньше, чем выполнится колбэк, так что ассерт срабатывает уже после того, как
принадлежащий ему тест отчитался зелёным, — а когда он падает, это падение _и есть_ реджект, который
никто не обработал. То же касается `async`-хелпера, вызванного без `await`, и `TypeError`, брошенного
внутри `import('…').then(…)` в продакшн-коде. В одном переехавшем Angular-монорепозитории — 1688
файлов спек, 11 587 тестов, зелено, код возврата 0 — ровно за этим сидели шесть настоящих дефектов,
два из них — просто ложные ассерты.

```ts
setupAutoSpy({ strayRejections: true });
```

Реджект тогда роняет тот тест, в котором раннер находился, когда zone.js на него махнул рукой:

```text
[vitest-auto-spy] 1 promise rejection(s) went unhandled and zone.js swallowed each one into console.error:
  - AssertionError: expected false to be true — attributed to TaskListComponent > renders once compiled
An assertion that settles after its test has finished cannot fail it: the test it belongs to was
reported green without ever running it. … return or await the promise so the assertion lands inside
the test.
```

«Приписан», а не «брошен», потому что реджект, созданный тестом одного файла, регулярно всплывает во
время другого; а завершающий совет меняется в зависимости от вида — упавший матчер и брошенная
ошибка — разные баги.

Два сознательных ограничения. zone.js должен быть уже загружен: этот пакет его никогда не
импортирует — zoneless-проект не должен его тянуть, — так что `import 'zone.js';` в начале
setup-файла или собственная точка входа билдера `@angular/build:unit-test` — вот что его туда кладёт,
и без него вызов **бросает**, а не молча наблюдает за пустотой. И слушатель
`process.on('unhandledRejection')` не ставится: собственный обработчик Vitest выключается, как только
появляется второй слушатель, так что добавить его — значит _заглушить_ нативные реджекты, о которых
раннер и так рапортует и из-за которых роняет прогоны. Нативные реджекты — не пробел; пробел —
проглоченные зоной.

Части экспортируются для сюиты, которой нужен более узкий охват или нужны сами захваты:

```ts
import { countStrayRejections, flushStrayRejections, trackStrayRejections } from 'vitest-auto-spy/setup';

const stop = trackStrayRejections(); // идемпотентно; возвращает отмену, восстанавливающую прежний обработчик

afterEach(() => {
  const stray = flushStrayRejections(); // { reason, assertion, testName }[], и начинает копить заново

  expect(stray).toEqual([]);
});
```

Каждая принимает тот же необязательный host, что и трекеры забытых таймеров, по умолчанию — настоящие
глобалы. `countStrayRejections()` бросает, когда за хостом никто не следит: просить счёт, который
всегда `0`, потому что никто не наблюдает, — тот режим отказа, о котором стоит кричать, — а
`flushStrayRejections()` вместо этого возвращает пустой массив, так что забытая после выключения опции
уборка не роняет сюиту.

Реджект, который раннер **уже** вменил завершившемуся тесту, второй раз не рапортуется. `async`-тест,
проваливший ассерт, оставляет свой `AssertionError` в обоих местах: раннер называет падение, и та же
ошибка приходит сюда как никем не обработанный реджект. Красный прогон из-за этого печатал два
сообщения на каждое падение, а первое, что делает читатель со вторым, — идёт искать дефект, которого
нет. Что переживает фильтр — то, ради чего проверка и существует: реджекты, не роняющие вообще ни
одного теста.

Правило [`no-floating-assertion`](/ru/utilities/eslint-plugin) ловит самую частую форму статически,
ещё до того, как она вообще выполнится.

## 9. Подрезка реестра моков, который никто не опустошает {#_9-pruning-the-mock-registry-nothing-empties}

По желанию, и это единственный переключатель на этой странице, который про то, во что прогон
обходится, а не про то, что он рапортует.

`vi.fn()` и `vi.spyOn()` добавляют созданный мок в единственный `Set` уровня модуля внутри
`@vitest/spy`, потому что именно его обходит `vi.clearAllMocks()`, — и ни один API оттуда ничего
никогда не убирает. При `isolate: true` модуль переоценивается на каждый файл, и множество каждый раз
начинается пустым. При `isolate: false` он оценивается один раз на воркер и только растёт, и большая
сюита чувствует обе половины этого:

- `clearMocks: true` обходит каждый мок каждого уже прогнанного файла **перед каждым отдельным
  тестом**, так что цена очистки растёт вместе с числом уже пройденных тестов;
- куча воркера держит сразу все моки прогона — с записанными аргументами, а через них и с целыми
  деревьями компонентов.

```ts
setupAutoSpy({ pruneMockRegistry: true }); // оставить только моки, переживающие файл
```

Для этого множества нет API, поэтому оно берётся у единственного, кто его обходит: `Set.forEach`
передаёт множество в колбэк третьим аргументом, так что `vi.clearAllMocks()` под ненадолго
пропатченным `Set.prototype.forEach` отдаёт реестр наружу. Захват проверяется по пробному моку, и без
совпадения ничего не подрезается — медленный прогон лучше сломанного.

Половина, которую стоит понять до включения, — что **не должно** уйти. Выбросить мок из реестра значит,
что `vi.clearAllMocks()` и `clearMocks: true` его больше не видят, а значит, его вызовы копятся молча:
безвредно для мока, умирающего вместе с создавшим его файлом, и баг для `vi.fn()` уровня модуля в
общем `*.mock.ts`, который импортируют шесть файлов спек. Первый импортировавший его файл его создаёт,
наивная подрезка выбрасывает его в конце этого файла, а файл, который окажется **вторым**, падает на
вызовах, сделанных его предшественником, — и читается это как флакающие тесты, потому что кто пойдёт
первым, решает раннер.

Поэтому граница проведена там, где она наблюдаема: всё, что уже лежит в реестре к моменту старта
хуков файла, было создано во время вычисления графа модулей, а это ровно и значит «живёт в модуле», —
и оно остаётся; всё добавленное после принадлежит тесту или хуку этого файла и уходит вместе с файлом.
Один случай попадает не на ту сторону линии — модуль, впервые загруженный динамическим `import()`
внутри теста, — и об этом говорится прямо:

```ts
// fixtures/navigation.mock.ts — импортируется шестью файлами спек
export const navigation = { setFocus: keepMockRegistered(vi.fn()) };
```

### Моки, которые он оставляет, он же и охраняет {#the-mocks-it-keeps-it-also-guards}

У того, что мок остаётся зарегистрированным, есть второе следствие, и как раз на его поиски уходит
день. `clearAllMocks` — не единственный, кто обходит это множество: `vi.resetAllMocks()` обходит то же
самое и вызывает `mockReset()` на всём подряд, а `mockReset` возвращает реализацию на место, только
если её передали в `vi.fn(implementation)`. `vi.fn()`, получивший поведение через цепочку
`.mockReturnValue(…)` или `.mockReturnThis()`, просто остаётся отвечать `undefined` — в `@vitest/spy`
это записано как `resetToMockImplementation ? mockImplementation : undefined`.

При `isolate: false` счёт приходит совсем в другом месте. Одна спека вызывает `vi.resetAllMocks()` в
своём `afterEach`; **другой** файл позже в том же воркере умирает внутри прикладного кода, потому что
общий дубль, которого он вообще не трогал, теперь отвечает `undefined`:

```
TypeError: Cannot read properties of undefined (reading 'info')
  app.component.ts:316   AppComponent.syncAllProcesses
```

Ничто в этом падении не называет спеку, которая его вызвала. Оно переезжает всякий раз, когда раннер
переупорядочивает файлы, оно никогда не воспроизводится на файле, который делал сброс, а
`vi.restoreAllMocks()` — вызов, которым естественно пробуют, — не вызывает его вовсе: в Vitest 4 он
обходит `MOCK_RESTORE`, куда пишет только `vi.spyOn`, так что проба, построенная вокруг него,
возвращается зелёной и уводит поиск не туда.

Поэтому реализация, которую долгоживущий мок несёт в момент первой классификации, запоминается и
возвращается перед тестом, который её потерял. Только когда она потеряна: мок, который тест намеренно
переопределил, остаётся таким, каким тест его оставил, а мок, у которого реализации не было никогда,
не трогается вообще. Хук — `beforeEach`, потому что Vitest применяет `restoreMocks` / `mockReset` /
`clearMocks` из `onBeforeTryTask`, который выполняется _до_ хуков `beforeEach`, а не после них.

Части экспортируются для сюиты, которой нужны они без остального: `trackMockRegistry()` ставит те же
хуки сам по себе, `keepRegisteredMocks()` помечает всё зарегистрированное на текущий момент как
долгоживущее, `pruneMockRegistry()` — разовое подметание, возвращающее, сколько ушло,
`restoreLongLivedImplementations()` — та самая починка, возвращающая, сколько вернула на место, а
`getMockRegistrySize()` рапортует, сколько осталось, — `undefined`, когда захват не состоялся.

## 10. Строгие дубли на всю сюиту {#_10-strict-doubles-for-the-whole-suite}

По желанию, и это единственный переключатель здесь, который меняет поведение **дубля**, а не среды.

```ts
setupAutoSpy({ strict: true }); // метод, который никто не настроил, бросает и называет себя
```

Выключено — метод, который никто не настроил, возвращает `undefined`, легальное значение, так что
падение всплывает там, где оно в конце концов используется, за несколько фреймов от пропуска и обычно
внутри продакшн-кода. Включено — он бросает на том вызове, который его породил, называя класс, метод и
аргументы. Форма для отдельного дубля — `createSpyFromClass(X, { strict: true })`; здесь тот же
переключатель на всю сюиту, так что переход на него — одна строка, а не правка на каждый вызов фабрики.

`onUnstubbedCall` — общая форма: что бы она ни вернула, это становится результатом вызова, так что
сюита может сначала записать пробелы, а потом уже включить бросание:

```ts
setupAutoSpy({ onUnstubbedCall: ({ className, method }) => console.warn(`unstubbed ${className}.${method}`) });
```

Собственная конфигурация дубля побеждает, **включая явный `strict: false`**, — и это единственный
способ вывести одного широкого коллаборатора из-под умолчания.

Две вещи про время жизни, обе важны при `isolate: false`. Умолчание взводится, только когда реально
передана одна из двух опций, так что голый `setupAutoSpy()` не может затереть умолчание, поставленное
чем-то другим. И оно снимается в `afterAll` того файла, который его взвёл: модуль, который его хранит,
общий для всех файлов воркера, так что оставленное взведённым умолчание уронило бы спеку, которая ни на
что не подписывалась, сообщением про класс, к которому эта спека не имеет отношения. Это тот же шов,
которым пользуется `strayTimers`, и по той же причине.

Докуда дотягивается охрана, что считается настроенным и вся цепочка приоритетов — на странице
[Строгий режим](/ru/core/strict-mode).

## 11. Бюджет хуков, которого у Jest был всего один {#_11-the-hook-budget-jest-had-only-one-of}

Включено по умолчанию, потому что оно только дописывает предложение к уже упавшему тесту.

```ts
setupAutoSpy({ hookTimeoutHint: false }); // выключить
```

Jest разрешает **один** бюджет и тратит его одинаково на хук и на тело теста:

```js
const timeout = hook.timeout || getState().testTimeout; // jest-circus
const timeout = test.timeout || getState().testTimeout;
```

Vitest разрешает два, и у `hookTimeout` собственное умолчание — 10 000 мс. Так что сюита, перенёсшая
из Jest-пресета `testTimeout: 30000` в конфиг раннера и на этом остановившаяся, даёт каждому хуку
треть того бюджета, что получают её тесты, и никто об этом не говорит.

Дорого это из-за того, куда прилетает падение. Vitest приписывает таймаут `beforeEach` **тесту**, и
длительность теста при этом равна лимиту:

```text
× should create 10045ms
```

Читается как медленный тест. Тело, которое он называет, не выполнялось вовсе, так что эти десять секунд
внутри него не найти, и читатель проводит вечер не в том файле. Подсказка вешает недостающее
предложение на саму ошибку, называя оба бюджета и поле, которое надо задать.

Она молчит, когда бюджеты совпадают, — тогда хук действительно медленный и конфиг ни при чём, — и
молчит для хука, назвавшего собственный лимит (`beforeEach(fn, 300)`). До `beforeAll` не дотянуться по
построению: его таймаут рапортуется как упавшая _сюита_, все тесты помечаются пропущенными, и ни один
`afterEach` не выполняется, чтобы подсказка на нём проехала.

Перенося конфиг раннера с Jest, поставьте оба рядом и считайте единственное число Jest относящимся к
обоим:

```ts
test: {
  testTimeout: 30_000,
  // У Jest на оба был один бюджет; Vitest сам по себе ставит здесь 10_000.
  hookTimeout: 30_000,
}
```

Одно соседнее поле расходится тихо и меняет только отчёт: `slowTestThreshold` — это `5` в Jest
(**секунды**) и `300` в Vitest (**миллисекунды**), так что переехавшая сюита начинает помечать
медленными бо́льшую часть своих файлов. Смена единиц, а не регрессия.

## 12. Таймаут, который объясняют часы, а не код {#_12-a-timeout-the-clock-explains-not-the-code}

Включено по умолчанию и молчит, пока часы не заморожены с колбэками в очереди.

```ts
setupAutoSpy({ frozenClockHint: false }); // выключить
```

Фейковые таймеры превращают ожидание в ожидание навсегда. `await new Promise((r) => setTimeout(r, 10))`
не разрешится никогда, пока что-нибудь их не прокрутит, а всё, что раннер может об этом сказать, — то
же, что он говорит про по-настоящему медленный тест:

```text
Error: Test timed out in 5000ms.
If this is a long-running test, pass a timeout value as the last argument …
```

То есть читателю велят поднять бюджет — единственную починку, которая не может сработать, потому что
колбэк не опаздывает, он не выполнится никогда. Под [`globalFakeTimers`](#fake-timers-for-the-whole-run)
всё хуже: в спеке ничто не говорит, что часы фейковые, потому что настройка приехала из Jest-пресета с
`fakeTimers.enableGlobally`, — и таймаут прилетает в файл, где о таймерах вообще ни слова.

Подсказка сообщает `vi.isFakeTimers()` и `vi.getTimerCount()` — часы заморожены, в очереди N колбэков,
и никто их не прокрутил. Это факт, а не догадка, поэтому проверка молчит, когда очередь фейковых часов
пуста: пустая очередь не объясняет никакого таймаута.

**Форма, которая доходит сюда вообще без таймеров на виду, — это HTTP-спека.** `setImmediate` входит в
число глобалов, которые `vi.useFakeTimers()` подменяет по умолчанию, а Express завершает запрос, не
совпавший ни с одним маршрутом, через `finalhandler`, который планирует на `setImmediate`. Поэтому 404
не пишется никогда, и ошибка в маршрутизации рапортуется как тест, занявший тридцать секунд. В таком
файле «тест завис» означает _маршрут не совпал_.

Одного эта подсказка не видит: спеки, чей собственный `afterEach` вызывает `vi.useRealTimers()`. Хуки
идут в обратном порядке регистрации, так что собственный хук спеки выполняется раньше того, который
ставит `setupAutoSpy`, и к моменту чтения часы уже настоящие. Тогда не сообщается ничего — а не
что-нибудь неверное.

## 13. Версия билдера, которая ест память, названная прямо в прогоне {#_13-the-builder-version-that-eats-memory-named-in-the-run}

Включено по умолчанию и молчит, если процесс не является воркером `@angular/build:unit-test` **и**
установленный `@angular/build` не попадает в `[22.1.5, 22.1.7)`.

```ts
setupAutoSpy({ angularBuildHint: false }); // выключить
```

В этом окне билдер собирает бандл юнит-тестов с выключенным code splitting в esbuild, так что каждая
спека — самодостаточный бандл, а `--coverage` растёт на сотни мегабайт без выхода на плато — 791 чанк
/ 596 МБ на сюите из 784 спек, пока прогон не прибьёт OOM killer. Билдер не печатает ни одного
предупреждения, а два места, которые уже об этом говорят — [проверка `doctor`](/ru/utilities/cli#doctor-—-defects-that-never-fail)
`angular-build-splitting-off` и [страница про Angular](/ru/adapters/angular#when-the-unit-test-build-has-code-splitting-off), —
надо ещё найти самому. Эта одна строка печатается изнутри прогона, там, где больно, в stderr, один раз
на воркер: билдер запускает Vitest с `isolate: false` и вычисляет setup-файл однажды, а уведомление
держит флаг на `globalThis`, чтобы второе вычисление промолчало.

Билдер распознаётся по маркеру, который его собственный setup-файл `vitest-mock-patch` оставляет на
`globalThis` (`Symbol.for('@angular/cli/vitest-mock-patch')`, выставляется до запуска любого
пользовательского setup-файла), так что обычный прогон Vitest ничего не читает вообще. Под билдером
версия берётся из ближайшего `node_modules/@angular/build/package.json` выше рабочей директории — **это
единственное место, где библиотека читает диск**: один файл, только на чтение, через
`process.getBuiltinModule`, а не статическим импортом `node:fs`, чтобы точка входа `/setup` грузилась и
там, где нет `process`, и ничего, кроме этой строки, от находки не зависит. На Node без
`getBuiltinModule` (до 20.16 / 22.3) она молчит, а не гадает.

## 14. Web Storage, которое раннер так и не передал {#_14-web-storage-the-runner-never-handed-over}

Включено по умолчанию, и — как и с глобалами таймеров — оно может только чинить.

Vitest копирует глобалы DOM-среды в `globalThis` через один фильтр:

```js
if (k in global) return KEYS.includes(k);
```

`Storage` в этом списке `KEYS` есть. `localStorage` и `sessionStorage` — нет. Пока Node не клал в
`globalThis` ни того ни другого, первая половина была ложной и оба копировались. Собственный Web
Storage в Node сделал ключ существующим, так что теперь фильтр спрашивает `KEYS`, `KEYS` отвечает
«нет», и хранилище среды не приезжает вовсе. Фильтр работает раньше любого кода, специфичного для
среды, так что jsdom и happy-dom ломаются одинаково:

| Node   | `localStorage` под Vitest         |
| ------ | --------------------------------- |
| 24.19  | работает                          |
| 25.9   | `setItem is not a function`       |
| 26.7   | `undefined`                       |

Сюита остаётся зелёной при этой поломке, потому что падают только спеки, которые трогают хранилище, —
поэтому обычно она приходит как «CI переехал на новый Node, и умерли одиннадцать никак не связанных
спек».

Починка решает, пользуясь хранилищем, а не глядя на него: она пишет ключ со своим префиксом, читает его
обратно и удаляет. Node 25 предлагает `setItem`, который бросает, Node 26 не предлагает ничего, а
следующий рантайм волен придумать третью форму; хранилище, пережившее круговой рейс, работает, кто бы
его ни реализовал. То, которое не пережило, заменяется — собственным хранилищем окна, где это отдельный
объект, и заменителем на `Map` в остальных случаях.

```ts
import { restoreWebStorage } from 'vitest-auto-spy/setup';

restoreWebStorage(); // безопасно в любой момент и сколько угодно раз
restoreWebStorage({ view: null }); // «окна нет» — не ставит ничего
```

Двух вещей она сознательно не делает. Она ничего не ставит в среде `node`, у которой Web Storage быть и
не должно: выдать проверяемому коду API, которого нет у настоящего рантайма, — изменение большее, чем то,
ради которого она существует. И она оставляет работающее хранилище ровно как есть, так что собственная
заглушка спеки её переживает.

## Два буфера, которые вычерпывает уборка {#the-two-buffers-teardown-drains}

Две из проверок выше держат найденное в буфере, пока его оттуда не заберут, и оба буфера
неограниченные.

- **Захваты реджектов.** `trackStrayRejections()` добавляет по записи на каждый проглоченный реджект, и
  каждая запись держит саму причину — `Error`, его стек, а через него и всю цепочку асинхронных
  замыканий, которая его породила.
- **Журнал свойств.** `mockReadonlyProp` и его родня дописывают в
  `globalThis.__vitestAutoSpyPatchedProps__` по записи на патч, каждая из которых держит
  пропатченный объект и перезаписанный дескриптор.

На поддерживаемом пути не растёт ни один: `afterEach` из `setupAutoSpy()` вычерпывает оба после каждого
теста — `flushStrayRejections()` отдаёт массив и оставляет его пустым, `restoreMockedProps()` опустошает
журнал прежде, чем что-то возвращать на место. Копится на всю жизнь воркера только самодельная
половина: `trackStrayRejections()`, который читают только через `countStrayRejections()`, или патчи,
которые читают только через `countMockedProps()`. **Счётчик ничего не опустошает.** Читайте через flush
или отдайте уборку `setupAutoSpy()`, а счётчики используйте ради того ассерта, для которого они и есть.

## Как переставлять заглушку на каждый тест {#reinstalling-a-stub-for-every-test}

```ts
import { installPerTest } from 'vitest-auto-spy/setup';

const observers = installPerTest(() => stubIntersectionObserver({ autoEmit: true }));

it('loads the section once it scrolls into view', () => {
  fixture.detectChanges();

  expect(observers().last.targets).toEqual([host]);
});
```

Любая заглушка, которую ставит эта библиотека, снимается `restoreMockedProps()` после каждого теста —
именно это не пускает её в следующий файл. Следствие легко упустить: заглушка, поставленная один раз на
уровне `describe` или в `beforeAll`, со второго теста исчезает, а падает ассерт про компонент
(«ожидалось 2 вызова, получено 0») — при том что заглушка стоит десятью строками выше и на вид в силе.

Тот же порядок кусает и с другой стороны. Общепроектный setup-файл ставит наблюдателей по умолчанию в
корневом `beforeEach`, а корневые хуки идут **раньше** собственных хуков файла — так что `beforeAll` в
спеке молча им проигрывает, а `beforeEach` в той же спеке выигрывает.

`installPerTest` возвращает **читатель**, а не ручку, потому что ручка в каждом тесте — другой объект:
заглушка, поставленная для предыдущего теста, — это ровно то, до чего не должно быть доступа.

## Опции {#options}

| Опция                 | По умолчанию | Примечания                                                                       |
| --------------------- | ------------ | --------------------------------------------------------------------------------- |
| `duplicateCopies`     | `'throw'`    | `'warn'` — сообщать без падения, `'off'` — пропустить проверку                    |
| `restoreProps`        | `true`       | `restoreMockedProps()` в глобальном `afterEach`                                   |
| `restoreMocks`        | `false`      | `vi.restoreAllMocks()` в глобальном `afterEach` — включать при `isolate: false`   |
| `strayTimers`         | `false`      | Отслеживать и отменять таймауты, интервалы и кадры, пережившие свой файл          |
| `onStrayTimers`       | —            | Принимает число отменённого за файл вместо предупреждения в stderr                |
| `strayRejections`     | `false`      | Ронять тест, в котором всплыл проглоченный zone.js реджект, — нужен zone.js       |
| `blockNetwork`        | `false`      | Закрыть все сетевые каналы, какие есть у среды, — `true` или сужающий объект      |
| `guardGlobals`        | `'off'`      | Сообщать о тесте, переопределившем глобальное свойство как non-configurable       |
| `globalFakeTimers`    | `false`      | Фейковые таймеры на каждый тест **и между тестами** — см. ниже                    |
| `restoreTimerGlobals` | `true`       | Возвращать глобалы таймеров, удалённые деинсталляцией фейков                      |
| `restoreWebStorage`   | `true`       | Дать прогону работающие `localStorage` / `sessionStorage` — см. раздел 14         |
| `pruneMockRegistry`   | `false`      | Держать вечно растущий реестр моков @vitest/spy в рамках моков, переживающих файл |
| `hookTimeoutHint`     | `true`       | Объяснять хук, исчерпавший `hookTimeout`, когда `testTimeout` больше              |
| `frozenClockHint`     | `true`       | Объяснять таймаут, случившийся потому, что фейковые часы никто не прокрутил       |
| `angularBuildHint`    | `true`       | Сказать раз на воркер, что `@angular/build` собирает тестовый бандл без сплита    |
| `strict`              | `false`      | Каждый построенный после этого дубль бросает на ненастроенном методе              |
| `onUnstubbedCall`     | —            | Общая форма `strict` — её возвращаемое значение становится результатом вызова     |

`restoreMocks` выключен по умолчанию, потому что он заодно сносит заглушки `vi.spyOn`, поставленные
сюитой в `beforeAll`; это ручка, за которую берутся, когда прогон делит одну среду между файлами.

```ts
setupAutoSpy({ restoreMocks: true, duplicateCopies: 'warn' });
```

## Фейковые таймеры на весь прогон {#fake-timers-for-the-whole-run}

```ts
setupAutoSpy({ globalFakeTimers: true }); // или объект конфигурации `vi.useFakeTimers()`
```

У Jest было `fakeTimers: { enableGlobally: true }`; у Vitest такой настройки нет. Сюита, приехавшая из
проекта, который ею пользовался, писалась против замороженных часов везде, а включать это обратно
файл за файлом — тысяча правок.

Оба конца защищены, и как раз эту половину пара самописных хуков делает неправильно. Спека, которая
сама крутит часы, иначе доехала бы до второго `vi.useRealTimers()`, а под happy-dom он оставляет среду
без `clearInterval` — что взрывается во время уборки того файла, который пойдёт следующим, и обвиняет
его.

Он также держит часы фейковыми **между** тестами — та половина `enableGlobally`, которую пара только
из `beforeEach` упускает: `beforeAll` внутри вложенного `describe` выполняется _после_ `afterEach`
предыдущего теста, так что блок, готовящий там свои образцы, иначе встретил бы настоящие таймеры и упал
бы с `the timers APIs are not mocked` — в наборе, чьи собственные тесты таймеров вообще не трогают.
Фейки снимаются насовсем в `afterAll`, так что они никогда не переживают файл. Для одного `describe`, а
не для всего прогона, это [`setupFakeTimers(config, { betweenTests: true })`](./fake-timers).

Передавайте объект конфигурации, а не `true`, когда прогон гоняет настоящий HTTP-обработчик: `toFake`
по умолчанию включает `setImmediate`, а это и есть способ, которым `404` в Express превращается в
30-секундный таймаут, не называющий ничего, — см.
[как убрать `setImmediate` из `toFake`](./fake-timers#taking-setimmediate-out-of-tofake).

## Общие фикстуры — это функции, а не константы {#shared-fixtures-are-functions-not-constants}

При `isolate: false` модуль вычисляется **один раз на воркер**. Экспортированный объект, держащий
`vi.fn()`-ы, — это, стало быть, один набор спаев, общий для всех импортирующих файлов, зарегистрированный
на тот файл, который добрался первым, и `clearMocks` остальных файлов до них не достаёт. Симптом —
30-секундный таймаут на каждом прогоне в разных файлах.

```ts
// ❌ константа: один набор спаев на весь воркер
export const mockActionContext = { actions: { navigateToSection: vi.fn() } };

// ✅ фабрика: по набору на каждого вызывающего
export const createActionContext = () => ({ actions: { navigateToSection: vi.fn() } });
```

То же касается общей фикстуры провайдера — `{ provide: X, useValue: { load: vi.fn() } }` остаётся
константой, пока его не возвращают из функции. А файл спеки не должен **экспортировать ничего**: при
`isolate: false` экспортирующий файл спеки импортируется соседями и теряет собственную сюиту. Общие
дубли кладите в `*.mock.ts` рядом с ними.

Правило [`no-shared-module-level-mock`](/ru/utilities/eslint-plugin) находит такое механически, а это
быстрее, чем таймаут, которым они находятся иначе.

## Порядок хуков отличается от Jest {#hook-order-differs-from-jest}

Vitest выполняет хуки `afterEach` как стек — самый внутренний и зарегистрированный последним идёт
первым, — тогда как Jest выполнял их в порядке объявления. В переехавшей сюите, где `afterEach` спеки
зависит от того, что поставил setup-файл, уборка setup-файла теперь идёт первой, и хук спеки работает
над уже восстановленной средой. `sequence: { hooks: 'list' }` в конфиге Vitest возвращает порядок Jest.

## Хуки принадлежат тому файлу, в котором выполнился этот вызов {#the-hooks-belong-to-the-file-this-call-ran-in}

Всё, что ставит `setupAutoSpy()`, — это `beforeEach` / `afterEach` / `afterAll`, а хук,
зарегистрированный во время импорта setup-файла, принадлежит тому файлу спеки, при сборе которого этот
импорт случился. Vitest переимпортирует setup-файлы для каждого файла спеки, так что обычно ничего из
этого не видно.

Видно становится, когда что-то держит setup-модуль в кэше модулей между файлами: вызов происходит один
раз, и у каждого файла после первого в этом воркере нет ни одного из хуков — ни восстановления свойств,
ни `blockNetwork`, ни отмены забытых таймеров, ни `restoreTimerGlobals`, ни глобальных фейковых
таймеров. Никто об этом не сообщает, а симптом всплывает совсем в другом месте — утёкший глобал или
`A function to advance timers was called but the timers APIs are not mocked` в спеке, которая зелёная,
когда её запускают отдельно.

Случай, встреченный в дикой природе, — `@angular/build:unit-test` **с покрытием**. Билдер тогда отдаёт
каждый тестовый файл как обёртку, импортирующую собранный бандл, setup-модуль остаётся разрешённым в
общей среде, и его верхний уровень больше не выполняется; без покрытия тот же прогон в порядке, отчего
это и читается как «покрытие сломало тесты».

Два выхода: гонять покрытие с пофайловой изоляцией (`ng test <project> --coverage --isolate` или
`isolate: true` в конфиге только для этого случая) либо вызывать `setupAutoSpy()` из чего-то, что
вычисляется на каждый файл, а не из модуля, который раннер может закэшировать.
