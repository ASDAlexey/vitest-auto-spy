# CLI

Четыре команды, ни одной зависимости, ничего не нужно настраивать:

```bash
npx vitest-auto-spy doctor   # только чтение. Выходит с кодом 1, когда что-то нашёл
npx vitest-auto-spy perf     # куда уходит CPU-время сюиты. Всегда выходит с кодом 0
npx vitest-auto-spy init     # пишет указатель на инструкции для агентов
npx vitest-auto-spy codemod  # по умолчанию сухой прогон. Выходит с кодом 1, когда что-то оставил как было
```

Это один бинарник, потому что все четыре отвечают на один вопрос с четырёх сторон — _не делает ли
что-нибудь в этой тестовой сюите молча совсем не то, чем кажется?_ `doctor` задаёт его репозиторию,
`perf` — собственным часам сюиты, `init` — агенту, который вот-вот напишет следующую спеку, а
[`codemod`](/ru/utilities/codemod) — каждому фрагменту, который переезд с `jest-auto-spies` иначе
переименовал бы в противоположный смысл. Эта страница про первые три; у кодмода
[своя страница](/ru/utilities/codemod), потому что бо́льшая часть его работы — отказываться.

Флаг, которого у команды нет, останавливает её с кодом 2 до того, как она что-то прочитает или
запишет, называет флаг в stderr и подсказывает, какой флаг, скорее всего, имелся в виду, — или
перечисляет флаги команды, если ничего похожего нет. Так же обходится значение, которое команда
использовать не может: `--min-severity loud`, `--max-test-ms abc` или `-5`, `--cwd` без директории
после него и id в `--ignore`, для которого у `doctor` нет проверки, — всё это код 2 и `Nothing ran.`,
а не молчаливый откат к значению по умолчанию.

## `doctor` — дефекты, которые никогда не падают {#doctor-—-defects-that-never-fail}

У всех проверок здесь одно общее свойство: **результат никто не потребляет**. Сюита зелёная,
`tsc --noEmit` показывает ноль ошибок, и единственный читатель протухшей вещи — человек, который
случайно открыл этот файл. Именно поэтому такие дефекты живут годами, и по той же причине линтер
почти ни один из них не найдёт — улики размазаны по файлам.

```
$ npx vitest-auto-spy doctor
vitest-auto-spy doctor — /work/app
1 284 files, runner: vitest, entry: vitest-auto-spy/angular

error  tsconfig-glob-matches-nothing libs/users/tsconfig.spec.json
       The "include" pattern "src*.spec.ts" matches no file.
       → A pattern that matches nothing type-checks nothing, and `tsc --noEmit` still reports
         zero errors. Fix the glob or delete the entry.
       Docs: https://asdalexey.github.io/vitest-auto-spy/utilities/cli#tsconfig-glob-matches-nothing

3 errors, 4 warnings, 1 note
```

**Он никогда не пишет.** `doctor` читает репозиторий и печатает; никакого `--fix` нет. Код возврата
1, когда нашлось что-то выше заметки, иначе 0, — так что он вставляется в CI одной строкой.

**`--min-severity` для сюиты, которая ошибки уже разобрала.** Репозиторий, починивший всё, всё
равно читает заметки на каждом прогоне — совет про окружение, строку `jasmine-era-project`, строку
`no-agent-instructions`, — а отчёт, который никто не читает, никто не прочитает и тогда, когда он
понадобится. `--min-severity warning` (или `error`) оставляет находки потише за пределами печатаемого
отчёта; `info` — значение по умолчанию, печатает всё. Две вещи сознательно остались на месте:
строка-итог всё равно считает скрытое, поэтому `0 errors, 0 warnings, 14 notes` по-прежнему говорит
читателю, что заметки есть, а код возврата не меняется, потому что заметка никогда не роняла
прогон. Слово, которого флаг не знает, останавливает команду с кодом 2 и списком допустимых значений,
а не угадывается: догадка в любую сторону либо спрятала бы находки, либо показала бы те, которые
просили скрыть. На `perf` флаг работает так же.

```
$ npx vitest-auto-spy doctor --min-severity warning
vitest-auto-spy doctor — /work/app
1284 files scanned, 212 of them spec files — runner: vitest, entry: vitest-auto-spy/angular

warn   dead-runner-config karma.conf.js
       Configures karma, which is not installed in this repository.
       → Delete it. While it stays, every reader — human or agent — treats it as the
         source of truth for how tests run.
       Docs: https://asdalexey.github.io/vitest-auto-spy/utilities/cli#dead-runner-config

0 errors, 1 warning, 3 notes (3 not shown: --min-severity warning)
```

**`--ignore` для находки, на которую репозиторий уже ответил.** Некоторые находки верны в общем
случае и неверны для конкретного репозитория так, что `doctor` этого не видит:
`angular-build-splitting-off` в проекте, который патчем возвращает сборщику code splitting, или
`no-agent-instructions` в CI у репозитория, где файлы инструкций для агентов не лежат в git, — у
каждого разработчика они есть, а в чистом чекауте их нет никогда. `--ignore <check,…>` принимает
идентификаторы проверок через запятую и убирает эти проверки из отчёта, из итога, из кода выхода и из
файла `--code-quality`, так что виджет мерж-реквеста их тоже не показывает. В отличие от
`--min-severity`, находка скрывается полностью — называйте только те проверки, на которые ответили.
Id, которого нет среди проверок ниже, останавливает прогон с кодом 2 и тем id, который, скорее всего,
имелся в виду, — так опечатка не оставит на месте находку, которую должна была заглушить.

```bash
npx vitest-auto-spy doctor --ignore no-agent-instructions --code-quality reports/doctor.json
```

**Одна причина печатается один раз.** Находки одной проверки с одним и тем же исправлением — это один
блок: сообщение один раз, если во всех местах оно одинаковое (шесть tsconfig библиотек с одинаково
пустым `include`), иначе под каждым файлом его собственная строка, исправление тоже один раз, а за ним
строка `Docs:` со ссылкой на запись проверки [ниже](#the-checks).
Находка со своими доказательствами или без файла не сворачивается никогда. Текст переносится по ширине
терминала, а в пайпе и в логе CI — по 80 колонкам (`COLUMNS` это меняет); путь и URL не режутся
никогда, и каждая строка находки, кроме первой, идёт с отступом, поэтому обвязка, которая собирает
находку как строку `error` плюс строки с отступом под ней, по-прежнему собирает её целиком. Отчёт
заканчивается строкой-итогом всегда, и на чистом прогоне тоже.

**`--format json` для скрипта.** Один JSON-документ в stdout и больше ничего: `schema`, `command`,
`version`, `cwd`, `runner`, `entry`, `scanned` (`files`, `specFiles`, `truncated`), `exitCode`,
`tally` (`errors`, `warnings`, `notes`) и все находки с `check`, `severity`, `file`, `message`,
`fix` и `details`. `--min-severity` влияет только на текст; в документе всегда все находки. Поля
только добавляются — поле, которое меняет смысл или исчезает, поднимает `schema`. Код возврата тот
же, что у текстового прогона.

**`--code-quality <path>` для merge request.** Те же находки, записанные отчётом
[GitLab Code Quality](https://docs.gitlab.com/ci/testing/code_quality/): укажите файл в
`artifacts:reports:codequality`, и виджет merge request покажет, что появилось и что исправлено
относительно целевой ветки. Виджет есть на всех тарифах GitLab, включая self-managed, и не требует
ни токена, ни внешнего сервиса. Находка про файл записывается на этот файл, находка про весь
репозиторий — на `package.json`. Файл пишется и пустым: пустой отчёт — это то, из чего виджет
узнаёт, что проблемы прошлого прогона ушли; `--min-severity` на него тоже действует. На `perf` флаг
работает так же и несёт советы, гейт и flaky-тесты.

```yaml
doctor:
  script: npx vitest-auto-spy doctor --code-quality gl-code-quality.json
  artifacts:
    when: always
    reports:
      codequality: gl-code-quality.json
```

### Проверки {#the-checks}

Каждая находка заканчивается строкой `Docs:`, которая ведёт на её запись здесь.

#### `tsconfig-glob-matches-nothing` {#tsconfig-glob-matches-nothing}

Паттерн в `include`, который не совпадает ни с одним файлом: ошибка, если рядом с конфигом лежат
файлы, которые он должен был найти, и `info` для библиотеки, где их ещё нет. Глоб, который ни с чем не
совпал, ничего не проверяет типами, а `tsc` рапортует об успехе.

Это проверка, ради которой инструмент и появился: спека показывала `Cannot find name 'vi'` в редакторе,
пока `tsc --noEmit` рапортовал ноль ошибок. Кодмод миграции, правивший `include`, съел `/**`,
превратив `src/**/*.spec.ts` в `src*.spec.ts` — синтаксически валидный глоб, не совпадающий ни с
чем. Из 152 tsconfig'ов спек свои спеки покрывали только девять.

Два вида паттернов сознательно исключены, потому что для них «ни с чем не совпадает» ничего не
доказывает: глоб только по декларациям (`src/**/*.d.ts` — рутинная заглушка под ambient-типы,
которых ещё нет) и паттерн внутри директории, куда сканер вообще не заходит (`dist`,
`libs/app/out-tsc`, `coverage` или директория, исключённая правилами git, — существует она или ещё
нет: паттерн в `src/generated/` исключён и до запуска генератора кода). Запись `files` внутри такой
директории тоже не считается пропавшей.

#### `tsconfig-file-missing` {#tsconfig-file-missing}

Запись в `files`, называющая файл, которого больше нет. То же, что выше: после того как раннер
перестал пользоваться конфигом, его читают только редакторы, и о пропавшем файле никто не сообщает.

#### `spec-imported-by-non-spec` {#spec-imported-by-non-spec}

Продакшн-модуль, импортирующий `*.spec.ts`. В общей среде такой импорт — цикл, и спека теряет
собственную сюиту.

#### `spec-exports-fixture` {#spec-exports-fixture}

Спека, импортирующая другую спеку. Сюиты импортированного файла собираются дважды, а его хуки
выполняются в контексте чужого файла. Общую фикстуру стоит вынести в файл, который не спека.

#### `foreign-runner-pragma` {#foreign-runner-pragma}

`@jest-environment` и родня, забытые в спеке, со строками, где они стоят. Vitest их не читает вообще;
среда берётся из конфига, так что комментарий выглядит рабочим, но не работает. Исправление называет
`@vitest-environment`, который говорит то же самое.

#### `dead-runner-config` {#dead-runner-config}

`jest.config.*`, `karma.conf.*` для раннера, который не установлен. Это первый файл, который новичок —
или агент — открывает, чтобы понять, как тут запускаются тесты.

#### `orphan-runner-file` {#orphan-runner-file}

Setup-файл, на который ссылался только этот мёртвый конфиг. Один найденный так файл был пустым ещё до
переезда: год в роли настройки, которая ничего не настраивала.

#### `angular-build-splitting-off` {#angular-build-splitting-off}

`@angular/build` в диапазоне `[22.1.5, 22.1.7)`. Бандл для юнит-тестов собирается без code
splitting, поэтому `--coverage` растёт на сотни мегабайт без выхода на плато, а билдер не печатает ни
одного предупреждения — прогон либо идёт медленно, либо его убивают за память. Исправление —
обновиться: с 22.1.7 splitting включён по умолчанию, а исправление называет таргеты unit-test, из
которых нужно убрать `"splitting": false`, если он там есть (22.2.0 объявляет опцию устаревшей: Vitest 5
она больше не нужна). См.
[чем он платит и как выйти](/ru/adapters/angular#when-the-unit-test-build-has-code-splitting-off);
`setupAutoSpy()` говорит об этом же раз на воркер изнутри задетого прогона.

#### `analog-behind-angular-build` {#analog-behind-angular-build}

`@angular/build` 22.2.0 или новее рядом с `@analogjs/vite-plugin-angular` старше 2.7.5. С 22.2.0
`SourceFileCache` билдера больше не наследует `Map`, а старый хост Analog вызывает на нём `cache.has`,
поэтому прогон падает на старте с `TypeError: cache.has is not a function` ещё до того, как собрана
первая спека. Ни один из пакетов в ошибке не назван. Исправление — обновить
`@analogjs/vite-plugin-angular` и `@analogjs/vitest-angular` до 2.7.5 или новее. Если какого-то из
пакетов нет, проверка молчит.

#### `builder-setup-unreached` {#builder-setup-unreached}

Таргет `@angular/build:unit-test` или `@nx/angular:unit-test`, чьи опции (вместе с `targetDefaults` из
`nx.json`) не называют ни `setupFiles`, ни `runnerConfig`, в проекте, чей конфиг Vitest (включая
`vitest-base.config.*`) перечисляет setup-файлы или где есть `src/test-setup.ts`. Билдер его никогда не запускает, поэтому
`setupAutoSpy()`, его `strict`, зарегистрированные матчеры и адаптер моков отсутствуют только под этим
таргетом. Исправление — опция `setupFiles` у этого таргета; `targetDefaults` в `nx.json` проносит её в
каждый проект с той же раскладкой, а `runnerConfig`, указывающий на конфиг Vitest, тоже подходит.

#### `module-mock-leak` {#module-mock-leak}

Один и тот же модуль замокан фабрикой в одной спеке и автомоком или `{ spy: true }` в другой, когда
среда общая (`isolate: false` в конфиге Vitest или умолчание Angular-билдера unit-test — находка
говорит, что именно). Умолчание билдера засчитывается начиная с `@angular/build` 21, если только
собственная опция `isolate` у таргета или конфиг раннера, который он называет, не задаёт
`isolate: true`; 20.x сохраняет пофайловую изоляцию Vitest. Vitest отдаёт фабрику более позднему автомоку, и тот падает с
`No "X" export is defined on the mock` только тогда, когда два файла попали в один воркер. Находка
перечисляет файлы с фабрикой и называет модуль так, как его назовёт ошибка. Исправление — мокать его
одинаково в обоих файлах; второй выход — `vi.resetModules()` перед импортом.

#### `mock-reset-config-unread` {#mock-reset-config-unread}

Запись `no-redundant-mock-reset`, в опциях которой назван `configFile` и рядом с ним нет ни одного
флага, а default export этого файла — вызов чего-то кроме `defineConfig` / `defineProject`: собственной
фабрики проекта или `mergeConfig`. Правило читает файл как текст, поэтому флаги, которые ставит
фабрика, ему не видны: оно не находит `clearMocks`, до Vitest 4 молчит, а с Vitest 5 считает флаг
включённым по умолчанию, что бы ни делала фабрика. Это заметка, а не ошибка. Исправление — выписать
флаги рядом с `configFile`: они важнее файла. Читается только литеральный `configFile`, путь
отсчитывается от корня репозитория.

#### `coverage-all-removed` {#coverage-all-removed}

`coverage.all` на Vitest 4 и новее. Ключ убрали, а не переименовали: его никто не читает и никто не
предупреждает, так что отчёт молча покрывает только то, что прогон импортировал.

#### `coverage-include-recompiles-globs` {#coverage-include-recompiles-globs}

Область покрытия из множества глобов на Vitest 4, где провайдер компилирует каждый глоб заново для
каждого проверяемого файла: `isIncluded()` вызывает `picomatch.isMatch(file, patterns, options)`,
который строит матчеры на каждом вызове, а `globCache` рядом запоминает только вердикт. Ничего не
падает. Vitest 5 компилирует список один раз; на четвёрке рецепт с custom-провайдером из раздела
[сопоставление покрытия стоит дороже самого покрытия](/ru/adapters/angular#coverage-matching-costs-more-than-coverage)
сократил один шард из 1 725 файлов с 229,59 с до 22,88 с при побайтно одинаковом отчёте. Под
`@angular/build:unit-test` Vitest 5 требует `@angular/build` 22.2.0 или новее, и исправление говорит об
этом, когда такой таргет в воркспейсе есть.

#### `coverage-include-misses-bundle` {#coverage-include-misses-bundle}

`coverage.include` только по исходникам в конфиге раннера у таргета `@angular/build:unit-test` — в
файле, который называет его `runnerConfig`, или, при `runnerConfig: true`, в `vitest-base.config.*`,
который билдер находит в корне проекта или воркспейса.
Покрытие сопоставляется дважды — сначала с чанками выполненного бандла, потом с ремапленными
исходниками. Список `.ts`-глобов теряет все счётчики на первом проходе, а прогон остаётся зелёным —
см. [покрытие под билдером unit-test](/ru/adapters/angular#coverage-under-the-unit-test-builder).

#### `vitest-5-removed` {#vitest-5-removed}

То, что Vitest 5 убрал, найденное в репозитории: импорт из `vitest/reporters` или `vitest/coverage`
(вместо них — `vitest/node`), `vitest/environments` или `vitest/snapshot` (вместо них —
`vitest/runtime`), `vitest/runners` или `vitest/suite` (вместо них — `TestRunner` из `vitest`) или
`vitest/mocker` (вместо него — `@vitest/mocker`); цепочка `.sequential` у `test`, `it`, `describe` или
`suite` (вместо неё — `{ concurrent: false }`); `--outputJson` или `--compare` в скрипте, который
запускает Vitest, и `benchmark.outputJson` или `benchmark.compare` в конфиге (вместо них —
`--reporter=json --outputFile=<path>`, а также `writeResult` вместе с `bench.from()`). На Vitest 5
каждая такая находка — ошибка, потому что сломано уже сейчас: спецификатор перестаёт резолвиться, сбор
файла падает, команда останавливается на `Unknown option` или ключ молча игнорируется. На Vitest 4 те
же строки работают, поэтому это заметки к обновлению: код выхода не меняется, а замены для импортов и
для `.sequential` работают уже на 4.1, так что правку можно влить до обновления. До Vitest 4 проверка
молчит — путь на пятёрку идёт сначала через собственную миграцию Vitest 4. Опция теста
`{ sequential: true }` не читается.

Ещё одна запись старше Vitest 5: `poolOptions` в конфиге на Vitest 4 и новее — предупреждение. Vitest
убрал его в четвёрке и печатает одну строку о deprecation, а потом работает без всех опций внутри,
так что `singleFork` или лимит потоков там ничего не настраивают. Исправление — опция верхнего
уровня, на которую её отображает гайд по миграции на Vitest 4.

`test.workspace` не репортится: Vitest 4 и 5 оба падают на старте и называют `test.projects`, так что
зелёной сюиты с ним не бывает. Не репортятся и переименованные ключи конфига, которые Vitest 5 ещё
принимает, — `experimental.fsModuleCache` и `experimental.fsModuleCachePath` (теперь на верхнем
уровне), `browser.isolate`, `browser.fileParallelism` и `browser.api` (теперь `isolate`,
`fileParallelism` и `api` верхнего уровня), `deps.optimizer.web` (теперь `deps.optimizer.client`) и
`cache.dir` (теперь `cacheDir` самого Vite): Vitest 5 на каждом прогоне печатает deprecation с
названием замены, а на Vitest 4 нового написания ещё нет.

#### `vitest-5-deprecated` {#vitest-5-deprecated}

Вызов `experimental_clearCache()` или `experimental_parseSpecifications()` на Vitest 5, который
переименовал их в `clearCache()` и `parseSpecifications()`. Это заметка: старые имена ещё работают, и в
отличие от переименованных ключей конфига во время прогона ничто не предупреждает — `@deprecated`
стоит только в типе. У Vitest 4 других имён для них нет, поэтому там проверка молчит.

#### `vitest-5-clear-mocks` {#vitest-5-clear-mocks}

Vitest 5 включает `clearMocks` по умолчанию: перед каждым тестом он вызывает `vi.clearAllMocks()`,
который стирает записанные вызовы каждого мока и оставляет его реализацию. На Vitest 5 явный
`clearMocks: true` в конфиге повторяет значение по умолчанию, и заметка говорит об этом. На Vitest 4
заметка приходит в репозиторий, чьи конфиги нигде не задают `clearMocks` (и `mockReset: true`, который
тоже очищает), а скрипты Vitest не передают `--clearMocks`: после обновления тест, который считает
вызовы, сделанные в `beforeAll` или в предыдущем `it`, начинает падать. `npx vitest run --clearMocks`
на Vitest 4 гоняет сюиту так, как будет гонять Vitest 5, так что цена известна до обновления; под
`@angular/build:unit-test` на этот один прогон поставьте `clearMocks: true` в конфиге раннера.
Явный `clearMocks: false` сохраняет сегодняшнее поведение.

#### `vitest-5-available` {#vitest-5-available}

Заметка на Vitest 4 и причина прочитать предыдущую. Если ничто в репозитории не мешает обновлению, она
говорит, что даёт Vitest 5: на сюите Angular 22.2 из 700 спек-файлов с покрытием прогон ускорился с
16,50 с до 8,91 с на v8 (−46 %) и с 37,07 с до 23,92 с на istanbul (−35,5 %); без покрытия обе
мажорные версии идут вровень. Методика и таблица — в разделе
[Vitest 5 под Angular-билдером unit-test](/ru/core/performance#vitest-5-under-the-angular-unit-test-builder).

Если что-то мешает, заметка называет это, с исправлением для каждого пункта: `@angular/build` старше
22.2.0 рядом с таргетом `@angular/build:unit-test` (первый релиз, чей билдер запускает Vitest 5),
`@analogjs/vite-plugin-angular` или `@analogjs/vitest-angular` старше 2.7.5, `vite` старше 6.4 или
версия Node ниже 22.12 в `.nvmrc`, `.node-version`, конфиге CI (`node-version:` или образ `node:`) или
в `engines` приватного пакета. `engines` публикуемого пакета не учитывается: он описывает потребителей
пакета, а не то, где идут его тесты. Vitest 2 и 3 заметку не получают: замер — это Vitest 4 против 5.

#### `fs-module-cache-not-persisted` {#fs-module-cache-not-persisted}

`fsModuleCache` включён — на верхнем уровне, под `experimental` или флагом `--fsModuleCache` в
скрипте — на Vitest 4 и новее, в репозитории с конфигом CI (`.github/workflows/*.yml`,
`.gitlab-ci.yml` и `.gitlab/**/*.yml`, `.circleci/config.yml`, `azure-pipelines.yml`,
`bitbucket-pipelines.yml`), ни один из которых не кеширует каталог кеша: `fsModuleCachePath`, а по
умолчанию `node_modules/.vitest-cache` на Vitest 5 и `node_modules/.experimental-vitest-cache` на
Vitest 4. Конфиг CI считается кеширующим, если называет путём этот каталог или каталог над ним,
например `node_modules`. Иначе каждый прогон в CI начинается с пустого кеша и платит за полный
transform, а настройка помогает только локально. `cache: npm` в `actions/setup-node` не считается: он
хранит кеш загрузок npm, а не `node_modules`. Vitest сам стирает кеш, когда меняется лок-файл, так что
ключа по хешу лок-файла достаточно. `npm ci` удаляет `node_modules` перед установкой, поэтому CI, который
его запускает, должен указать `fsModuleCachePath` вне `node_modules` и кешировать этот каталог.

#### `jasmine-era-project` {#jasmine-era-project}

`jasmine-core`, `@types/jasmine`, `jasmine-auto-spies`, `@hirez_io/observer-spy`, пакет `karma*` или
`karma.conf.*` на диске — либо `"types": ["jasmine"]` в tsconfig. Info, никогда не ошибка: репозиторий
имеет полное право оставаться jasmine-репозиторием. В подсказке назван порядок, который работает, —
направить спеки на [`vitest-auto-spy/jasmine`](/ru/migrating-jasmine) и довести сюиту до зелёного,
_а потом_ `codemod --from jasmine` и убрать импорт. Наоборот — это переписывание сюиты, которая
никогда не была зелёной.

#### `no-agent-instructions` {#no-agent-instructions}

Ни один `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` не называет пакет. Заметка, не ошибка: это
единственный момент, когда сказать об этом ничего не стоит. Исправление читает `.gitignore`: если
часть файлов инструкций не лежит в git, оно называет отслеживаемые в `init --only`; если не лежит ни
один, оно советует передать `--ignore no-agent-instructions` в CI, который их никогда не видит.

#### `helper-from-wrong-entry` {#helper-from-wrong-entry}

Хелпер, импортированный из точки входа, которая его не экспортирует, — `provideAutoSpy` из корня,
`flushEventLoop` из `/angular`. Чтобы сопоставить имя с точкой входа, которой оно принадлежит, нужна
таблица, сгенерированная из export map установленной версии, — а её нет ни у одного пофайлового
линтера, см. [две проверки, которые разрешают имя](#the-two-checks-that-resolve-a-name). Срабатывает
она обычно там, куда не дотягивается ни одна программа `tsc`.

#### `no-unawaited-helper` {#no-unawaited-helper}

`expectEmission`, `expectError`, `stable`, `flushEventLoop` и их родня, вызванные как отдельная
инструкция и выброшенные, со строками, где они стоят. Промис разрешается уже после конца теста,
поэтому ассерт внутри рапортует в более поздний тест или в никуда. Прогон остаётся зелёным, а спека
выглядит так, будто что-то проверила.

#### `scan-cap-reached` {#scan-cap-reached}

Скан файлов остановился на предохранителе в 50 000 файлов (`VITEST_AUTO_SPY_SCAN_CAP` его
поднимает), так что каждая другая проверка прочитала только часть дерева. Репозиторий крупнее раньше
получал «No problems found.» за файлы, которых никто не читал; теперь он получает это предупреждение
и код 1, пока предел не поднят или `--cwd` не сузил дерево.

### Что скан считает этим репозиторием {#what-the-scan-counts-as-this-repository}

Каждая проверка выше читает один и тот же список файлов, и первая строка отчёта — его длина, поэтому
то, что в него попадает, решает, о чём будет каждая находка. Строят его четыре правила:

- **Директории вывода сборки и пакетов пропускаются целиком**: `node_modules`, `dist`, `build`,
  `coverage`, `out-tsc`, `.git`, `.angular`, `.nx`, `.next`, `.nuxt`, `.output`, `.svelte-kit`,
  `.turbo`, `.yarn`, `.cache`, `bower_components`, `out`, `tmp`, `vendor` — а также хранилища пакетных
  менеджеров, которые CI нередко держит внутри рабочей копии: `.bun`, `.npm`, `.pnpm-store`.
- **Директория, исключённая правилами git, тоже пропускается** — `src/generated/`, `/reports`,
  `tmp-*/`, `**/cache`, а `!` возвращает директорию, как это делает git. Правила берутся оттуда же,
  откуда их читает git, от младшего к старшему: пользовательские исключения (`core.excludesFile` из
  глобального конфига или конфига репозитория, иначе `$XDG_CONFIG_HOME/git/ignore`; `GIT_CONFIG_GLOBAL`
  учитывается, `[include]` не раскрывается), `.git/info/exclude` корня (через файл `.git` у worktree
  тоже), корневой `.gitignore` и каждый `.gitignore` ниже — каждый относительно своей директории.
  Читаются сами файлы, `git` не вызывается, и в счёт идут только директории: игнорируемый файл в
  список попадает. Паттерн с экранированием `\` или POSIX-классом отбрасывается — это лишь значит, что
  скан прочтёт больше, — а если не удаётся прочесть правило с `!`, его файл не применяется целиком,
  чтобы не отрезать директорию, которую git оставляет. `.gitignore` выше корня скана не читается:
  запускайте из корня репозитория, иначе домашняя директория под git с `*` опустошила бы скан.
- **В директорию, которая сама по себе репозиторий, скан не заходит** — git-worktree, у которого
  `.git` — файл, или вложенный клон. Его файлы лежат на чужой ветке: пока их считали, каждый граф
  импортов выходил дублем самого себя, а на дереве самого этого репозитория, где ворктри лежат в
  директории с точкой в имени, это давало **2 240 файлов против 1 213**, которые в нём есть на самом
  деле. То же правило не пускает `codemod --write` в рабочую копию чужой ветки.
- **Скан останавливается на 50 000 файлов.** `codemod` говорит об этом в stderr, а не объявляет
  репозиторий переехавшим по списку, который не дочитал, а `VITEST_AUTO_SPY_SCAN_CAP` поднимает
  предел для репозитория, который действительно больше.

### Две проверки, которые разрешают имя {#the-two-checks-that-resolve-a-name}

`helper-from-wrong-entry` и `no-unawaited-helper` обе отвечают на вопрос про имя, и ни одна не
гадает. Таблица точек входа, которую они читают, **генерируется из собственной карты `exports` этого
пакета** — barrel-модули компилируются, экспортированные символы берутся у компилятора, а набор функций,
возвращающих промис, — из сигнатур, а не из списка, набитого руками. Написанная руками копия
разъехалась бы при первом же переезде хелпера между точками входа — и разъехалась бы молча.

Поэтому же это проверки `doctor`, а не правила линтера: у пофайлового линтера такой таблицы нет.

Обе сознательно консервативны.

- Таблица описывает одну мажорную версию. `doctor` читает версию, реально установленную в
  репозитории, и молчит, когда мажоры расходятся. Правило, на котором это держалось, — хелпер
  переезжает между точками входа только в мажоре — перестало быть верным в 5.21.0: тридцать два
  имени уехали из `/angular` в три спутника внутри минора. Значит, внутри одного мажора таблица
  может опережать установку, поэтому `helper-from-wrong-entry` ещё и читает `exports` копии, которая
  разрешается от каждого файла, и называет только те точки входа, которые эта копия публикует. Если
  CLI **новее** установленной копии (`npx vitest-auto-spy@latest doctor` против закреплённой
  5.20.x), хелпер, чьей новой точки входа там ещё нет, просто не попадает в отчёт; если манифест
  установки не читается вовсе, проверка молчит, а не гадает.
- `no-unawaited-helper` рапортует одну-единственную форму — вызов, который и начинает инструкцию, и
  заканчивает её. Всё, откуда промис ещё может утечь наружу, остаётся нетронутым: `await`, `return`,
  присваивание, аргумент, `.then`, короткое тело стрелки, явный `void`. Как и одноимённый метод, и
  любой вызов, чей callee этот файл у нас не импортировал. `expectEmission`, переименованный через
  `as`, всё равно разрешается; чужой `stable` — никогда.
- Ни одна не читает текст, который не является кодом. Строки, шаблонные литералы и комментарии
  вырезаются до всякого сопоставления, так что фикстура кодмода, генератор документации, цитата в
  заголовке `describe` или закомментированная строка не попадут в отчёт никогда. Комментарии
  вырезаются первыми, потому что апостроф в прозе иначе открыл бы строку. Именно этот случай и
  определил дизайн: собственные спеки этого пакета цитируют import-инструкции, и проверка, которая
  бы на них рапортовала, была бы красной на репозитории, который её и поставляет.

На собственных 758 исходниках этого репозитория обе не находят ровным счётом ничего.

**Всё ещё только чтение.** Обе находки называют механическую правку — поменять специфер, добавить
`await`, — и ни одна не применяется. Никакого `--fix` в `doctor` нет вообще, и это решение, а не
пробел: инструмент, который только что сообщил вам о четырёх вещах, которых больше никто не видел,
ещё не заслужил права писать в прочитанные им файлы.

## `perf` — куда на самом деле уходит время CPU {#perf-—-where-the-cpu-time-actually-goes}

Vitest печатает одну итоговую строку на прогон — `Duration 8.91s (transform 26.20s, setup 14.70s,
import 55.27s, tests 27.24s, environment 155.65s)`, — и это единственное место, где эти шесть чисел
вообще появляются. Она говорит, что подготовка среды — 56 % времени CPU; она не говорит, какие из
1 400 спек сюиты вообще не нуждались в DOM. `perf` читает те же числа по каждому файлу через
`TestModule.diagnostic()` — собственный публичный аксессор Vitest, через репортер, который
поставляет этот пакет, — и превращает доминирующую фазу в список файлов и правило, по которому они
туда попали. Никакого разбора вывода терминала здесь нет.

```bash
npx vitest-auto-spy perf              # прогнать всю сюиту один раз и отчитаться
npx vitest-auto-spy perf src/cli      # путь передаётся в Vitest как фильтр по файлам
npx vitest-auto-spy perf --json out/perf.json   # разобрать готовый отчёт вместо прогона Vitest
npx vitest-auto-spy perf --out out/perf.json    # сохранить JSON, который пишет этот прогон
npx vitest-auto-spy perf --gate                 # упасть на медленном файле или тесте и сказать почему
```

**Если добавлять в CI одну строку, то `perf --gate`.** Он падает только на файле или теле теста,
который медленный относительно остального того же прогона, сначала перемеряет его в одиночку и под
подтверждённой находкой печатает карточку того, что увидел CPU-профиль, — самые медленные тесты, хуки
против тел, куда ушло время по пакетам и в вашем собственном коде, и вероятную причину.
[Гейт](#the-gate) показывает карточку целиком и правило, по которому считается бюджет; остальная часть
раздела — советы, которые `perf` печатает на каждом прогоне.

На Vitest 5 голый прогон ещё и передаёт `--experimental.diagnostics=false`, чтобы собственные подсказки
Vitest после прогона не повторяли то, что печатает `perf`.

```
$ npx vitest-auto-spy perf src/cli
vitest-auto-spy perf — /Users/alexeypopov/Desktop/projects/vitest-auto-spy
16 test files, 860ms wall clock, 17.30s of CPU time summed over the workers

  phase               time    share
  prepare            6.34s    36.7%
  environment        5.46s    31.6%
  setup              3.01s    17.4%
  transform          1.19s     6.9%
  import             879ms     5.1%
  tests              411ms     2.4%

info   perf-environment
       Environment setup is 31.6% of the measured CPU time, against 2.4% in the test bodies. No
       spec file could be proved DOM-free, so this names none; 109 were left undecided.
       → Nothing can move while every spec loads `src/test-setup.ts`: a setup file that
         mentions a DOM name keeps every spec on the DOM. Move the DOM part of it into a setup
         file only the DOM specs load.
       Docs: https://asdalexey.github.io/vitest-auto-spy/utilities/cli#perf-environment

info   perf-isolation
       Per-file environment, setup and prepare together are 85.6% of the measured CPU time.
       `test.isolate: false` pays those once per worker instead of once per file.
       → Try `isolate: false` in vitest.config.mts and keep it only if peak memory stays
         acceptable: without isolation, every double a file creates lives until its worker ends.
       Docs: https://asdalexey.github.io/vitest-auto-spy/utilities/cli#perf-isolation

```

Это собственная сюита этого репозитория. Она называет ноль кандидатов на жизнь без DOM и оставляет
109 файлов нерешёнными, потому что `src/test-setup.ts` строит Angular `TestBed` перед каждой
спекой, — правило ниже как раз объясняет, почему настоящий репозиторий получает честное «не могу
сказать» вместо догадки, а исправление называет setup-файл, который это решил.

**Суммы по фазам — это время CPU, сложенное по воркерам**, а не время по часам: прогон выше занял
860 мс на часах и 17,30 с CPU, потому что работа разошлась по нескольким воркерам. Сумма фазы
больше времени по часам — не баг.

| Фаза          | Что измеряет Vitest (формулировки его собственного `ModuleDiagnostic`)                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| `environment` | Время на импорт и инициализацию среды (`jsdom`, `happy-dom`, `node`) для файла                              |
| `prepare`     | Время, которое Vitest тратит на подготовку тестовой обвязки — раннера, моков — для файла                    |
| `import`      | Время на импорт тестового модуля: всего, что он импортирует, плюс выполнение его suite-колбэков             |
| `setup`       | Время на импорт настроенных setup-файлов для этого файла                                                    |
| `tests`       | Накопленная длительность самих тел тестов и хуков                                                           |
| `transform`   | Время трансформации (esbuild/Vite): за весь прогон до Vitest 5, по файлам на пятёрке — см. `perf-transform` |

Фаза порождает находки, только когда она стоит чьего-то вечера: ниже 30 % от общего времени или
ниже 5 с суммарного CPU за весь прогон `perf` так и говорит и на этом останавливается, а не называет
файлы поверх шума.

### Советы, которые он печатает {#the-advice-it-prints}

На Vitest 5 отчёт ещё и записывает конфигурацию, которую Vitest на самом деле разрешил, — `isolate`,
`pool`, `maxWorkers`, `environment`, `fsModuleCache`, — и какие из них вы задали сами
(`providedOptions` Vitest). Когда она есть, советы ниже читают эти значения, а не ищут их в тексте
`vite(st).config.*`, так что засчитывается и настройка, сделанная в билдере, в проекте воркспейса или в
командной строке. Против опции, которую вы задали явно, совета не бывает: собственные подсказки Vitest
следуют тому же правилу.

#### `perf-environment` {#perf-environment}

Срабатывает, когда доминирует `environment`. Он ранжирует каждую спеку,
которая _обходится без DOM_ — доказуемо, а не вероятно, — по потраченному ею времени среды и
предлагает для каждой `// @vitest-environment node` (или проект со средой `node`). Правило намеренно
одностороннее: спека становится кандидатом, только если она сама, настроенные setup-файлы и каждый
модуль репозитория, который кто-то из них импортирует, были прочитаны, ни в одном из них не
упоминается DOM-имя, а все импортируемые ими пакеты входят в короткий белый список без DOM
(`vitest`, `rxjs`, `date-fns`, `lodash`, `zod`, …). Всё, что правило не смогло разрешить, — импорт,
за которым не пройти, пакет вне списка — попадает в **нерешённые**, а не в безопасные по умолчанию:
ложное срабатывание — это чья-то сюита, падающая на `document is not defined`, и это дороже, чем
упущенная оптимизация. На этом репозитории правило не называет ничего и относит 109 файлов к
нерешённым — по причине выше.

**Окружение считается один раз на воркер, а не на файл.** Vitest строит окружение один раз на
воркер и затем копирует это одно число в отчёт каждого файла, который воркер прогнал, поэтому сумма
по файлам умножает один запуск на число файлов за ним — на шарде в 672 файла на 13 воркерах 126.4 s
в отчёте против 2.44 s на деле. `perf` считает каждое различное значение один раз, а находка честно
оценивает перенос: окружение воркера экономится, только если **каждый** файл, который он прогнал,
свободен от DOM, и когда сосед с DOM означает, что перенос ничего не освобождает, находка так и
говорит.

На Vitest 5 каждый файл ещё и сообщает дорожку, на которой шёл (`concurrencyId`), и `perf` считает
значение один раз на дорожку, а не один раз на весь прогон, так что две дорожки, у которых случайно
совпало время окружения, больше не сливаются в одну. Vitest 5 сообщает и `workerId` на каждый файл, но
это новое число для каждого файла, даже когда воркер переиспользуется под `isolate: false`, поэтому
`perf` по нему не группирует.

#### `perf-environment-engine` {#perf-environment-engine}

Вторая половина того же совета, для файлов, которые `perf-environment` увезти не может: спеке, которой DOM действительно нужен, его всё равно приходится
строить, а `happy-dom` строит его дешевле. Замерено на собственной ангуляровской сюите этого пакета,
на тех же 117 файлах и тех же проверках: **26,5 с user CPU против 23,2 с**, то есть на 12 % меньше.
На спеке, которая строит DOM и больше ничего не делает, разрыв куда шире — 253 мс против 119 мс
environment-времени на файл, — так что сколько из него вернётся, зависит от того, какую долю файла
занимает окружение.
Срабатывает, только если прогон шёл на `jsdom` — на Vitest 5 это читается из разрешённого конфига, до
него из `vite(st).config.*`, который называет `jsdom`, — и ни один из конфигов не упоминает
`happy-dom`: сюиту, которая этот выбор уже сделала, второй раз не спрашивают. Находка называет конфиг,
который ставит `jsdom`. Это замена, а не флаг: `happy-dom` реализует меньше платформы, поэтому
переключать стоит по одному проекту за раз, оставляя сюиту зелёной после каждого.

#### `perf-transform` {#perf-transform}

Только Vitest 5. С Vitest 5 каждый файл сообщает, сколько его сбор и setup ждали, пока сервер Vite
трансформирует модули (`collectFetchDuration` + `setupFetchDuration`), и таблица фаз считает это
ожидание как `transform`, а не внутри `import` и `setup`, — так же делит время итоговая строка самого
Vitest. Находка срабатывает, когда это ожидание — 30 % измеренного времени CPU или больше, а кеш
модулей выключен. Она печатает секунды, которые файлы прождали, в сумме по ним, и советует
`fsModuleCache: true`: следующий прогон прочитает трансформированные модули из
`node_modules/.vitest-cache`, а не будет трансформировать их заново, так что напечатанное ожидание —
потолок того, что это сэкономит. В CI кеш помогает, только если этот каталог сохраняется между
пайплайнами, в кеше джобы, — находка об этом говорит. Она не срабатывает, когда `fsModuleCache` уже
включён или когда вы задали его явно (например, `false`). В отчёте Vitest 4 опция пишется
`experimental.fsModuleCache`, а каталог — `node_modules/.experimental-vitest-cache`.

#### `perf-import` {#perf-import}

Срабатывает, когда доминирует `import`, и называет каждую спеку, которая
добирается до своего предмета через barrel — модуль `index`/`public-api` без собственных объявлений,
одни реэкспорты, — потому что спека, импортирующая такой модуль, грузит всё, что barrel реэкспортит,
ради одного экспорта из неё. В прогоне выше он не срабатывает: `import` — всего 5,1 % от суммы этого
репозитория.

На Vitest 5 ожидание трансформации считается под `transform`, так что `import` — это одно выполнение:
запуск модулей, до которых дотягивается спека, — и находка так и говорит. Ожидание, пока Vite их
трансформирует, — дело `perf-transform`, и `isolate: false` его не меняет: сервер трансформирует каждый
модуль один раз в любом случае.

#### `perf-isolation` {#perf-isolation}

Срабатывает, когда `environment` + `setup` + `prepare` доминируют вместе, и
показывает на `test.isolate: false` — настройку, которая платит за эти три раз на воркер, а не раз
на файл. Он подан как сделка, а не как выигрыш, и ссылается на собственные замеры памяти этого
пакета ([`core/performance#memory-under-isolate-false`](/ru/core/performance#memory-under-isolate-false)),
а не повторяет числа здесь: без изоляции каждый дубль, созданный файлом, живёт до конца воркера, и
пиковая память растёт вместе с сюитой. `perf` не предлагает эту настройку, когда у прогона уже
`isolate: false` — на Vitest 5 это читается из разрешённого конфига, до него из `vite(st).config.*` или
из Angular-билдера, который её передаёт, — когда пул `vmThreads` или `vmForks`, которые и так дают
каждому файлу свежий контекст, или когда вы задали `isolate` сами.
`@angular/build:unit-test` передаёт `isolate: false` начиная с 21.0, но накладывает блок `test` из
конфига раннера, который называет таргет, поверх этого умолчания, так что `test.isolate: true` там
остаётся в силе и `perf` всё равно предлагает сделку; с 22.1 собственная опция `isolate` у таргета
важнее обоих.

На Vitest 5 находка ещё и говорит, во что изоляция обошлась на старте: сколько воркеров было запущено и
их суммарное время старта (запуск, загрузка бандла и окружение — `state.startupTime` и
`state.workersSpawned`). Когда воркеров запущено больше, чем дорожек, она печатает выигрыш по часам по
той же оценке, что даёт собственная подсказка Vitest 5 про изоляцию: суммарный старт, разложенный по
дорожкам, минус один старт на дорожку, который остаётся при переиспользовании воркеров, —
`startup ÷ lanes − startup ÷ workers`, где дорожек меньшее из числа файлов и `maxWorkers` (или самая
старшая дорожка, которую занял прогон). Печатается как «не меньше»: выполнение модулей, которое
переиспользованные воркеры тоже экономят, в неё не входит.

#### `perf-workers` {#perf-workers}

Единственная находка здесь, которая про память, а не про время. Vitest берёт по
воркеру на ядро, а воркер — это целый рантайм: замерено на собственной ангуляровской сюите этого
пакета, резидентная память вышла в **1,42 ГБ плюс ~155 МБ на воркер**, так что на 16-ядерной машине
восемь воркеров сверх капа в четыре — это около 1,9 ГБ сами по себе. Wall clock такой кап стоит
немного: на полевой развёртке этого пакета — **13,50 с против 13,13 с** на оптимуме из восьми, то
есть 2,8 %, при 3,7 ГБ резидентной памяти вместо 5,8 ГБ. Срабатывает только на прогоне, чья сумма
CPU больше минуты, и только когда `maxWorkers` нигде не объявлен: ниже этого настройка — деталь, а
сюита, которая её выставила, эту мысль уже думала. Находка считает ядра машины, на которой шёл
прогон, и предлагает половину из них — в том конфиге раннера, который нашла. Само число — свойство
машины, а не сюиты: сравните время по часам до и после, прежде чем фиксировать его.

На Vitest 5 число берётся из прогона, а не из машины: разрешённый `maxWorkers` или самая старшая
дорожка, на которой шёл файл. Прогону, который ни разу не занял больше половины ядер, ограничивать их
не советуют.

#### `perf-long-pole` {#perf-long-pole}

Только Vitest 5. Каждый файл сообщает дорожку, на которой шёл (`concurrencyId`), и момент старта, так
что `perf` может разложить прогон по дорожкам. Тогда в шапке появляется одна строка — сколько дорожек,
насколько они были заняты на отрезке от первого старта до последнего конца и какой файл шёл в конце
один:

```text
15 lanes busy 40.5% of the 2.58s span; src/cli/report.spec.ts ran alone for the last 10ms
```

Находка срабатывает на файле, который ещё шёл, когда все остальные дорожки уже простаивали, если этот
хвост не короче 2 с и не меньше 30 % отрезка: всё это время прогон по часам был одним файлом. Разбейте
файл, чтобы его тесты разошлись по нескольким дорожкам, или сохраняйте кеш результатов Vitest между
прогонами CI — его секвенсер первыми запускает файлы, которые знает как медленные, а медленный файл,
запущенный последним, и есть время прогона по часам. Время файла на дорожке — его `prepare` + `setup`

- `import` + `tests`; окружение не входит, потому что переиспользованный воркер не платит за него на
  каждый файл.

#### `perf-vitest-doctor` {#perf-vitest-doctor}

Только Vitest 5, и одной строкой. Когда срабатывает находка про переключатель — `perf-isolation`,
`perf-environment-engine`, `perf-transform` или `perf-workers`, — а прогон снят на Vitest 5 или новее,
`perf` показывает на `npx vitest doctor`: собственный A/B-раннер **Vitest**, а не `doctor` этого
пакета. Он перезапускает сюиту по разу на каждого кандидата — пул, изоляцию, DOM-движок и кеш модулей,
— делит `maxWorkers` пополам, пока это помогает, и советует только переключатель, который на этой
машине замерил как более быстрый. `perf` называет переключатель по одному прогону; `vitest doctor` —
способ подтвердить его, прежде чем оставить. `perf-environment` его не вызывает: перенос файлов на
`node` докблоком — не тот кандидат, который меряет `vitest doctor`.

### Когда читать нечего {#when-there-is-nothing-to-read}

Без `--gate` `perf` выходит с `0` на любом отчёте, который смог прочитать, —
медленная сюита не значит падающая, поэтому сама по себе она никогда не роняет CI-джобу. Он выходит
с `2`, когда судить нечего: Vitest не установлен в `--cwd`, отсутствует собственный
`dist/perf-reporter.js` пакета, прогон не выдал отчёта, файл `--json` не парсится или в отчёте не
выполнилось ни одного тела теста. `1` принадлежит только гейту — см. [Гейт](#the-gate). Если сюита
прогналась, но упала, `perf` всё равно рапортует измеренные тайминги — с предупреждением, что сам
прогон не прошёл.

Каждый из этих случаев назван своим именем. Путь `--json`, которого нет, файл, который не валидный
JSON, JSON, который не отчёт perf, и отчёт версии формата, которую эта сборка не читает, — четыре
разные строки. `--command`, вышедший с ненулевым кодом без отчёта, — это упавший прогон: сначала
добейтесь, чтобы он проходил; вышедший с `0` без отчёта дошёл до конфига Vitest, который не подключает
репортер, и сообщение печатает две строки, которые нужно добавить
([ниже](#when-a-bare-run-is-not-your-suite)). Отчёт, все файлы которого лежат вне `--cwd`, был снят в
другой рабочей копии: передайте `--cwd` директорию, где его снимали.

Репортер не ждёт конца прогона, чтобы писать: по мере того как файлы заканчиваются, он переписывает
отчёт, не чаще раза в две секунды, с пометкой `partial: true`, так что прогон, который Vitest не
довёл до конца, — убитый, упавший или вышедший по таймауту, — всё равно оставляет отчёт. `perf`
печатает то, что намерили законченные файлы, под предупреждением, что прогон не закончился, и с
числом файлов в отчёте, а гейт отказывается его судить ровно так же, как красный прогон: файлов, до
которых прогон не дошёл, в отчёте нет, а вердикт по части сюиты — это «всё чисто», которое она не
заработала. `--format json` несёт `run.partial: true`, а `--format markdown` пишет «the run did not
finish» вместо «the suite did not pass».

### Flaky-тесты и куча {#flaky-tests-and-the-heap}

Две находки делаются на каждом прогоне, каким бы дешёвым он ни был, потому что ни одна из них не про
фазы.

#### `perf-flaky` {#perf-flaky}

Называет каждый файл, где тест прошёл только после ретрая — это собственный
`TestCase.diagnostic().flaky` Vitest, — и сами тесты по имени. Это предупреждение, прогон остаётся
зелёным. Упавшие попытки входят во время файла, поэтому гейт ещё и считает такой файл медленнее, чем он
есть. В отчёте, который записывает ретраи, исправление говорит, сколько это было упавших попыток, а
когда в файле один перезапущенный тест, тело которого отчёт сохранил, сообщение печатает, во что он
обошёлся за все попытки. Вычесть попытки нельзя: Vitest меряет перезапущенный тест от первой попытки
до успешной как одну длительность. По той же причине находка `perf-gate-slow-test` на перезапущенном
тесте говорит, что её время покрывает все попытки, а находка `perf-gate-slow-file` считает упавшие
попытки внутри файла. `--fail-on-flaky` делает находку ошибкой и выходит с кодом 1 — так же, как `failOnFlakyTests` в
Playwright и `flaky-result = "fail"` в nextest: ретрай, прячущий настоящую гонку, — это тест, который
упадёт в чужом merge request.

#### `perf-heap` {#perf-heap}

Перечисляет пять файлов, после которых занято больше всего кучи, в мегабайтах, — когда
прогон кучу записал. Голый прогон сам передаёт `--logHeapUsage`; прогону через `--command` нужен
`logHeapUsage: true` в конфигурации, до которой он доходит. Это заметка. Под `isolate: false` число
после файла несёт ещё и все файлы, прошедшие до него в том же воркере. На Vitest 5 `perf` это
разбирает: при разрешённом `isolate: false` каждая дорожка держит один воркер, поэтому он упорядочивает
файлы дорожки по старту и перечисляет, сколько каждый файл **добавил** к куче сверх предыдущего, — пять
самых больших приростов. Это и есть файл, который оставляет память за собой, без догадок. С
включённой изоляцией или на более старом отчёте он, как и раньше, перечисляет кучу после каждого файла.

### Когда голый прогон — не ваша сюита {#when-a-bare-run-is-not-your-suite}

`vitest run` без пути читает конфигурацию из директории, где его запустили, и в множестве
репозиториев этой конфигурации просто нет: сюиту собирает Angular-билдер, таргет Nx или скрипт,
который порождает конфиг на каждый проект. Там голый прогон берёт умолчания Vitest — без `globals`,
без алиасов путей, с `include`, который выметает каждый `*.spec.*` в дереве вместе с результатами
сборки, — и ни один файл не собирается. Замер на одном таком воркспейсе: **1 830 файлов, 29 с
настенного времени, ноль выполненных тел тестов**, и таблица фаз, выглядевшая совершенно правдоподобно
— потому что transform и environment это настоящие секунды, чем бы ни кончились файлы.

`perf` отказывается от обеих половин. До запуска он проверяет, будет ли голый прогон вообще сюитой
этого репозитория — нет корневого `vite(st).config.*` (на Vitest 2 и 3 считается и
`vitest.workspace.*` или `vitest.projects.*`; Vitest 4 такие файлы читать перестал), а скрипт `test`
не вызывает `vitest` сам, — и останавливается, не тратя полминуты. Печатает он один выход: команду для билдера с подставленными
проектом и таргетом, если нашёл таргет unit-test Angular или Nx, а иначе — две строки репортера и
`--command`, который нужно запустить. А отчёт, в котором **ни одно
тело теста не завершилось**, не печатается как измерение ни при каком источнике: код возврата 2 и
строка о том, сколько файлов собрано против того, сколько тел выполнилось.

```bash
npx vitest-auto-spy perf --command 'npm test'                    # померить собственную команду
npx vitest-auto-spy perf --command 'npm test -- {paths:--include=}' --gate
```

`--command` запускает эту строку шелла с `VITEST_AUTO_SPY_PERF_OUT` и
`VITEST_AUTO_SPY_PERF_REPORTER` в окружении. Репортер подключает уже та конфигурация, до которой
команда доходит, — это две строки там, где объявлены её `reporters`:

```ts
const perf = process.env['VITEST_AUTO_SPY_PERF_REPORTER'];

reporters: perf === undefined ? ['default'] : ['default', perf],
```

Репортер не пишет вообще ничего, пока `VITEST_AUTO_SPY_PERF_OUT` не назовёт файл, — поэтому
репозиторий, чей конфиг раннера нельзя переписывать на каждый прогон, может объявить его навсегда и
ничего не платить на прогонах, которые ничего не меряют.

`{paths}` в команде — место, куда подставляются файлы подтверждающего прогона; `{paths:<префикс>}`
ставит флаг перед каждым, что и нужно харнессу, принимающему `--include=<glob>`. Без этого токена
команду нельзя сузить, и гейт говорит об этом прямо, вместо того чтобы перезапускать всю сюиту ради
подтверждения одного файла.

### Гейт {#the-gate}

`--gate` — единственная часть `perf`, которая что-то роняет. Всё остальное, что он печатает, —
совет, а совет не имеет права красить merge request; у гейта обязанность обратная, поэтому каждая
находка в нём должна быть тем, что автор диффа сделал и может отменить. Отсюда три решения, и это
весь дизайн.

**Он судит тела тестов, а не машину.** Из шести фаз `environment`, `prepare`, `setup` и `transform` —
это харнесс: они масштабируются от числа файлов и от CPU, и ни один автор спеки не уменьшит их, написав
код лучше. `import` ещё хуже в атрибуции — в общем воркере первый файл, дотянувшийся до модуля, платит
за всех, так что счёт приходит тому файлу, который первым запустил планировщик. `tests` — единственная
фаза, которая является чьим-то кодом, поэтому бюджеты именно по ней.

**Бюджет файла считается в медианных тестах прогона, а не в миллисекундах.** Медианный тест — это
медиана по файлам, закончившим хотя бы один тест, от суммы тел файла, делённой на число его тестов.
Файл выходит за бюджет, когда сумма его тел больше наибольшего из трёх чисел: `--max-file-tests`
(2 000) × медианный тест, `--factor` (10) × медианный тест на каждый тест файла и `--max-file-ms`
(5 000). Первые два едут вместе с машиной — загруженный раннер поднимает каждый тест, — поэтому вердикт
одинаков на ноутбуке и на раннере в девять раз медленнее. Третье — порог, который может только
пощадить файл, но никогда не обвинить. Равномерно медленная сюита не даст ни одной находки по файлам —
выброса в ней нет, — и для этого случая есть `--max-wall-ms`, выключенный, пока не попросят:
настенное время это свойство раннера.

Раньше правило было `--max-file-ms` **и** `--factor` × медианный **файл**, и на потребительской сюите
из 2 023 файлов оно судило размер файла и скорость раннера, а не медленность. Медианный файл там —
8,9 мс и пять тестов, так что десять таких медиан и близко не подходили к порогу в 5 с, и решал один
порог: тот же отчёт, проигранный с замедлением ×1, ×3, ×6 и ×9, отмечал 0, 4, 8 и 19 файлов, среди них
сервисную спеку на 209 тестов по 5 мс, а одна спека компонента в одиночку мерилась 0,96 с на ноутбуке и
5,62 с в CI — зелёная там и красная здесь. Разбиение файла на два тоже проходило гейт. По правилу на
тест тот же отчёт не отмечает ничего ни при каком замедлении; самый тяжёлый файл набирает 742 медианных
теста из 2 000 нужных.

**Ничто не падает по одному измерению.** Каждый кандидат перемеряется в одиночку, прежде чем ему
позволят что-то уронить, — той же командой `--command`, из которой пришло первое чтение. Файл, который
не медленный, когда машина принадлежит только ему, помечается как **не воспроизвелось** — это `info`,
а не находка, — потому что «твой тест медленный» и «твой тест делил воркер ещё с четырьмя» это разные
утверждения, а гейт, который их не различает, выключают за неделю. Там, где подтверждение невозможно,
находки становятся предупреждениями и ничего не роняют, если только `--no-confirm` не скажет, что
одного чтения достаточно.

**Подтверждённая находка говорит, почему.** Подтверждающий прогон и так гоняет подозреваемые файлы в
одиночку, поэтому причина меряется там же: `perf` выставляет `VITEST_AUTO_SPY_PERF_PROFILE`, репортёр
только на этот прогон добавляет `dist/perf-profiler.js` в `setupFiles` каждого проекта, а профилировщик
снимает CPU-профиль каждого файла через собственную сессию `node:inspector` воркера, с шагом 500 мкс.
`--cpu-prof` тут ничего не записывает: воркер пула завершают, а не дают ему выйти, а Node пишет такой
профиль на выходе. Тот же прогон записывает все тела тестов этих файлов, а не только те, что дольше
100 мс, чтобы находка могла назвать самые медленные. Под подтверждённой находкой гейт печатает самые
медленные тесты файла, долю времени в хуках против тел тестов и функции, на которые ушло время, — в
спеке, в коде проекта под ней, по пакетам и самые горячие по отдельности:

В терминале карточка цветная: числа сверх бюджета и тела тестов дольше `--max-test-ms` красные, остальные замеры жёлтые, у каждой доли полоска, которая желтеет от 20 % и краснеет от 40 %, рамка приглушена. **Likely cause** — не больше двух предложений, и каждое срабатывает по правилу, которое в нём и названо: больше половины времени в хуках, один тест втрое дольше следующего, пакет DOM или фреймворка больше 20 %, сборка мусора больше 10 %; если ни одно не сработало, блока нет. Первая строка находки прежняя, а все строки карточки с отступом, так что обвязка, собирающая находку как строку `error` и строки с отступом под ней, передаёт карточку целиком. С `NO_COLOR` она печатается без цвета.

**На Angular-спеке карточка называет собственные затраты Angular.** Строка `angular` под хуками
раскладывает профиль на настройку TestBed (`configureTestingModule`, `compileComponents`,
`resetTestingModule`, вызовы `override*`), создание компонента, change detection (`refreshView`),
JIT-компиляцию (время внутри `@angular/compiler`) и вычисление стилей (`getComputedStyle` в jsdom).
Фреймы, которые есть только у Angular, узнаются откуда бы они ни пришли: `@angular/build:unit-test`
собирает пакеты в чанки, и пути `node_modules` там уже нет. Эту строку читают ещё четыре вероятные
причины, и они идут раньше общих: настройка и создание через TestBed вместе от 30 % (она заменяет
фразу про хуки, потому что говорит, чем эти хуки заняты), JIT-компилятор от 15 %, change detection от
30 %, вычисление стилей от 15 %.

```
       │ hooks        ███████████░░░░░░░░░ 54%   test bodies 46%
       │ angular      TestBed set-up 31%  ·  change detection 22%  ·  component creation 9%
       ├─ slowest imports · with everything under them ────────────────
       │   1.24s  @angular/material
       │   310ms  src/app/player/player.component.ts
       ├─ likely cause ────────────────────────────────────────────────
       │ TestBed rebuilds the testing module and the component for every test: 40% is TestBed set-up and component creation. (…)
```

**Самые медленные импорты берутся у Vitest.** На Vitest 4.1 и новее измеряемый прогон запрашивает
десять самых медленных импортов каждого файла, когда конфиг не задаёт
`experimental.importDurations.limit`, а подтверждающий прогон поднимает меньший лимит только для себя,
так что конфиг не нужен. Карточка перечисляет самые тяжёлые прямые
импорты спеки вместе со всем, что они за собой потянули: пакет — по имени, модуль — по пути. Модуль,
который первым импортировал другой файл, оплачен там и в список не попадает. На более старом Vitest
или в харнессе, где спека — собранный чанк, раздела нет.

Каждая доля — от просэмплированного времени без тиков простоя, и функция считается один раз на сэмпл,
как бы глубоко она ни рекурсировала, поэтому включающие строки в сумме дают больше 100 % — `setUpWith`
содержит change detection под собой. Профиль, который не удалось прочитать, оставляет находку без этих
строк, а не роняет что-то.

```
$ npx vitest-auto-spy perf --json out/perf.json --gate --command 'npm test -- {paths:--include=}'

perf gate: re-measuring 1 file on its own before failing anything.

perf gate verdict — 1 judged, 1 fails the run
  kind  first  again  budget  verdict    where
  test  4.31s  4.05s   1.00s  confirmed  libs/a/src/lib/thing.spec.ts › Thing > waits for the retry

error  perf-gate-slow-test libs/a/src/lib/thing.spec.ts
       `Thing > waits for the retry` spent 4.31s in its body, over the 1.00s budget
       (--max-test-ms 1000). Re-measured on its own: 4.05s, still over budget.
       → A test body over a second is usually waiting rather than working: a timer nobody advanced
         (`vi.useFakeTimers()` and `vi.advanceTimersByTime`), a real request or a real animation
         frame, an `await` on something that settles on a schedule, or a fixture rebuilt from
         scratch in every case.

```

Гейт отказывается судить прогон, который не прошёл: упавший тест меряется до своего таймаута, а 30 с
таймаута выглядят ровно как 30 с медленного кода. И он никогда не судит файл вне `--gate-only`, если
тот задан, — CI может передать спеки, которых коснулась ветка, а медиана всё равно берётся по всему
прогону.

**Коды возврата.** `0` — отчёт прочитан и ничего не упало. `1` — упал гейт, и это единственное, что
значит «сюита вышла за бюджет». `2` — судить было нечего: нет Vitest, нет отчёта, файл `--json` не
парсится, в прогоне не выполнилось ни одного тела теста или под `--gate` пришла красная либо
незаконченная сюита.

### Две таблицы и шарды, из которых они слиты {#the-two-tables-and-the-shards-they-were-merged-from}

В самом низу отчёта, после находок, `perf` один раз называет бюджеты — на тело теста и три, которым
подчиняются тела файла, с тем, сколько `--max-file-tests` стоит в этом прогоне, — и печатает то, что
уронило бы `--gate`, и ничего больше: **файлы сверх бюджета** — с `time`, `budget`, который превышен,
`over` (одно, делённое на другое), `tests`, `ms/test`, `×median` и, если `--baseline` называет
закоммиченный baseline, `vs base` — во сколько раз файл сейчас занимает больше своей записанной доли
прогона, или `new`, — и **тела тестов сверх бюджета**, то есть не короче `--max-test-ms`. Заголовок
каждой таблицы считает все строки сверх бюджета и говорит, когда `--top` часть отрезал. Флаги
бюджетов рисуют таблицы и без `--gate`, поэтому отчёт и гейт по одной сюите согласны в том, что за
бюджетом. Строки берутся из тех же функций, по
которым судит гейт, и `--gate-only` сужает их так же, поэтому таблица и вердикт под ней не могут
разойтись. Раньше это были десять самых дорогих файлов и тел любого прогона, и на потребительской сюите
из 2 023 файлов наверху списка стояли спека компонента на 234 теста по 8,6 мс и сервисная спека на
209 тестов по 5 мс — самые большие файлы, которые никому не нужно открывать. Когда за бюджетом ничего
нет, об этом говорит одна строка; под `--gate` её заменяет собственное «всё чисто» гейта. `--top`
ограничивает число строк, `--top 0` выключает обе таблицы.

Числа идут первыми и выровнены вправо, путь — последним и целиком, поэтому и в логе CI на 80 колонок
виден путь, который можно скопировать; раньше таблицы резали его посередине ради раскладки на 140
колонок. У тела теста два имени — файл и его собственное, — поэтому таблица тел печатает файл один раз,
а тела под ним. Время каждой строки идёт красным, заголовки — приглушённым. Цвет включён в терминале и
выключен в пайпе и в файле, если `FORCE_COLOR` не просит обратного; `NO_COLOR`, `FORCE_COLOR=0` и
`TERM=dumb` выключают его везде. Обвязка, которая перехватывает этот вывод и перекрашивает его
построчно, поэтому получает простой текст.

```
files over budget — 2 of 2015; the gate re-measures these and fails on them
   time  budget  over  tests  ms/test  ×median  vs base  file
  1.90s   634ms  3.0×    101     19ms     9.0×     0.8×  apps/web/src/app/catalog/item-card.component.spec.ts
  1.43s   418ms  3.4×      5    285ms     136×      new  apps/web/src/app/checkout/receipt-page.factory.spec.ts
```

Под `--gate` за подтверждающим проходом идёт **таблица вердикта**: по строке на кандидата — `kind`
(`test`, `file`, `grew`, `run`), первый замер `first`, повторный отдельно `again`, `budget` и
`verdict` — `confirmed`, `not reproduced`, `unconfirmed` (перемерить было нечем), `single reading`
(`--no-confirm`) или `over budget` для бюджета на весь прогон. Карточка под подтверждённой находкой
сравнивает кандидата с **его собственным** бюджетом; раньше и для медленного тела, и для регрессии
против baseline она показывала бюджет суммы файла и печатала «0.1× over» над находкой, которая только
что уронила прогон. Весь отчёт заканчивается одной строкой-итогом — за советы, гейт и baseline вместе.

`--format json` печатает тот же прогон одним документом в stdout — `run` (файлы, тесты, миллисекунды
на часах и CPU, обе медианы, фазы и `slowestFiles` — `--top` самых медленных файлов, по умолчанию 10,
у каждого путь от корня репозитория, миллисекунды, число тестов и миллисекунды по фазам), `budgets`, `gate` (`status`, `confirmation` и строки вердикта),
`tally` и все находки — и уводит вывод запускаемой сюиты в stderr, чтобы stdout оставался разбираемым.
Прогон, который нечего судить, всё равно печатает документ — с `error` и `run: null`.

Когда в отчёте они есть, документ добавляет `run.vitest` (версия Vitest), `run.partial`, `run.config`
(разрешённые опции и `provided`), `run.startup` (`{ ms, workers }`) и `run.lanes`
(`{ lanes, spanMs, busy, longPole?: { file, aloneMs } }`). На Vitest 5 каждый `slowestFiles[].phases`
ещё и несёт `transform`, а `import` и `setup` — за его вычетом, как в таблице фаз. Markdown-отчёт
называет версию Vitest в итоговой строке, печатает под ней строку дорожек и добавляет колонку
`Transform` в таблицу самых медленных файлов. Для отчёта без этих данных ничего из этого не
появляется, и отчёт старого Vitest печатает ровно то же, что и раньше. Формат отчёта — версия 4.

Шардированный пайплайн пишет по отчёту на джобу, и правило, которое сравнивает файл с **медианой
своего прогона**, сравнивает его тогда с четвертью улик. `--json` принимает каталог или шаблон и
сливает их:

```bash
npx vitest-auto-spy perf --json 'coverage/**/perf-*.json' --gate
```

Время transform складывается, настенное — **нет** (шарды шли одновременно, поэтому у слияния оно
максимальное из них), версия берётся по беднейшему входу, а файл, измеренный в двух шардах,
сохраняет более медленное измерение и называется в отчёте. Слияние ещё и переносит все отчёты на
один корень, и это не косметика: GitLab клонирует каждую джобу в свой каталог сборки, четыре отчёта
не сходятся в том, где лежит репозиторий, и слияние «в лоб» молча выбросило бы файлы трёх шардов.

### Baseline — то, чего один прогон увидеть не может {#the-baseline-—-catching-what-a-single-run-cannot-see}

Гейт по сегодняшним числам слеп к регрессии, которая на самом деле накапливается: файл, который
месяц назад шёл 300 мс, а сегодня идёт 900 мс, и всю дорогу — под каждым бюджетом, по одному
`beforeEach` за раз. `--baseline` закрывает это зафиксированной записью:

```bash
npx vitest-auto-spy perf --json out/perf.json --update-baseline    # записать; файл коммитится
npx vitest-auto-spy perf --json out/perf.json --gate --baseline perf-baseline.json
```

**Записывается отношение, а не миллисекунды**, и в этом всё дело. Baseline пишется на чьём-то
ноутбуке, а сравнивается на раннере, который в два-пять раз медленнее и делит хост с тремя другими
джобами; в миллисекундах каждый файл оказался бы «в 1,8 раза хуже», и ратчет отчитывался бы о железе.
Хранится доля файла от медианного файла его собственного прогона — медленная машина поднимает и
числитель, и знаменатель. Файл, который был 3× медианы, а стал 9×, стал таким из-за репозитория.

Регрессия становится обычным кандидатом гейта: тот же подтверждающий прогон перемеряет её в
одиночку, а в сообщении стоят миллисекунды, которых эта доля стоит **в этом** прогоне, — число на
экране можно сверить с часами. Файлы, которых baseline не знает, — новые; файлы, которые он знает, а
прогон не измерил, — чужой шард; ни то ни другое не находка, оба печатаются как дрейф.
`--baseline-factor` (2) и `--baseline-floor-ms` (500) — два порога.

**Путь `.jsonl` — это история, а не снимок.** Один зафиксированный снимок — один замер, и файл, чья доля
в прогоне гуляет между 2× и 5× медианы, в обычный день задевает храповик на 2×. Укажите в `--baseline`
файл JSON Lines, и `--update-baseline` будет дописывать по строке на прогон — те же доли файлов, время
записи и коммит из `CI_COMMIT_SHA` или `GITHUB_SHA` — и хранить последние 30. Файл регрессирует,
только когда его доля одновременно больше `--baseline-factor` × его **среднего** по записанным прогонам
и больше **каждой** доли, с которой он был записан, — это правило Datadog Test Optimization применяет
относительно основной ветки; до трёх записанных прогонов файл регрессировать не может вовсе. Коммитить
файл не нужно: держите его в кэше CI, записывайте с основной ветки, судите на merge request.

```yaml
perf:
  cache:
    key: perf-history
    paths: [perf-history.jsonl]
  script:
    - npx vitest-auto-spy perf --json out/perf.json --gate --baseline perf-history.jsonl
    - if [ "$CI_COMMIT_BRANCH" = "$CI_DEFAULT_BRANCH" ]; then npx vitest-auto-spy perf --json out/perf.json --baseline perf-history.jsonl --update-baseline; fi
```

### Флаги {#flags}

| Флаг                  | Что делает                                                                                                                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--cwd <dir>`         | Работать в другой директории вместо текущей (общий с остальными командами)                                                                                                                      |
| `--json <path>`       | Прочитать отчёт, записанный более ранним прогоном с `--out`, вместо повторного запуска Vitest                                                                                                   |
| `--out <path>`        | Сохранить JSON-отчёт по этому пути. Без него отчёт пишется в `node_modules/.cache` и удаляется, как только его прочитали                                                                        |
| `--command <c>`       | Померить эту строку шелла вместо прямого запуска Vitest; `{paths}` / `{paths:<префикс>}` принимают файлы подтверждающего прогона                                                                |
| `--gate`              | Уронить прогон на подтверждённом бюджете. Код возврата 1                                                                                                                                        |
| `--max-test-ms`       | Бюджет одного тела теста. По умолчанию 1000; ничего меньше 100 мс в отчёт не пишется, это и есть порог                                                                                          |
| `--max-file-ms`       | Файл, чьи тела в сумме меньше этого, никогда не находка. По умолчанию 5000                                                                                                                      |
| `--max-file-tests`    | Сколько медианных тестов прогона должна набрать сумма тел файла. По умолчанию 2000                                                                                                              |
| `--factor <n>`        | Во сколько раз один тест файла должен в среднем стоить дороже медианного теста прогона. По умолчанию 10 — считается в самом прогоне, поэтому не зависит от машины                               |
| `--max-wall-ms`       | Бюджет всего прогона. По умолчанию выключен: настенное время — свойство раннера, за вас его никто не выведет                                                                                    |
| `--gate-only`         | Пути через запятую, которые гейту разрешено судить; медиана всё равно берётся по всему прогону                                                                                                  |
| `--no-confirm`        | Пропустить подтверждающий прогон и судить по одному чтению                                                                                                                                      |
| `--baseline <p>`      | Сравнить с зафиксированным baseline и уронить на том, что выросло; хранится как отношение к медианному файлу прогона, поэтому медленная машина — не регрессия. Путь `.jsonl` — история прогонов |
| `--update-baseline`   | Записать этот прогон в baseline вместо того, чтобы судить его, или дописать в историю `.jsonl`, которая хранит 30 прогонов. По умолчанию `perf-baseline.json`                                   |
| `--fail-on-flaky`     | Тест, прошедший только после ретрая, роняет прогон, выход 1. Без флага — предупреждение                                                                                                         |
| `--code-quality <p>`  | Дополнительно записать находки отчётом GitLab Code Quality. Общий с `doctor`                                                                                                                    |
| `--baseline-factor`   | Во сколько раз файл должен превысить свою записанную долю, чтобы это была регрессия. По умолчанию 2                                                                                             |
| `--baseline-floor-ms` | Абсолютный порог, ниже которого выросший файл всё ещё шум. По умолчанию 500                                                                                                                     |
| `--top <n>`           | Сколько строк в таблицах «файлы сверх бюджета» и «тела тестов сверх бюджета»; `0` выключает их. По умолчанию 10                                                                                 |
| `--format json`       | Один JSON-документ в stdout вместо текстового отчёта; собственный вывод сюиты уходит в stderr. Общий с `doctor`                                                                                 |
| `--min-severity`      | Самые тихие находки, которые попадают в отчёт: `error`, `warning` или `info` (по умолчанию). Строка-итог всё равно считает скрытые, и код возврата не меняется. Любое другое значение — код 2   |

Позиционный путь (`npx vitest-auto-spy perf src/cli`) передаётся в Vitest как фильтр по файлам; без
него `perf` меряет всю сюиту.

## `init` — указатель, который агент действительно читает {#init-—-the-pointer-an-agent-actually-reads}

Ни в один контекст инструкций кодового агента нет пути без настройки. Каждый инструмент ищет правила
по фиксированному набору путей в корне репозитория или в dot-директориях, и **ни один не сканирует
зависимости** — ни скилл, ни `AGENTS.md`, лежащие внутри тарбола этого пакета, не находятся
автоматически. Что-то в репозитории должно один раз на них показать.

```bash
npx vitest-auto-spy init
```

**Ярус 1, пишется всегда** — три корневых файла покрывают всё поле:

| Файл                                      | Кто читает                                                                                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AGENTS.md`                               | Codex, Cursor, Copilot, Cline, Windsurf, Zed, OpenCode, Qwen, Roo, Junie, Aider                                                                                  |
| `CLAUDE.md`                               | Claude Code, а также GLM / Kimi, работающие внутри него                                                                                                          |
| `GEMINI.md`                               | Gemini CLI, который по умолчанию не читает `AGENTS.md`                                                                                                           |
| `.claude/skills/vitest-auto-spy/SKILL.md` | Claude Code — заглушка, чей frontmatter скопирован дословно из поставляемого скилла, а тело только показывает на `node_modules`, так что протухнуть оно не может |

**Ярус 2, только когда собственная директория инструмента уже существует**, и с ограничением по
глобу, чтобы задача не про тесты не платила за это контекстом: `.cursor/rules/`,
`.github/instructions/`, `.windsurf/rules/`, `.devin/rules/`, `.clinerules/`, `.roo/rules/`.

**Никогда не создаётся:** `.rules`, `.cursorrules`, `.windsurfrules` или `.clinerules` в виде
_файла_. Zed разрешает инструкции по принципу «побеждает первое совпадение» по упорядоченному
списку, который заканчивается `AGENTS.md`, так что создание любого из них молча затеняет инструкции
всего проекта. Если такой файл уже есть, `init` дописывает в него, а не оставляет его протухшим.

### Почему команда, а не сниппет {#why-a-command-rather-than-the-snippet}

[Сниппет для копипасты](/ru/agents) вынужден перечислять каждый раннер и каждый адаптер, и половина
его для любого конкретного репозитория ложна. `init` читает `package.json` потребителя и конфиг
тестов и пишет только истинную половину — какой subpath подходит этому раннеру, какой адаптер
подходит фреймворку, реальный путь к setup-файлу, которому нужен `import 'vitest-auto-spy/rxjs'`, — и
целиком опускает пункт про rxjs, когда rxjs не установлен.

### Идемпотентен по построению {#idempotent-by-construction}

Всё пишется между маркерами:

```md
<!-- vitest-auto-spy:begin v=3.7.0 sha=90452bea -->

…

<!-- vitest-auto-spy:end -->
```

Текст между ними перегенерируется целиком на каждом прогоне; текст снаружи не читается и никогда не
переформатируется. Запуск `init` после обновления — это либо no-op, либо диф в один хунк. `CLAUDE.md`,
который является симлинком на `AGENTS.md` или уже содержит строку импорта `@AGENTS.md`, остаётся
нетронутым — оба способа держат один файл инструкций, и запись через любой из них продублировала бы
блок.

Файл по пути, которым владеет `init`, но без маркеров, написан вручную, и `init` его никогда не
перезаписывает. Один случай он не пропускает молча, а сообщает о нём: `.claude/skills/vitest-auto-spy/SKILL.md`
с `name: vitest-auto-spy` во frontmatter — это копия поставляемого скилла, застывшая на той версии,
с которой её скопировали. `init` помечает его как `stale` и предлагает удалить файл и запустить `init`
ещё раз — тогда на его месте появится указатель; `init --check` на нём выходит с кодом 1.

Блок сознательно держат меньше 1,6 кБ. Codex ограничивает всю цепочку `AGENTS.md` от корня до cwd
значением `project_doc_max_bytes` (по умолчанию 32 768 байт) и молча обрезает всё сверх него, так что
`init` предупреждает, когда файл, в который он дописал, эту границу перешёл.

### Флаги {#flags-1}

| Флаг              | Команда    | Что делает                                                               |
| ----------------- | ---------- | ------------------------------------------------------------------------ |
| `--cwd <dir>`     | все четыре | Работать в другой директории                                             |
| `--check`         | `init`     | Ничего не писать; выйти с 1, если блока нет или он устарел. Форма для CI |
| `--dry-run`       | `init`     | Напечатать, что изменилось бы, и ничего не писать                        |
| `--uninstall`     | `init`     | Убрать управляемые блоки и удалить файлы, созданные `init`               |
| `-h`, `--help`    | все четыре | Экран справки                                                            |
| `-v`, `--version` | все четыре | Установленная версия                                                     |

Собственные флаги `perf` — `--json`, `--out` — в [его разделе выше](#perf-—-where-the-cpu-time-actually-goes).
Собственные флаги кодмода — `--write`, `--verify`, `--only`, `--skip`, `--list` — на
[его странице](/ru/utilities/codemod#flags).

Каждая команда принимает флаги своей таблицы плюс `--cwd`, `--help` и `--version` и ничего больше.
Флаг, которого нет ни в одной из них, останавливает команду с кодом 2 до того, как она прочитает или
запишет файл, и подсказывает флаг, который, скорее всего, имелся в виду, или печатает те, что она
принимает. Флаг-значение, после которого ничего нет (`--cwd --check`), и числовой флаг со словом или
отрицательным числом останавливают её так же.

`init --check` в CI устроен так же, как `llms:check` в этом репозитории: он падает, когда блок на
диске — не тот блок, который написала бы установленная версия, то есть ровно тогда, когда обновление
изменило совет.

**`--check` сравнивает блок, а не штамп версии в его маркере.** Это разные вопросы, и только один из
них касается потребителя: обновление, которое меняет совет, — работа, а обновление, которое меняет
лишь `v=` в маркере, — нет, и побайтовое сравнение делало каждый релиз пакета красным шагом в
репозитории, где инструкции не сдвинулись ни на слово. Обычный `init` штамп обновляет. Такой файл под
`--check` — `unchanged`, под `--dry-run` — `updated`, и оба объясняют это в пояснении: _only the
version stamp differs_.

## В CI {#in-ci}

```yaml
- run: npx vitest-auto-spy doctor
- run: npx vitest-auto-spy init --check
- run: npx vitest-auto-spy codemod --verify # на сюите, которая уже переехала
- run: npx vitest-auto-spy perf --out perf.json # всегда выходит с 0 — не ворота, а артефакт на память
- run: npx vitest-auto-spy perf --gate # выход 1 на подтверждённом медленном файле или тесте, с причиной под ним
- run: npx vitest-auto-spy doctor --code-quality gl-code-quality.json # те же находки в виджете merge request GitLab
```

Ни одной из них не нужны сеть, конфиг-файл или токен. CLI поставляется вместе с пакетом, не имеет
собственных рантайм-зависимостей и является единственной его частью, которой позволено трогать
`node:fs`, — этот инвариант репозиторий проверяет на каждой сборке.
