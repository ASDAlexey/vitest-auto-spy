# ESLint-плагин

```js
// eslint.config.js
import autoSpy from 'vitest-auto-spy/eslint-plugin';

export default [{ files: ['**/*.spec.ts'], ...autoSpy.configs.recommended }];
```

Ограничьте его файлами спек сами: каждое правило — про тестовый код, а `Object.defineProperty` или
объект из `vi.fn()` в прикладном коде совершенно уместны.

::: warning Только flat config
Легаси-форма `.eslintrc` с `plugins: ['…']` разрешает имена плагинов в пакеты `eslint-plugin-*`, а
subpath-экспорт этого пакета таким пакетом быть не может.
:::

**Как устроена эта страница.** [Как подключить](#adding-it-to-your-project) — четыре вещи, нужные
первому конфигу. [Какие касаются вас](#which-of-the-twenty-apply-to-you) отвечает на вопрос, который
задаёт проект только на Vitest: четыре из двадцати — про диалект, на котором вы, возможно, не
говорите. [Правила](#rules) — справочная таблица в пяти группах. [Настройка](#tuning-it-for-your-project) —
все ручки, включая три правила, которые могут сработать на корректном коде. Всё после этого — _почему_:
по разделу на правило, на случай, когда сообщение уже прилетело и хочется понять, от чего оно вас
уберегло.

## Как подключить его к проекту {#adding-it-to-your-project}

Ставить нечего — плагин это subpath пакета, который у вас уже есть, так что он всегда той же версии,
что и API, который он советует.

### 1. Блок конфигурации {#_1-the-config-block}

`configs.recommended` — обычный объект с двумя ключами, `plugins` и `rules`, и его раскрытие через
спред — вся проводка, которая тут есть. Кладите его **после** остальных конфигов, чтобы выжили именно
его уровни серьёзности:

```js
// eslint.config.js
import tseslint from 'typescript-eslint';
import autoSpy from 'vitest-auto-spy/eslint-plugin';

export default [
  ...tseslint.configs.recommended,
  {
    files: ['**/*.spec.ts', '**/*.test.ts'],
    ...autoSpy.configs.recommended,
  },
];
```

### 2. Глоб `files` не опционален {#_2-the-files-glob-is-not-optional}

Глоба по умолчанию нет, и это сознательно: только вы знаете, где живут ваши спеки. Ошибки в две
стороны выглядят совершенно по-разному: слишком **узкий** — и плагин молча бездействует (самый частый
вопрос в поддержку, а `npx eslint --print-config path/to/a.spec.ts` решает его одной командой);
слишком **широкий** — и `no-object-define-property` начинает срабатывать на прикладном коде, который
имеет полное право его вызывать.

Типичные варианты:

```js
files: ['**/*.spec.ts'],                                  // Angular, раскладка эпохи Karma
files: ['**/*.test.ts', '**/*.test.tsx'],                 // React / Vue / Node
files: ['**/*.{spec,test}.{ts,tsx}', '**/test/**/*.ts'],  // и то и другое плюс папка с тестами
```

В монорепозитории один блок в корне покрывает каждый пакет, пока глоб не привязан к началу пути:
`'**/*.spec.ts'` спокойно матчит `packages/*/src/**`. Второй блок добавляйте только там, где спекам
одного пакета нужны другие уровни серьёзности.

### 3. Информация о типах не нужна {#_3-no-type-information-required}

Все правила синтаксические: они читают собственный AST файла и никогда не спрашивают тайпчекер. Так что
плагин работает при незаданном `parserOptions.project`, ничего заметного ко времени линта не добавляет
и не требует, чтобы ваши спеки были в `tsconfig`, — а это важно в репозиториях, где их там нет.

Плата за это — честное ограничение [трёх правил, которые могут сработать на корректном
коде](#the-three-rules-that-can-report-on-correct-code): чего правило не видит в одном файле, того оно
и не знает.

### 4. Как выглядит первый прогон {#_4-what-the-first-run-looks-like}

Каждое правило — `error`, так что на существующей сюите первый прогон, скорее всего, будет красным —
и это смысл такого умолчания, а не ошибка настройки. Первый заход укорачивают две вещи:

```bash
npx eslint . --fix          # prefer-as-spy, no-mocked-for-spy и prefer-native-spy-api чинят себя сами
npx eslint . --format stylish | tail -30   # в сводке видно, какое правило доминирует
```

Всё, что осталось, — это либо настоящая находка, либо правило, которое вы пока не готовы включать в
силу. Ответы на оба случая ниже.

## Какие из двадцати касаются вас {#which-of-the-twenty-apply-to-you}

Резонный вопрос, если вы пришли сразу на Vitest и не написали ни строчки на Jasmine: **четыре из этих
правил — про диалект, на котором вы не говорите.** Они всё равно включены, и причина не в принципе, а
в том, что на вашем коде они сработать не могут.

| Вы                                              | Что плагин делает для вас                                                                                    |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| пишете на Vitest, никогда не трогали Jasmine или Jest | пятнадцать основных правил работают; **четыре jasmine-правила бездействуют** — оставьте их и никогда не увидите |
| переезжаете с `jest-auto-spies` / Jest          | работу делают основные правила, больше всего — `no-done-callback` и `prefer-as-spy`                            |
| переезжаете с `jasmine-auto-spies`              | все двадцать, с `prefer-native-spy-api` в `'off'`, пока мост не убран                                          |

### Если вы никогда не пользовались Jasmine {#if-you-never-used-jasmine}

Каждое из четырёх цепляется за синтаксис, которого в Vitest-сюите нет, так что рапортовать им не о
чем:

| Правило                           | Цепляется за                                                                     | В вашей сюите                                                                                                        |
| --------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `no-jasmine-globals`              | `jasmine.*` и голые глобалы `spyOn(`, `spyOnProperty(`, `fail(`, `pending(`      | вы пишете `vi.spyOn` и `expect.fail`; голые формы под Vitest — это `ReferenceError`, то есть их не существует         |
| `jasmine-namespace-without-entry` | `.and` / `.calls` / `.withArgs` **на спае, построенном этой библиотекой**        | вы пишете `.mockReturnValue`, `.mock.calls` и `calledWith`                                                            |
| `no-save-arguments-by-value`      | `spy.calls.saveArgumentsByValue()`                                               | собственный API jasmine; ни в одной Vitest-сюите такого вызова нет                                                    |
| `prefer-native-spy-api`           | те же namespace'ы `.and` / `.calls`                                              | то же, что выше                                                                                                      |

Так что выключать их можно, но выигрыша это не даёт никакого измеримого — правило без подходящего узла
не делает ничего сверх обхода AST, который и так делает каждое правило. Если всё-таки хочется конфиг
покороче:

```js
export default [
  {
    files: ['**/*.spec.ts'],
    ...autoSpy.configs.recommended,
    rules: {
      ...autoSpy.configs.recommended.rules,
      // мы никогда не пользовались jasmine; этим четырём тут нечего сказать
      'vitest-auto-spy/no-jasmine-globals': 'off',
      'vitest-auto-spy/jasmine-namespace-without-entry': 'off',
      'vitest-auto-spy/no-save-arguments-by-value': 'off',
      'vitest-auto-spy/prefer-native-spy-api': 'off',
    },
  },
];
```

::: warning Одно из них всё-таки срабатывало и на Vitest-сюите — починено в 4.0.0
`jasmine-namespace-without-entry` матчил `spy.mock.calls[0]`, `spy.mock.calls.length` и
`spy.mock.calls[0]?.[0]` — то есть то, как каждая Vitest-сюита читает записанные аргументы. Член зовётся
`calls`, `[0]` делает чтение _сквозным_, а цепочка спускается к одной из фабрик этой библиотеки — все три
условия правила выполнены. Голый `spy.mock.calls` проходил, а `spy.mock.calls[0]` рапортовался — разницу
не объяснило бы никакое сообщение, и на уровне `warn` за этим никто не шёл. Теперь правило отказывается
от любого namespace, висящего на `.mock`: это бухгалтерия раннера, а не jasmine.
:::

### Если вы приходите из Jest {#if-you-are-coming-from-jest}

Отдельного набора правил для Jest нет, потому что бо́льшая часть того, что Jest-сюите надо разучиться
делать, уже в основных пятнадцати — вот те, что несут переезд на себе:

| Правило                        | Что ловит в Jest-сюите                                                                                                                                                                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `no-done-callback`             | `it('x', (done) => …)`. Vitest передаёт туда вызываемый `TestContext`, так что `done()` бросает — а там, где он стоит в конце колбэка, тест [проходит, выполнив почти ничего из себя](#no-done-callback-%E2%80%94-what-the-first-parameter-actually-is)      |
| `prefer-as-spy`                | `TestBed.inject(X) as Spy<X>`, написанное по разу на дубль в `jest-auto-spies`-сюите и дающее `TS2352` в этой библиотеке — [самая частая ошибка компиляции у переехавшей Angular-сюиты](/ru/migrating#reading-a-spy-back-out-of-the-container)                |
| `no-mocked-for-spy`            | объявления `Mocked<T>`, требующие приватных полей, которых у спая нет                                                                                                                                                                                          |
| `no-shared-module-level-mock`  | экспортированная фикстура `{ save: jest.fn() }` — один объект на **воркер** при `isolate: false`, а не один на тест                                                                                                                                            |
| `prefer-create-spy-from-class` | дубль в виде объекта из `fn()`-ов, который расходится с классом в тот день, когда у класса появляется метод                                                                                                                                                    |
| `no-floating-assertion`        | `expect()` в `.then()`, которого никто не дождался                                                                                                                                                                                                             |

`no-jasmine-globals` стоит оставить включённым и здесь, и не по той причине, которую подсказывает имя:
Jest работал на **jest-jasmine2** вплоть до Jest 27, а тот раннер ставил `spyOn`, `fail` и `pending`
глобалами — так что сюита, достаточно старая, чтобы предшествовать `jest-circus`, вполне может их
содержать. Опасен здесь `spyOn`: у jasmine он ставит заглушку, `vi.spyOn` вызывает настоящий метод, так
что переименование компилируется, спека выполняется, и проверяемый код начинает по-настоящему
разговаривать со своим коллаборатором.

Массовая правка — это команда, а не проход линтера: `npx vitest-auto-spy codemod --from jest`
(`--from jasmine` для другого диалекта, а дефолтный `auto` читает каждый файл и применяет тот набор,
который этому файлу нужен). См. [Переезд с jest-auto-spies](/ru/migrating).

### Если вы приходите из Jasmine {#if-you-are-coming-from-jasmine}

Касаются все двадцать, а четыре из последней группы написаны прямо для вас. Два — чистая диагностика:
`no-jasmine-globals` и `no-save-arguments-by-value` называют молчаливые изменения поведения, которые
переживают переименование, — а `jasmine-namespace-without-entry` ловит спай, построенный до того, как
поставили слой совместимости. Четвёртое, `prefer-native-spy-api`, рапортует про сам мост, так что это
единственная строка конфига, которую хочет переезд, пока сюита не позеленела:

```js
'vitest-auto-spy/prefer-native-spy-api': 'off', // удалите это на последней миле
```

Массовая правка — `npx vitest-auto-spy codemod --from jasmine`, который делает то, что правило
отказывается автофиксить. См. [Переезд с jasmine-auto-spies](/ru/migrating-jasmine).

## Правила {#rules}

Каждое правило — `error`. До 4.0.0 эта таблица была смесью `error` / `warn` / `off`, то есть плагин
решал, насколько сильно каждому проекту не всё равно; `warn`, который никто не читает, — это `off` с
дополнительным выводом, а какие находки блокируют мердж, решает проект, а не библиотека. Понизить одно
правило — [одна строка](#turn-one-rule-down).

Колонка **Без него** — это то, что делает прогон, когда правила нет, и именно из-за неё список стоит
читать, а не проглядывать: больше половины из них защищают от теста, который _зелёный и неправильный_,
а это единственный режим отказа, о котором сюита не может отчитаться сама. Одиннадцать из них
[измерены](#measured-what-each-rule-is-worth); остальные вычитаны из исходников и помечены _(по
построению)_.

### Ассерты, которые никогда не выполняются {#assertions-that-never-run}

Тест проходит, потому что до ассерта не дошли — поток промолчал, промис никто не дождался, колбэк
вернулся первым.

| Правило                                                                                         | На что срабатывает                                                                            | Правка   | Без него |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------- | :------: |
| [`no-expect-in-subscribe`](#no-expect-in-subscribe-reports-one-shape-and-three-different-edits) | `expect()` внутри колбэка `subscribe()` → `expectEmission` / `firstValueFrom`                  | подсказка | зелено  |
| [`no-floating-assertion`](#an-assertion-in-a-then-nobody-awaits)                                | `expect()` в `.then()`, которого никто не дождался → `expect(await promise)`                   | —        | зелено  |
| [`no-done-callback`](#a-done-parameter-is-not-a-style-question)                                 | `it('x', (done) => …)` → `async` и дождавшийся ассерт, а `done.fail(…)` — по месту вызова      | —        | зелено  |
| [`no-bare-called-with`](#no-bare-called-with-%E2%80%94-one-word-two-opposite-meanings)          | `spy.m.calledWith(1);` отдельной инструкцией — заглушка, которую никто не продолжил, без ассерта | —      | зелено  |

### Дубли и модули, которые их держат {#doubles-and-the-modules-that-hold-them}

Не про отдельный тест, а про то, что один файл оставляет следующему.

| Правило                                                                                              | На что срабатывает                                                                                                        | Правка   |     Без него      |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------- | :---------------: |
| [`prefer-create-spy-from-class`](#two-things-these-rules-learned-the-hard-way)                       | объектный литерал из двух и более `vi.fn()` → `createSpyFromClass` / `createAutoMock`, если это не затравка самой фабрики   | —        |      красно       |
| [`no-shared-module-level-mock`](#a-double-built-once-per-worker-not-once-per-test)                   | **экспортированное** значение, держащее `vi.fn()` → экспортируйте фабрику, которая его возвращает                           | —        |      зелено       |
| [`no-object-define-property`](#no-object-define-property-%E2%80%94-nothing-puts-the-descriptor-back) | `Object.defineProperty` в спеке → `mockReadonlyProp` / `mockValueProp`                                                      | подсказка |      зелено       |
| [`no-import-time-spread`](#the-spread-that-only-fails-under-a-bundler)                               | `export const x = [...Imported]` на уровне модуля → `TypeError` во время загрузки бандла                                    | подсказка | красно _(по построению)_ |

### Angular DI и TestBed {#angular-di-and-the-testbed}

Пять способов, которыми провайдер оказывается не тем дублем, который спека, по её мнению,
зарегистрировала.

| Правило                                                                                            | На что срабатывает                                                                                                        | Правка   |     Без него      |
| -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------- | :---------------: |
| [`prefer-provide-auto-spy`](#two-things-these-rules-learned-the-hard-way)                          | самодельный `useValue` **или** `useFactory` → `provideAutoSpy(Class)` / `provideAutoSpyForToken(TOKEN)`                     | —        |      красно       |
| [`prefer-inject-spy`](#the-three-prefer-rules-%E2%80%94-drift-and-one-line-that-undoes-a-provider) | `vi.spyOn(TestBed.inject(X), 'm')`, инлайном или через `const` → `injectSpy(X).m`                                           | подсказка |      красно       |
| [`no-unregistered-inject-spy`](#the-spy-that-only-the-compiler-can-see)                            | `injectSpy(X)` для токена, который этот файл не регистрировал → настоящий инстанс, чьи спай-хелперы есть только у компилятора | —      | красно _(по построению)_ |
| [`prefer-render-shallow`](#the-render-nobody-reads)                                                | `TestBed.createComponent` в файле, который ни разу не читает шаблон → `renderShallow(X)`                                    | подсказка |      зелено       |
| [`no-overridden-provider`](#two-providers-one-token)                                               | два провайдера на один токен в одном массиве → более ранний не выполняется никогда; точный дубликат можно удалить            | подсказка |      зелено       |
| [`no-inject-before-override`](#the-trap-this-plugin-s-own-advice-sets)                             | `TestBed.inject()` в хуке в сюите, которая всё ещё вызывает `override*`                                                     | —        |      красно       |

### Типы {#types}

Два, чьё отсутствие рапортует компилятор — громко, но словарём класса, а не словарём ошибки.

| Правило                                    | На что срабатывает                                                                                                                          | Правка            |        Без него        |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- | :--------------------: |
| [`no-mocked-for-spy`](#the-two-type-rules) | `Mocked<T>` в любой типовой позиции → `Spy<T>`, вместе с импортом — подсказка там, где присвоенное значение не пришло из фабрик этой библиотеки | `--fix` / подсказка |       компиляция       |
| [`prefer-as-spy`](#the-two-type-rules)     | `TestBed.inject(X) as Spy<X>` → `asSpy(TestBed.inject(X))`, вместе с импортом                                                                 | `--fix`           | компиляция _(по построению)_ |

### Уход с jasmine {#coming-off-jasmine}

Написаны для сюиты, которая ещё не приехала, — работающей на
[`vitest-auto-spy/jasmine`](/ru/migrating-jasmine) или думающей, что работает. **Бездействуют в сюите,
которая никогда не пользовалась jasmine**, — см. [какие касаются вас](#if-you-never-used-jasmine).

| Правило                                                                                                         | На что срабатывает                                                                                               | Правка            |         Без него          |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------- | :-----------------------: |
| [`no-jasmine-globals`](#no-jasmine-globals-%E2%80%94-the-one-that-pays-for-itself-on-the-first-run)             | `jasmine.*`, голые `spyOn(` / `spyOnProperty(` / `spyOnAllFunctions(` / `fail(` / `pending(` и `.withContext(`      | —                 | зелено _(случай `spyOn`)_ |
| [`jasmine-namespace-without-entry`](#jasmine-namespace-without-entry-%E2%80%94-the-one-that-needs-setupmodules) | `.and` / `.calls` / `.withArgs` на спае библиотеки в файле, который нигде не ставит слой совместимости               | —                 |  красно _(по построению)_ |
| [`no-save-arguments-by-value`](#no-save-arguments-by-value-%E2%80%94-the-purest-silent-case-on-this-page)       | `spy.calls.saveArgumentsByValue()` — здесь это no-op, так что спека молча проверяет состояние после мутации          | —                 | зелено _(по построению)_  |
| [`prefer-native-spy-api`](#prefer-native-spy-api-%E2%80%94-the-one-to-switch-off-while-you-migrate)             | `.and` / `.calls` там, где собственный API спая говорит то же самое, — последняя миля с jasmine-шима                 | `--fix` / подсказка | — _(рапортует рабочий код)_ |

## Настройка под ваш проект {#tuning-it-for-your-project}

Конфиг — обычный объект, так что каждая ручка — одна строка в **вашем** `eslint.config.js`, и ничего
здесь не требует форка или обёртки.

### Понизить одно правило {#turn-one-rule-down}

```js
export default [
  {
    files: ['**/*.spec.ts'],
    ...autoSpy.configs.recommended,
    rules: {
      ...autoSpy.configs.recommended.rules,
      'vitest-auto-spy/prefer-provide-auto-spy': 'warn', // сообщать, но не блокировать мердж
      'vitest-auto-spy/prefer-create-spy-from-class': 'off', // не наш стиль
    },
  },
];
```

Раскрывайте `autoSpy.configs.recommended.rules` перед своими переопределениями: голый ключ `rules`
рядом с раскрытым конфигом **заменяет** всю карту, а не сливается с ней, и в результате получается
конфиг из двух правил без единой ошибки об этом.

### Как внедрить на большой существующей сюите без красного CI {#land-it-on-a-large-existing-suite-without-a-red-ci}

Сначала возьмите находки как предупреждения, чините их партиями, а потом удалите блок:

```js
const asWarnings = Object.fromEntries(Object.keys(autoSpy.configs.recommended.rules).map((rule) => [rule, 'warn']));

export default [
  {
    files: ['**/*.spec.ts'],
    ...autoSpy.configs.recommended,
    rules: { ...autoSpy.configs.recommended.rules, ...asWarnings },
  },
];
```

Средний путь, который стареет лучше: держать каждое правило на `error`, а ещё не починенные файлы
вынести во второй блок с выключенными в нём проблемными правилами. Сокращающийся список путей — это
видимый прогресс; общесюитный `warn` — решение, к которому никто не возвращается.

### Три правила, которые могут сработать на корректном коде {#the-three-rules-that-can-report-on-correct-code}

Все правила здесь синтаксические, и трём из них задают вопрос, на который один файл не всегда может
ответить. Они всё равно ошибки — быть неправым насчёт вашего проекта чинится одной строкой, и каждая
строка ниже, — но если первый прогон вас удивил, смотреть надо в первую очередь на них.

| Правило                           | Когда оно неправо насчёт вас                                                                                                                                               | Строка, которая это чинит                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `jasmine-namespace-without-entry` | `enableJasmineCompat()` живёт в записи `setupFiles` Vitest, которую не импортирует ни одна спека, так что файл с `.and` выглядит файлом без установленного слоя            | `['error', { setupModules: ['./test-setup'] }]`                                |
| `no-unregistered-inject-spy`      | файл регистрирует часть дублей в форме, которую правило читает, **и** получает ещё один через хелпер, за которым оно не идёт, — общий `beforeEach`, настраивающий TestBed   | опции нет; локальный `'off'` или отключение на строку                          |
| `prefer-native-spy-api`           | вы **посреди переезда** с `jasmine-auto-spies`; оно рапортует рабочий код моста, так что в первый день срабатывает на каждой его строке                                     | `'off'`, пока сюита не позеленеет, потом `'error'` и `--fix` на последнюю милю |

Опция есть только у первого, и там `setupModules` — это и есть починка, а не понижение серьёзности: она
говорит правилу, где ставится слой, и оно перестаёт гадать. Импорт точки входа, которая _не может_
загрузить jasmine-вариант (`vitest-auto-spy/bun`, `…/node`), тоже глушит его для этого файла.

`no-unregistered-inject-spy` в большинстве проектов не нуждается в опции, потому что он **и так**
консервативен: он молчит, пока файл хотя бы раз не вызовет `provideAutoSpy`, и умолкает в ту минуту,
когда встречает то, что не может прочитать, — спред или неизвестную фабрику провайдера в `providers`,
`createWithAutoSpies`, `renderShallow` или `TestBed.overrideProvider`. То, что переживает этот фильтр,
обычно настоящая находка: `injectSpy(X)`, отдающий настоящий сервис со спай-хелперами, которые есть ради
компилятора и бросают на первом же `.mockReturnValue(…)`.

### Заглушить одну строку, а не одно правило {#silence-one-line-not-one-rule}

```ts
// eslint-disable-next-line vitest-auto-spy/no-object-define-property -- свойство это геттер на замороженном host-объекте
Object.defineProperty(target, 'clientWidth', { value: 100 });
```

Это стоит предпочитать конфигурационному `off` везде, где исключение действительно локально: правило
продолжает работать для остальных четырёхсот файлов, а комментарий фиксирует, чем этот отличается.

### Проверить, что применяется на самом деле {#check-what-actually-applies}

```bash
npx eslint --print-config src/app/cart.spec.ts | grep vitest-auto-spy
```

Если ничего не напечаталось, глоб `files` не совпадает — а симптом у этого тот же, что и у «плагин не
нашёл проблем», и поэтому проверять надо до того, как решить, что сюита чистая.

### Опции правил {#rule-options}

Есть одна у `prefer-render-shallow`, и она превращает находку про цену в политику:

```js
'vitest-auto-spy/prefer-render-shallow': ['error', { templates: 'never' }],
```

`'as-needed'` — по умолчанию — рапортует только про рендер, чей шаблон никто не читает. `'never'`
рапортует про каждый `TestBed.createComponent` и каждый `keepTemplate: true` — для проекта, решившего,
что разметка принадлежит e2e. Это стоит стопроцентного порога покрытия на компонентах; измерение — в
[рендере, который никто не читает](#the-render-nobody-reads).

Есть одна и у `prefer-create-spy-from-class`:

```js
'vitest-auto-spy/prefer-create-spy-from-class': ['error', { minRunnerFns: 1 }],
```

По умолчанию `2`, и причина — то, чего правило не видит: объект с одним `vi.fn()` неотличим от мешка
опций с колбэком, а правило срабатывает на каждом объектном литерале в файле. Тем не менее семь партий
спотыкались об асимметрию — два дубля на соседних строках, один помечен, другой нет, — так что порог
назван в сообщении и настраивается здесь. Случай, о котором эти сообщения на самом деле были, закрыт с
той стороны, где его можно доказать: у `prefer-provide-auto-spy` рядом с объектом есть `provide:`, так
что он срабатывает уже на **одном**, а с тех пор как он научился идти по имени к `const` выше TestBed,
он добирается до тех же дублей.

Правило не должно наказывать за собственную починку, а `prefer-create-spy-from-class` наказывал.
Объект, переданный в одну из фабрик этой библиотеки, — это **затравка**, а не самодельный дубль, и
другой формы у неё быть не может:

```ts
const xhr = createAutoMock<XhrLike>({ send: vi.fn(), abort: vi.fn() }); // ✅ никогда не помечается
const api = mockDeep<Api>({ api: { load: vi.fn(), save: vi.fn() } }); // ✅ и ни на какой глубине
```

Всё, что внутри вызова `autoMocked`, `createAutoMock`, `createMock`, `createSpyClass`,
`createSpyFromClass`, `mockConstructor`, `mockDeep`, `provideAutoSpy` или `provideAutoSpyForToken`,
исключено. `prefer-provide-auto-spy` в таком исключении не нуждается: `useValue`, построенный фабрикой,
— это вызов, а он всегда смотрел только на объектные литералы.

### Выбирать правила руками {#picking-rules-by-hand}

Пропустите `configs.recommended` целиком и перечислите нужные правила — объект плагина экспортируется
сам по себе, так что это поддерживаемая форма, а не обходной путь. Предпочитайте
[Настройку под ваш проект](#tuning-it-for-your-project), если хотите весь набор с парой подкрученных
ручек; предпочитайте это, если хотите короткий список и больше ничего:

```js
import autoSpy from 'vitest-auto-spy/eslint-plugin';

export default [
  {
    files: ['**/*.spec.ts'],
    plugins: { 'vitest-auto-spy': autoSpy },
    rules: {
      'vitest-auto-spy/no-expect-in-subscribe': 'error',
      'vitest-auto-spy/no-done-callback': 'error',
    },
  },
];
```

Каждое сообщение заканчивается ссылкой на подходящий рецепт в разделе
[How to mock](https://github.com/ASDAlexey/vitest-auto-spy#how-to-mock) в README: правило, которое
только говорит «не надо», перекладывает проблему, а не решает её. Правила едут вместе с API, который
они советуют, поэтому версионируются вместе с ним и перестают переписываться заново в каждом проекте,
который ставит пакет.

## Почему эти правила существуют {#why-the-rules-exist}

По разделу на правило, в порядке таблицы выше, — на случай, когда сообщение уже прилетело и вопрос в
том, от чего оно вас уберегло. У [четырёх jasmine-правил](#the-four-jasmine-rules) свой раздел следом;
[измерения](#measured-what-each-rule-is-worth), подкрепляющие колонку _Без него_, — в конце.

### `no-bare-called-with` — одно слово, два противоположных смысла {#no-bare-called-with-—-one-word-two-opposite-meanings}

`calledWith` — это **настройщик заглушки** в этой библиотеке. Начиная с Vitest 4.1 это ещё и, в
бандле chai, **ассерт**:

```ts
expect(fn).to.have.been.calledWith('example'); // chai: проверяет, что вызов был
cart.checkout.calledWith(1); // эта библиотека: настраивает, чем ответит вызов
```

Вторая строка не проверяет ничего. Она регистрирует «на аргумент `1` отвечать `undefined`» — а именно
это ненастроенный спай и так делает, — так что тест проходит независимо от того, вызывался ли
`checkout` вообще. Правило рапортует об этом и называет обе починки: продолжить цепочку
(`.mockReturnValue(v)`, `.resolveWith(v)`, `.nextWith(v)`, `.failWith(err)`) либо проверить через
`expect(spy.method).toHaveBeenCalledWith(...)`. Цепочки с корнем в `expect(...)` не трогаются, так что
собственная форма chai его никогда не задевает.

`mustBeCalledWith` сам по себе получает другое сообщение, потому что он неправ по-другому: когда для
переданных ему аргументов ничего не настроено, он отвергает **каждый** вызов — включая совпадающий.

### `no-expect-in-subscribe` рапортует одну форму и три разные правки {#no-expect-in-subscribe-reports-one-shape-and-three-different-edits}

Пять партий переезда разбирали эту работу руками, и пропорции меняются от _файла_ к файлу, а не от
сюиты к сюите: в одном 110 мест из 111 были механической инверсией, в другом — 36 из 119. Время съедало
то, что для всех них читалось одно сообщение, поэтому теперь правило говорит, на какой из трёх случаев
оно смотрит.

```ts
// 1. подписка — последнее, что делает тест: инвертируем
const value = await firstValueFrom(source$);
expect(value).toBe(1);

// 2. поток заставляет эмитить то, что идёт после неё, — держим промис.
//    `await firstValueFrom(...)` здесь встаёт в дедлок: await не возвращается, значит, триггер
//    не выполняется. `expectEmission` подписывается, когда вы его вызвали, а не когда дождались.
const emission = expectEmission(service.getCurrentLevel());
httpMock.expectOne(url).flush(payload);
await expect(emission).resolves.toEqual(payload);

// 3. ассерт в ветке ошибки — `expectEmission` разрешается на значении
await expect(firstValueFrom(source$)).rejects.toBeInstanceOf(UdmsStatusError);
```

Признак для второго случая чисто синтаксический: после инструкции с `subscribe` есть ещё одна
инструкция. Третий — это то, в каком обработчике сидит ассерт, позиционном или именованном, — и стоит
сказать, что `subscribe({ next: () => expect.unreachable(…), error: (e) => expect(e).toBe(err) })` тоже
схлопывается в одну строку с `rejects`, потому что защита от эмиссии — это ровно то, что `rejects` и
так делает.

Оно читает и ассерты, до которых колбэк добирается через хелпер:

```ts
const assertShape = (data: Content): void => {
  expect(data.items).toHaveLength(3);
};

source$.subscribe((data) => assertShape(data)); // всё ещё ассерт, который может не выполниться
```

Один шаг через имя, связанное в том же файле, — информация о типах для этого не нужна, а форму это
покрывает. Хелпер, объявленный _внутри_ колбэка, считается один раз, а не два.

### Ассерт в `.then()`, которого никто не дождался {#an-assertion-in-a-then-nobody-awaits}

`no-floating-assertion` ловит то же падение, что и `no-expect-in-subscribe`, только очередью правее.
`compileComponents().then(() => expect(…))` отдельной инструкцией выполняет свой колбэк после того, как
написавший его тест закончился, так что уронить его ассерт не может, — а под zone.js получившийся
реджект вычерпывается в `console.error`, а не рапортуется, оставляя зелёный тест и строку в stderr.
Правило смотрит только на _непосредственно_ объемлющий колбэк, потому что именно в этой области
дожидание цепочки и есть настоящая починка: `expect()`, припаркованный в `subscribe()` или
`setTimeout()` внутри `.then()`, оставлен `no-expect-in-subscribe` и
[`setupAutoSpy({ strayRejections: true })`](/ru/utilities/setup#_8-failing-on-a-rejection-zone-js-swallowed),
который ловит в рантайме то, чего не увидит никакой селектор.

### Параметр `done` — не вопрос стиля {#a-done-parameter-is-not-a-style-question}

Vitest передаёт вызываемый `TestContext` первым параметром теста, так что его вызов бросает —
`done() callback is deprecated, use promise instead` на Vitest 4,
[измерено ниже](#no-done-callback-%E2%80%94-what-the-first-parameter-actually-is). Это безобидный
случай. В форме, которой на самом деле полна Jasmine-сюита, вызов стоит в конце колбэка, тело
возвращает `undefined` раньше, чем он выполнится, и тест **проходит**, выполнив почти ничего из себя.
Четыре таких теста годами стояли зелёными в той сюите, из которой пришло это правило; ничего, кроме
тайпчекера, их не замечало, да и то косвенно.

### Дубль, построенный раз на воркер, а не раз на тест {#a-double-built-once-per-worker-not-once-per-test}

`no-shared-module-level-mock` существует потому, что экспортированный дубль строится раз на **модуль**,
а не раз на тест:

```ts
// ❌ эти спаи общие для каждой импортирующей спеки, на весь воркер
export const actionContext = { actions: { navigateToSection: vi.fn() } };

// ✅ по набору на каждого вызывающего
export const createActionContext = () => ({ actions: { navigateToSection: vi.fn() } });
```

При `isolate: false` модуль вычисляется раз на воркер, так что все импортирующие файлы делят один
объект. `clearMocks: true` до спаев внутри него действительно дотягивается —
[измерено](#no-shared-module-level-mock-%E2%80%94-one-module-two-files) — и чистит их вызовы; чего он
вычистить не может, так это состояния, которое фикстура держит рядом с ними и которое переезжает из
того файла, что прогнался первым, во все остальные. Правило останавливается на каждой границе функции,
так что форма-фабрика — то есть починка — не помечается заодно с проблемой. Применяйте его и к
модулям фикстур, и к файлам спек; файл спеки
[не должен экспортировать вообще ничего](/ru/utilities/setup#shared-fixtures-are-functions-not-constants).

### Спред, который падает только под бандлером {#the-spread-that-only-fails-under-a-bundler}

`no-import-time-spread` существует ради `TypeError`, который поднимается во время _загрузки_ бандла
спек на дереве, где все тесты проходят:

```
Spread syntax requires ...iterable[Symbol.iterator] to be a function
```

Форма — спред на уровне модуля, чей операнд принадлежит другому модулю:

```ts
import { BaseEvents } from './base-events';

export const webosEvents = [...BaseEvents]; // ❌ безопасно под tsc, TypeError внутри бандла
```

Под `tsc` и под браузерным ESM-загрузчиком это упасть не может — модуль никогда не выполняется раньше
своей зависимости. Внутри одного бандла может: сборщик выпускает общие чанки, чанк может быть вычислен,
пока реэкспортируемый им биндинг ещё `undefined`, а `[...undefined]` бросает. Первопричина та же, что и
у [заметки про инициализацию бочек](/ru/migrating) в гайде по переезду, но симптом не называет ни
модуля, ни barrel-модуля, так что связать эти два не по чему.

Скан стоит иметь, потому что находимая им популяция мала: проход по AST в поисках спредов
импортированного идентификатора на уровне модуля нашёл ровно **семь** мест в воркспейсе на 8 673
файла, два из них разворачивали barrel воркспейса. Этого достаточно мало, чтобы помечать прямо под
курсором, и это решается по импортам того же файла.

::: warning У того же сообщения есть вторая причина, которой правило не видит
`Spread syntax requires ...iterable[Symbol.iterator] to be a function` — это ещё и то, что говорит
бандл спек, когда **сборщик** разложил точки входа иначе, и тогда ни один спред в исходниках вообще ни
при чём. Измерено на одном шарде Angular-воркспейса, дерево неизменно, три конфигурации подряд: при
незаданном собственном ключе `isolate` у `@angular/build:unit-test` — 860 файлов зелёные; при
`"isolate": false` — 39 файлов красные с этим сообщением и **ноль собранных тестов**; при
`"isolate": true` — снова 860 файлов зелёные. `isolate` уровня раннера и одноимённая опция сборщика —
это не одна и та же настройка.

Признак — число тестов. Спред на уровне модуля, который действительно сломан, кладёт файл _после_ того,
как тесты собраны; в случае сборщика не собирается ни один, стека нет вообще, а список падающих файлов
от прогона к прогону не повторяется. Читайте это как «спред ни при чём» и оставляйте ключ `isolate` у
сборщика незаданным — пусть изоляцию включает покрытие, — а не пишите `false`. Эти числа из одной серии
и здесь не воспроизводятся.
:::

Три вещи сознательно не рапортуются, потому что выполняются позже модуля:

```ts
export const make = () => [...BaseEvents]; // тело функции
class Events {
  all = [...BaseEvents]; // поле инстанса — выполняется при конструировании
  static all = [...BaseEvents]; // …а вот статическое помечается: оно выполняется вместе с объявлением класса
}
```

И операндом должен быть сам импортированный биндинг. `[...BaseEvents.slice()]` — это вызов, и что бы он
ни бросил, это уже другая проблема.

### Две вещи, которым эти правила научились на своей шкуре {#two-things-these-rules-learned-the-hard-way}

**Настроенный спай — всё ещё спай.** `vi.fn()` и `vi.fn().mockReturnValue(of([]))` — это один и тот же
дубль, просто второй настроен, — но проверка за `prefer-provide-auto-spy` и
`prefer-create-spy-from-class` читала непосредственно вызываемое и на этом останавливалась, так что
видела голую форму и упускала все настроенные. В одном массиве `providers` это означало, что дубль на
одной строке помечался, а на следующей — нет:

```ts
{ provide: A, useValue: { getProductCardData: vi.fn() } },              // помечен
{ provide: B, useValue: {                                              // молчание, до сих пор
    getProducts: vi.fn().mockReturnValue(of([])),
    getProductById: vi.fn().mockReturnValue(of(null)),
} },
```

Ровно наоборот: чем сильнее самодельный дубль настроен, тем дальше он ушёл от класса, за который стоит,
и тем больше смысла было о нём рапортовать. Теперь цепочка разматывается до вызова, создавшего мок,
какой бы длинной она ни была.

**Токен — не класс.** `prefer-provide-auto-spy` раньше советовал `provideAutoSpy(Token)` для всего, а на
`InjectionToken` этот совет не компилируется — `provideAutoSpy` читает прототип класса, а у токена его
нет. Три партии переезда сообщили об этом независимо; в одной из них шесть отчётов из восьми были про
токены. Теперь правило их различает — по объявлению, когда `new InjectionToken(…)` в пределах
досягаемости резолвера, иначе по написанию `SCREAMING_SNAKE_CASE` — и называет для токена
`provideAutoSpyForToken(TOKEN)`, а в сообщении для класса заодно упоминает и форму для токена.

### Ловушка, которую расставляет собственный совет этого плагина {#the-trap-this-plugin-s-own-advice-sets}

`TestBed.inject()` и `TestBed.createComponent()` **инстанцируют** тестовый модуль, и после этого любой
`TestBed.override*` бросает. Переезд на `provideAutoSpy` заводит в неё людей за руку: самодельный
`useValue` настраивал возвращаемые значения прямо в литерале, а замене их положить некуда, так что
строка уезжает в `beforeEach`.

```ts
beforeEach(() => {
  TestBed.configureTestingModule({ providers: [provideAutoSpy(Api)] });
  asSpy(TestBed.inject(Api)).load.mockReturnValue(of(page)); // ❌ модуль теперь инстанцирован
});
```

После этого любой `override*` в сюите бросает — включая написанный _выше_ этой строки, внутри хелпера
`createComponent`, который вызывают тесты. Найдено дважды независимо после переезда, один раз — на
шестнадцать тестов разом. Две починки, обе в сообщении:

```ts
it('renders', () => {
  TestBed.overrideProvider(Other, { useValue: x });
  injectSpy(Api).load.mockReturnValue(of(page)); // ✅ настроено после всех override
});

const api = () => injectSpy(Api); // ✅ или держите доступ ленивым, чтобы
//    инстанцирование случилось в первом тесте
```

Проверка сознательно **не зависит от порядка**, потому что лексический порядок — не порядок выполнения:
хелпер выше это и доказывает. Она спрашивает, делает ли сюита override вообще, с единственным
исключением, которое можно вычитать из исходника: `override*`, стоящий в том же теле хука перед
инъекцией, действительно выполняется раньше. Сюита, вызывающая `TestBed.resetTestingModule()`,
исключена полностью.

### Два провайдера, один токен {#two-providers-one-token}

Angular оставляет **последний** зарегистрированный для токена провайдер, так что всё выше него мертво.
В тестовом модуле это не про аккуратность:

```ts
providers: [
  provideAutoSpy(DisplaySettingsService), // ❌ не выполняется никогда
  { provide: DisplaySettingsService, useValue: mockDisplaySettingsService }, // вот что раздаёт DI
];
```

В одном файле спеки восемь токенов были зарегистрированы обоими способами сразу. Это вводит в
заблуждение с обеих сторон: автор верит, что там auto-spy, и пишет ассерты против него, тогда как
внедряется на самом деле самодельный объект, расходящийся с классом, — а тот, кто позже придёт этот
объект заменять, видит рядом `provideAutoSpy` и читает переезд как уже сделанный.

Токены сравниваются как написаны, а не как разрешены: в массиве `providers` токен появляется по имени,
один раз, рядом с дублем, за который он стоит, так что резолверу тут нечего добавить.

#### Пара классифицируется, потому что половины — разные дефекты {#the-pair-is-classified-because-the-two-halves-are-not-the-same-defect}

Первые полевые данные по этому правилу — 20 отчётов на воркспейс из 8 673 файлов — разделились надвое, и
теперь правило говорит, на какую половину оно смотрит.

**Большинство были буквальными дубликатами.** Один и тот же провайдер, написанный дважды, теми же
словами:

```ts
providers: [provideAutoSpy(KidsModeService), provideRouter([]), provideAutoSpy(KidsModeService)];
```

Angular и так уже игнорировал первый, так что удаление не может изменить то, что получает тест. Это
единственная форма здесь, к которой прилагается правка — и предлагается она **подсказкой**, а никогда
не через `--fix`, потому что прогон, без присмотра удаляющий строки из массива `providers`, — не то,
что стоит обнаруживать в дифе. Сообщение называет токен и строку, на которой стоит выжившая копия.

**Остальные — интересный вид: выживает _более бедный_ из двух.**

```ts
providers: [
  provideAutoSpy(AccountService, { gettersToSpyOn: ['plan'], instanceMethodsToSpyOn: ['refresh'] }),
  provideAutoSpy(AccountService), // ← вот этот и раздаёт DI
];
```

Всё, что настроила первая строка, пропало, а ассерты ниже выполняются против более бедного спая,
отзывающегося на то же имя, — дубль, который спека настраивала, не тот, который она получила. Здесь
удалять за вас нечего, потому что какой из двух оставить — это и есть весь вопрос, так что сообщение
говорит именно это: перенесите настройку на выживший провайдер или удалите его.

Всё, что ни то ни другое, — auto-spy, погребённый настроенным самодельным `useValue`, случай восьми
токенов выше — сохраняет исходную формулировку плюс номер строки победившего провайдера.

**`multi: true` исключён, и иначе нельзя.** Angular _накапливает_ multi-провайдеры для токена, а не
оставляет последний, так что второй — вовсе не переопределение:

```ts
providers: [
  { provide: BEFORE_INIT, useValue: first, multi: true },
  { provide: BEFORE_INIT, useValue: second, multi: true }, // выполняются оба, в этом порядке
];
```

Спеке, проверяющей, что её хуки выполняются в порядке регистрации, нужны оба, и рапорт про любой из них
можно заглушить только `eslint-disable` над рабочим тестом. Смешение двух режимов для одного токена
остаётся находкой: Angular отказывает такой паре в рантайме с
`Cannot mix multi providers and regular providers`, так что это дефект, какая половина ни имелась бы в
виду. Значение, которое правило не может разрешить (`multi: flag`), читается как multi — пропущенный
рапорт не стоит ничего, ложный стоит комментария-отключения над корректным кодом.

`prefer-provide-auto-spy` отступает от той же формы по другой причине: `provideAutoSpy` строит один
дубль на токен и не принимает режим регистрации, так что рекомендованной им замены попросту не
существует, а следование ей тихо превратило бы накапливающий провайдер в переопределяющий.

### Спай, которого видит только компилятор {#the-spy-that-only-the-compiler-can-see}

`no-unregistered-inject-spy` рапортует про `injectSpy(X)` для токена, который в этом файле никто не
регистрировал как auto-spy:

```ts
TestBed.configureTestingModule({
  imports: [RouterTestingModule], // даёт настоящий ActivatedRoute
  providers: [provideAutoSpy(UserService)],
});

const route = injectSpy(ActivatedRoute); // ❌ настоящий, со спай-хелперами, которых там нет
```

Возвращается то, что уже было у Angular DI, — настоящий сервис или объект, положенный туда
импортированным тестовым модулем. У компилятора возражений нет, и в этом весь дефект: `injectSpy`
объявлен возвращающим `Spy<T>`, так что каждый хелпер на нём проверяется против этого объявления, а не
против значения, — то есть хелперы есть для `tsc` и отсутствуют в рантайме. Первый же
`.mockReturnValue(…)` или `.calledWith(…)` попадает на настоящий метод и бросает прямо там —
`TypeError` на строке, которая читается как обычная настройка спая.

Библиотека уже говорит это в рантайме: `injectSpy` проверяет, что вернул инжектор, и предупреждает, что
это обычный инстанс. Предупреждение в stderr — самое слабое место, чтобы это сказать. Оно не роняет
прогон, оно прокручивается мимо в сюите из тысячи файлов, и приходит оно только для тех тестов, которые
эту строку действительно выполнили, — в одном потребительском монорепозитории десятки файлов спек
печатают его на каждом прогоне CI, и никто ни разу ничего с этим не сделал. Проверке не нужна никакая
информация о типах, так что её место там, где ошибка написана: весь вопрос в том, какие токены этот файл
зарегистрировал и какой токен запрашивают.

**Правило молчит, пока не видит картину целиком**, потому что ложное срабатывание здесь дороже
заменяемого предупреждения. Оно не рапортует ничего, когда:

- файл ни разу не вызывает `provideAutoSpy` — тогда он настраивает DI как-то иначе, чем здесь
  смоделировано, и отсутствие токена в подсчёте ни о чём не говорит;
- какой-нибудь массив `providers` содержит спред или фабрику провайдера, отличную от `provideAutoSpy`.
  `providers: [...sharedMocks]` — обычный способ подтянуть общий модуль моков, а что он регистрирует, не
  видно. Одна нечитаемая запись прячет неизвестное число токенов, поэтому она глушит **файл**, а не одну
  строку;
- файл вызывает `createWithAutoSpies`, `renderShallow` или `TestBed.overrideProvider` — каждый из них
  регистрирует дубли там, куда этот скан не смотрит.

Токен, предоставленный руками, — `{ provide: X, useValue: someObject }` — записывается как
предоставленный и не трогается. Для этой формы есть правило `prefer-provide-auto-spy`, а два правила,
срабатывающих на одной строке, только научили бы людей отключать оба. `useValue`, являющийся вызовом
`createAutoMock`, `createSpyFromClass`, `createMock` или `mockDeep`, считается регистрацией так же, как
и `provideAutoSpy`. Токены сравниваются как текст исходника — так же, как их уже сравнивает
`no-overridden-provider`, — и ни правки, ни подсказки здесь нет: починка — это либо провайдер, которого
в этом файле нет, либо `TestBed.inject(X)`, говорящий, что настоящая реализация и была смыслом.

### Рендер, который никто не читает {#the-render-nobody-reads}

`prefer-render-shallow` рапортует про `TestBed.createComponent` в файле, где отрендеренный шаблон никто
никогда не читает — ни `nativeElement`, ни `debugElement`, ни `By.css`, ни `querySelector`. Код
работает; прогон зелёный в обоих случаях. Правило — про счёт.

`TestBed.createComponent` компилирует шаблон компонента и инстанцирует всё дочернее поддерево. Спека,
которая только выставляет инпуты и проверяет сигналы или обычное состояние, этим поддеревом не покупает
ничего, а платит за него на каждом тесте. `renderShallow(X)` — тот же `TestBed`, та же настоящая
`ComponentFixture`, но с выброшенными детьми и пустым шаблоном; инпуты, сигналы, хуки жизненного цикла
и DI остаются на месте.

Сколько это экономит — вопрос не вкуса; `bench-angular/` это меряет, а числа сверяются с закоммиченным
базлайном. На цикл теста, относительно `TestBed.createComponent`:

| Детей рендерит компонент | `renderShallow()`   |
| ------------------------ | ------------------- |
| 0                        | вровень — см. ниже  |
| 25                       | 0.57×               |
| 100                      | 0.24×               |
| 400                      | 0.05×               |

**Прочитайте первую строку раньше последней.** При нуле детей экономить нечего, и два измерения ложатся
по обе стороны от 1,0 — эта строка самая шумная в бенчмарке (±16 % против ±3 % у строки на сто детей), а
`overrideComponent` заставляет JIT перекомпилировать то, за что листовой компонент раньше не платил.
Правило окупается в сюите, чьи компоненты рендерят другие компоненты, и чем глубже дерево, тем сильнее.
Одно только обнуление шаблона — шаг от `renderShallow({ keepTemplate: true })` к `renderShallow()` на
компоненте со ста детьми — стоит само по себе около **3,8×**.

Двух вещей правило не видит, и починка у обеих одна:

- Компоненту, который читает собственный шаблон через `viewChild`, `contentChild` или проекцию
  содержимого, шаблон нужен. Правило читает спеку, а не компонент, так что о нём оно сообщит;
  `renderShallow(X, { keepTemplate: true })` сохраняет шаблон и всё равно выбрасывает детей.
- Компонент, чьё поведение управляется из его собственного шаблона — событие, привязанное в разметке,
  блок `@defer`, — находится в том же положении.

Вопрос правило задаёт сознательно про **файл**, а не про одну фикстуру: сюита компонента паркует
фикстуру в `let`, заполняет её в `beforeEach` и читает `debugElement` через три хелпера. Одно чтение
шаблона где угодно глушит весь файл, так что правило скорее недорапортует, чем гадает.

Одна форма вычитается до того, как задан этот вопрос, потому что она глушила правило ровно на том файле,
ради которого оно существует. Спека, подменяющая `location` или `defaultView`, подсовывает заменитель
`DOCUMENT`, делегирующий остальное настоящему документу — `querySelector: document.querySelector.bind(document)`, —
и каждый скопированный ею ключ есть в списке слов выше. Отбрасывается только форма `name: document.name`,
и только там, где оба имени совпадают: это делегирование и ничем другим быть не может. Голый
`document.querySelector('.row')` по-прежнему считается, потому что фикстуру, прикреплённую к документу,
читают именно так.

#### Переписывание предлагается, а не применяется {#the-rewrite-is-offered-not-applied}

Правило поставляет **подсказку** — `TestBed.createComponent(X)` → `renderShallow(X).fixture`, с
добавлением импорта, когда имя свободно, — и сознательно никакого `--fix`. `renderShallow` сам вызывает
`configureTestingModule`, добавляет `NO_ERRORS_SCHEMA` и запускает первый цикл обнаружения изменений:
правильный модуль для спеки, которая не читает разметку, но не тот модуль, который был у файла. `--fix`
работает без присмотра по всему репозиторию, а спека, уже инстанцировавшая модуль — любой
`TestBed.inject` выше этой строки, — начала бы бросать *Cannot configure the test module when the test
module has already been instantiated*. Подсказку жмут по одному вызову, с дифом перед глазами.

Предлагается она только для `TestBed.createComponent(X)` с одним компонентом. Форма с двумя аргументами
несёт опции, которые `renderShallow` пишет иначе, и переписывание, их потерявшее, было бы молчаливым
уроном.

#### `{ templates: 'never' }` — переключатель политики {#templates-never-—-the-policy-switch}

По умолчанию `'as-needed'`: рапортовать про рендер, который никто не читает. Проект, решивший, что
разметка принадлежит e2e, может сказать это прямо, и тогда ни одна спека не рендерит настоящий шаблон
вообще:

```js
'vitest-auto-spy/prefer-render-shallow': ['error', { templates: 'never' }],
```

Под `'never'` рапортуется каждый `TestBed.createComponent` независимо от того, читает ли файл DOM, и то
же самое — `keepTemplate: true`. Один рендер исключён: host, построенный
[`createDirectiveHost`](/ru/adapters/angular). Директива навешивается на элемент, значит, кто-то должен
этот элемент отрендерить — шаблон host'а тут оснастка, а не проверяемая разметка, и запретить его значило
бы запретить тестировать директивы вообще, включая тот способ, который рекомендует документация самого
этого пакета.

Отчёт под двумя настройками читается по-разному, и иначе нельзя. `'as-needed'` не нашёл чтения шаблона и
может так и сказать; `'never'` вообще не спрашивал, и под ним громче всех рапортуется обычно тот файл,
который читает шаблон сильнее прочих. Так что настройка-политика формулирует политику, а не утверждает
что-то о файле, чего она не проверяла.

**Знайте счёт до того, как включать.** Измерено на одной потребительской сюите: `'never'` покрасил
**18 из 40** тестов в спеке компонента и увёл покрытие со **100 % до 95,7 %**. Из отчёта не исключалось
ничего — при `templateUrl` скомпилированный шаблон отображается обратно в `.html`, а его глоб покрытия по
`*.ts` и так никогда не матчил. Перестал выполняться обычный TypeScript: тело метода, условие входа в
который — `viewChild`, поставляемый шаблоном. Этот код не исчезает из отчёта, когда перестаёт
выполняться, и никакая настройка покрытия его не спрячет, потому что это не код шаблона — это
собственный код компонента. Проект, берущий эту опцию, отказывается от стопроцентного порога по строкам
на своих компонентах, и такова сделка, сказанная прямо.

### Два правила про типы {#the-two-type-rules}

`no-mocked-for-spy` рапортует про форму **объявления**, а не про каждое использование: `Mocked<T>`
по-прежнему уместен рядом с `vi.mocked()`, и его правило не трогает. Оно — про объявление, чьё
присваивание потом падает со списком имён приватных полей, который о настоящей причине не говорит
ничего.

`prefer-as-spy` — тот же вопрос строкой ниже, и именно его переезд встречает массово:
`devicesService = TestBed.inject(DeviceListService) as Spy<DeviceListService>` пишется по разу на каждый
внедрённый дубль в `jest-auto-spies`-сюите, и каждый из них падает с `TS2352` в этой библиотеке —
[самая частая ошибка компиляции у переехавшей Angular-сюиты](/ru/migrating#reading-a-spy-back-out-of-the-container).
`asSpy(...)` — то же утверждение без каста, поэтому правило чинит это под `--fix`.

## Четыре jasmine-правила {#the-four-jasmine-rules}

Они рулят в противоположную сторону от остального плагина. Другие пятнадцать толкают Vitest-сюиту к API
этой библиотеки; эти четыре — про сюиту, которая ещё не приехала: работающую на
[`vitest-auto-spy/jasmine`](/ru/migrating-jasmine) или думающую, что работает.

### `no-jasmine-globals` — то, которое окупается на первом же прогоне {#no-jasmine-globals-—-the-one-that-pays-for-itself-on-the-first-run}

`jasmine`, `spyOn`, `spyOnProperty`, `spyOnAllFunctions`, `fail` и `pending` — это глобалы, которые
ставит собственный раннер jasmine. Здесь их не ставит никто, так что большинство из них громко падает на
первом прогоне с `ReferenceError`. **Одно — нет, и именно поэтому это правило, а не строчка в гайде по
переезду:**

```diff
- spyOn(analytics, 'track');        // jasmine: track() не выполняется никогда
+ vi.spyOn(analytics, 'track');     // Vitest: track() выполняется при каждом вызове
```

`spyOn` в jasmine ставит **заглушку**; `vi.spyOn` **вызывает настоящий метод**. Переименование
компилируется, спека выполняется, и проверяемый код начинает по-настоящему разговаривать со своим
коллаборатором — вот так переехавшая сюита и начинает ходить в сеть или проходить, проверяя значение,
которое настоящая реализация случайно вернула. Сообщение называет
`vi.spyOn(obj, 'm').mockImplementation(() => undefined)` там, где строка на jasmine означала «заглушить
его», и показывает на `createSpyFromClass` / `provideAutoSpy`, которые заглушают каждый метод по
построению.

Правило проявляет ту же вежливость к имени, которое оказалось чужим, что и все остальные правила здесь:
`jasmine`, объявленный самим файлом, или `import { spyOn } from 'bun:test'` — другая функция с тем же
именем, и на этом рантайме правильная — не трогаются. `.withContext(` рапортуется тем же правилом,
потому что [chai-слой Vitest его молча проглатывает](/ru/migrating-jasmine#withcontext-does-not-throw-it-loses-the-message),
а не бросает.

### `jasmine-namespace-without-entry` — то, которому нужен `setupModules` {#jasmine-namespace-without-entry-—-the-one-that-needs-setupmodules}

`.and`, `.calls` и `.withArgs` — не члены спая, который строит эта библиотека; их ставит
`vitest-auto-spy/jasmine` или `enableJasmineCompat()` на рантайме, который его импортировать не может.
У спая, построенного до этого вызова, их нет, и спека умирает на
`Cannot read properties of undefined (reading 'returnValue')` — что не называет ни недостающего импорта,
ни спая.

Ставит ли слой **проект**, по одному файлу не узнать: вызов обычно сидит в записи `setupFiles` Vitest,
которую не импортирует ни одна спека. Поэтому вопрос сужается до того, на что один файл может ответить
честно: «этот файл использует namespace на спае, **который построил сам**, и сам не ставит ничего». Это
всё ещё сужение, а не доказательство, и поэтому именно это правило и `no-unregistered-inject-spy` —
те два, которые могут срабатывать на корректном проекте. До 4.0.0 ответом на это был `warn`; теперь это
`error`, потому что предупреждение, которое никто не читает, — не запас прочности, а настоящая починка
находится в одной опции. Два аварийных выхода: импорт любой точки входа, которая _не может_ загрузить
jasmine-вариант (`vitest-auto-spy/bun`, `…/node` — они неизбежно ставят слой из setup-файла), глушит
файл, а проект может назвать собственный setup-модуль:

```js
{
  rules: {
    'vitest-auto-spy/jasmine-namespace-without-entry': ['error', { setupModules: ['./test-setup'] }],
  },
}
```

### `no-save-arguments-by-value` — самый чистый молчаливый случай на этой странице {#no-save-arguments-by-value-—-the-purest-silent-case-on-this-page}

`spy.calls.saveArgumentsByValue()` здесь **no-op**, и сознательно: jasmine защитно копирует аргументы
каждого вызова, Vitest, Bun и `node:test` все держат ссылку, а снимать снимок с каждого аргумента каждого
вызова ради совпадения обложило бы налогом каждый спай в сюите. Вызов при этом выполняется. Ничего не
падает. А спека, попросившая аргументы _такими, какими их передали_, теперь читает то, что проверяемый
код оставил в объекте потом, — утверждение о состоянии на момент вызова превратилось в утверждение о
состоянии на момент проверки, и ни дифа, ни предупреждения, ни падающего прогона, которые бы на это
показали.

### `prefer-native-spy-api` — то, которое выключают на время переезда {#prefer-native-spy-api-—-the-one-to-switch-off-while-you-migrate}

Оно рапортует про код, который **работает**. Слой совместимости — это то, на чём сюита работает, _пока_
её переносят, так что в первый день переезда оно срабатывает на каждой строке моста. Ровно поэтому до
4.0.0 оно поставлялось в `off`; теперь это `error`, потому что большинство сюит не посреди переезда, а
тем, кто посреди, нужна ровно одна строка на всё время, пока мост нужен:

```js
{ rules: { 'vitest-auto-spy/prefer-native-spy-api': 'off' } } // пока сюита не позеленеет
```

Удалите эту строку на последней миле — и правило становится инструментом, который доводит дело до
конца:

`eslint --fix` тогда делает те переименования, чьего получателя он может проследить до одной из фабрик
этой библиотеки: `.and.returnValue(x)` → `.mockReturnValue(x)`, `.and.callFake(f)` →
`.mockImplementation(f)`, `.and.nextWith(v)` → `.nextWith(v)` и девять других делегированных хелперов,
`.withArgs(a).and.returnValue(v)` → `.calledWith(a).mockReturnValue(v)`, `.calls.count()` →
`.mock.calls.length`, `.calls.reset()` → `.mockClear()`, `.calls.argsFor(i)` → `.mock.calls[i]`. Везде
ещё та же правка предлагается **подсказкой**, потому что `.calls` на чужом объекте — чужой метод; ту же
лицензию берёт себе и [`no-mocked-for-spy`](#which-rules-fix-and-why-so-few).

Трёх вещей оно сознательно не перепишет. Стратегии без эквивалента — `.and.returnValues`,
`.and.callThrough`, `.and.stub`, `.and.throwError`, `.and.resolveTo` — в его таблице нет вообще, потому
что нет переименования, которое сказало бы то же самое. `.calls.mostRecent()` и `.calls.all()` вне игры
по той же причине: нативная форма — не одно выражение. И цепочка с **опциональным звеном** не трогается
совсем: замена строится из текста получателя плюс имени члена, так что `spy?.and.returnValue(1)`
вернулся бы как `spy.mockReturnValue(1)` — тот же вызов с молча убранной защитой.

`npx vitest-auto-spy codemod --from jasmine` делает всю сюиту за один проход, включая то, от чего это
правило отказывается. См. [Переезд с jasmine-auto-spies](/ru/migrating-jasmine).

## Какие правила чинят и почему их так мало {#which-rules-fix-and-why-so-few}

Три из двадцати переписывают исходник сами, восемь предлагают переписывание подсказкой, и разделение это
про цену неверной догадки, а не про сложность переписывания.

`no-mocked-for-spy` трогает только **объявление**. Ошибись оно — и файл перестанет компилироваться, а
это самое громкое и самое дешёвое падение из имеющихся у кодовой базы, — поэтому оно одно из трёх
правил, работающих под `--fix`, и делает правку целиком:

```ts
// до
import { Mocked } from 'vitest';
let cart: Mocked<CartService>;

// после --fix
import type { Spy } from 'vitest-auto-spy';
let cart: Spy<CartService>;
```

Импорт `Mocked` уходит, когда переименование оставляет его сиротой, — вместе с объявлением, когда он был
последним специфером, и из скобок, когда не был. И правило отступает там, где не может доказать
переименование: `Mocked`, объявленный самим файлом, — не из Vitest, `Spy`, уже связанный с чем-то другим,
— не свободен, а `Mocked<{ total: Mock }>` спрашивает у системы типов не то, на что отвечает `Spy<T>`.
О таком всё равно сообщается, но без правки.

::: warning «Решается по объявлению» — не то же самое, что «решается по файлу»
Эту лицензию однажды прочитали слишком вольно, и правило выпустило код, который не компилировался.
Объявление решается; а вот что имени _присвоят_ несколькими строками ниже — отдельный вопрос:

```ts
let register: Spy<Pick<Registry, 'metrics'>> & { contentType: string }; // ← что написал --fix
register = { contentType: '…', metrics: vi.fn().mockResolvedValue(payload) }; // ← что он оставил
// TS2322: Type 'Mock<Procedure>' is not assignable to type
//   'AddSpyMethodsByReturnTypes<() => Promise<string>>'
```

`eslint --fix` отчитался чисто, а типовые ворота упали следом — худшая форма автофикса, потому что
собственная проверка правила проходит и ничто не показывает обратно на него. Поэтому простая правка
выживает только там, где значение пришло из собственных фабрик этой библиотеки (`createSpyFromClass`,
`createAutoMock`, `createMock`, `mockDeep`, `injectSpy`, `asSpy`, …), которые и так возвращают `Spy<T>`.
Везде ещё та же правка предлагается **подсказкой**, чтобы принять её вместе с починкой места создания —
обычно `createAutoMock<T>()` вместо литерала.

Аннотация, не принадлежащая никакой переменной, — параметр, тип возврата, выражение `as` — сохраняет
простую правку, и это же не даёт `--fix` переписать объявление, оставив под ним каст, всё ещё
написанный как `Mocked`.
:::

`prefer-as-spy` получает ту же лицензию с другого конца: каст, о котором он сообщает, — это собственное
утверждение разработчика, что значение является `Spy<X>`, а `asSpy` — типизированная функция
тождества, так что переписывание сохраняет это утверждение целиком, меняет только его написание и живёт
целиком на уровне типов. Знать что-то про другой файл не нужно, потому что правило ничего не решает:
решил каст, а неверная правка не скомпилируется.

```ts
// после --fix
import { asSpy } from 'vitest-auto-spy';

// до
devicesService = TestBed.inject(DeviceListService) as Spy<DeviceListService>;

devicesService = asSpy<DeviceListService>(TestBed.inject(DeviceListService));
```

Типовые аргументы переносятся, а не отдаются на вывод. У `Spy<T, Options>` и `asSpy<T, Options>` один и
тот же список параметров, так что перенос — это транспозиция, и строка после правки утверждает ровно то
же, что и до неё, — включая `Spy<Cinemas, { overload: 'first' }>`, который вывод молча потерял бы. Это
сохраняет и единственный случай, где вывод активно неправ: на **дженерик**-классе `TestBed.inject`
отвечает `Service<any>`, и этот `any` всплывает восемью уровнями ниже как несовпадение между
`AddPromiseSpyMethods<unknown>` и `WithMockReturnValue<…>`, причём в сообщении ничто не показывает на
спеку.

Две формы намеренно не трогаются. `Spy`, объявленный самим файлом, — не тип этой библиотеки, а каст,
прыгающий через `unknown` — `{} as unknown as Spy<CartService>` — прямо говорит, что значение _не_
`CartService`, так что `asSpy<CartService>(...)` не скомпилировался бы; такой форме нужен настоящий дубль
(`createAutoMock<T>()`), а не переименование. Единственное исключение —
`TestBed.inject(X) as unknown as Spy<X>`, где контейнер по построению возвращает `X`, а `as unknown` был
там только чтобы заглушить `TS2352`: вот это чинится вместе с прыжком.

Остальные три меняют **поведение**, ради чего они и существуют, и поэтому только подсказывают. Найдёт ли
`injectSpy(X)` вообще какой-нибудь спай, решает `provideAutoSpy(X)`, который обычно живёт в другом файле.
`mockValueProp` оставляет свойство writable и configurable там, где `Object.defineProperty` его
запечатал, — и подсказка выбирает тот хелпер, которого просит дескриптор: `mockValueProp` для
`{ value }` и `mockReadonlyPropGetter` для `{ get }`. А `no-expect-in-subscribe` переписывает тест
целиком:

```ts
// ❌ что породил механический переезд с jasmine-колбэка done
it('maps the products', () =>
  new Promise<void>((done) => {
    service.getProducts(id).subscribe((products) => {
      expect(products).toEqual(expected);
      done();
    });
  }));

// ✅ что получается, если принять подсказку
it('maps the products', async () => {
  const products = await firstValueFrom(service.getProducts(id));

  expect(products).toEqual(expected);
});
```

Этот один шаблон дал 111 из 133 нарушений в партии из 22 переехавших файлов, так что распознаватель себя
оправдывает. Предлагается он только для точно такого каркаса — одна инструкция `subscribe` в исполнителе
промиса, один колбэк с блочным телом, `done` упомянут один раз и вызван последним, — потому что всё
остальное в исполнителе обычно и есть инструкция, которая _запускает_ источник, а она должна выполняться,
когда кто-то уже слушает. Редактор предлагает все три; принимает их человек.

`no-overridden-provider` и `no-import-time-spread` подсказывают по той же причине с другого конца: у
каждого ровно одна форма, чья починка локальна. У первого это дословный дубликат, где удаление доказуемо
безвредно ([выше](#the-pair-is-classified-because-the-two-halves-are-not-the-same-defect)); у второго —
отложить значение:

```ts
// ❌ вычисляется во время загрузки модуля — `[...undefined]` внутри бандла
export const webosEvents = [...BaseEvents];

// ✅ что получается, если принять подсказку; каждое использование имени обзаводится `()`
export const webosEvents = () => [...BaseEvents];
```

Последняя — подсказка в самом сильном смысле: принять её значит заставить тайпчекер назвать каждую точку
вызова, которую надо изменить, и именно поэтому никакой `--fix` не имеет права делать это без присмотра.
Другая безопасная починка — заинлайнить константу, чтобы для этой строки ничего не надо было
импортировать, — из одного файла вообще не пишется.

У оставшихся пяти правки на узел нет. `createSpyFromClass` нужен класс, которого объектный литерал
никогда не называет, `provideAutoSpy` выбрасывает возвращаемые значения, которые настраивало тело
`useValue`, а `Object.defineProperties` — это по одной инструкции `mockValueProp` на запись. Каждая из
них — правка по файлу, а не по узлу.

## Измерено: чего стоит каждое правило {#measured-what-each-rule-is-worth}

Каждое обоснование выше — утверждение о том, что делает прогон, поэтому каждое прогнали. Vitest 4.1.9,
собственные конфиги этого репозитория — дефолтный проект, `vitest.shared-env.config.mts` для
`isolate: false`, zone-проект для половины с zone.js, — по одной пробной спеке на правило, и в каждой
ассерт, который не может быть истинным.

| Правило                        | Без него прогон говорит                                                                                                                                                                                                                                          | Вердикт |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-----: |
| `no-expect-in-subscribe`       | ничего — [4 формы из 4 зелёные на 4 поведениях потока](/ru/core/observable-assertions#measured-four-forms-against-four-streams)                                                                                                                                   | зелено  |
| `no-done-callback`             | ничего, когда `done()` сидит в колбэке: тело возвращает `undefined`, тест кончается, ассерт приземляется после него                                                                                                                                               | зелено  |
| `no-floating-assertion`        | zoneless: `Unhandled Rejection`, код 1, ни один тест не назван. Под zone.js: один из двух реджектов исчезает совсем                                                                                                                                               | зелено  |
| `no-bare-called-with`          | ничего — спай отвечает `undefined` на эти аргументы, что он делал и до того, а тест, собиравшийся проверить вызов, не проверяет ни одного                                                                                                                        | зелено  |
| `no-shared-module-level-mock`  | ничего — собственное состояние фикстуры переезжает между файлами при `isolate: false`                                                                                                                                                                             | зелено  |
| `no-object-define-property`    | ничего в файле, который патчил; **следующий** файл читает пропатченное значение                                                                                                                                                                                   | зелено  |
| `no-mocked-for-spy`            | `TS2322 … missing the following properties from type 'CartService': http, cache`                                                                                                                                                                                 | компиляция |
| `prefer-create-spy-from-class` | `TypeError: cart.applyPromo is not a function`                                                                                                                                                                                                                   | красно  |
| `prefer-provide-auto-spy`      | то же самое, одним прыжком DI дальше                                                                                                                                                                                                                             | красно  |
| `prefer-inject-spy`            | `spy.getPlans.nextWith is not a function`                                                                                                                                                                                                                        | красно  |
| `no-inject-before-override`    | `Cannot override provider when the test module has already been instantiated. Make sure you are not using \`inject\` before \`overrideProvider\``                                                                                                                | красно  |
| `no-overridden-provider`       | ничего — там, где самодельный дубль случайно отвечает: стоящий рядом `provideAutoSpy` мёртв, а ассерты проходят. Прочитайте обратно через `injectSpy` — и станет красно, причём [`injectSpy` объясняет почему](/ru/adapters/angular#injectspy-says-when-it-got-the-real-thing) | зелено  |

Важна последняя колонка. Шесть из одиннадцати проверенных здесь защищают от теста, который **зелёный и
неправильный**, а это единственный режим отказа, о котором сюита не может отчитаться сама; четыре
защищают от красного теста, чьё сообщение и так понятно; одно — ошибка компилятора. Именно это
разделение показывает колонка _Без него_ в [Правилах](#rules), и раньше за ним следовала ещё и
серьёзность — пока 4.0.0 градуировал конфиг на `error` / `warn` / `off` вдоль него. Больше нет:
насколько громкой должна быть находка, решает проект, а эта таблица — свидетельство для решения, а не
само решение.

[Четырёх jasmine-правил](#the-four-jasmine-rules) в этой таблице нет, потому что их не проверяли тем же
способом — их предмет переезд, а не поведение раннера. Два из них по построению относятся к зелёной
стороне, и исходники говорят это прямо: `saveArgumentsByValue()` — функция, чьё тело `undefined`, а
вызов настоящего метода по умолчанию у `vi.spyOn` — документированное поведение, а не дефект.

`no-overridden-provider` — то, чей вердикт зависит от остального файла, и поэтому его стоит иметь
правилом, а не рантайм-проверкой. Прочитайте токен обратно через `injectSpy` — и прогон красный, с
диагностикой, называющей причину; прочитайте через `TestBed.inject` и проверяйте против самодельного
дубля — так и сделал файл, породивший это правило, — и всё проходит, пока стоящий выше `provideAutoSpy`
не выполнялся никогда.

### `no-done-callback` — чем на самом деле является первый параметр {#no-done-callback-—-what-the-first-parameter-actually-is}

Этот параметр — не `undefined` и не простой объект. Vitest 4 передаёт **вызываемый** `TestContext`:

```text
typeof done                → 'function'
Object.keys(done)          → signal, task, skip, annotate, onTestFailed, onTestFinished
done()                     → Error: done() callback is deprecated, use promise instead
```

Так что синхронный вызов ловится, громко и по имени. Это форма, которую никто не пишет. Форма, которой
полна каждая Jasmine-сюита, ставит `done()` в конец колбэка:

```ts
it('loads', (done) => {
  setTimeout(() => {
    expect(1).toBe(999); // ← бросает здесь, так что до done() дело даже не доходит
    done();
  }, 0);
});
```

Тело возвращает `undefined`, так что тест кончается раньше, чем сработает таймер. Измерено: **зелено**,
а `AssertionError` прилетает потом одной из необработанных ошибок прогона, и до ошибки об устаревании
дело не доходит вовсе. Правило существует потому, что громкий случай — редкий.

`done.fail(…)` тоже рапортуется — по месту вызова, а не по параметру. Это канал падения из jasmine, а у
`TestContext`, который передаёт Vitest, никакого `fail` нет, так что строка бросает
`done.fail is not a function` — и бросает _там, где стоит_, то есть почти всегда в колбэке `error` или в
`.catch()`, то есть внутри промиса, которого никто не дождался. Реджект необработан, тело теста давно
вернулось, а прогон **зелёный ровно на том пути, который должен был его уронить**. Проверяйте падение
иначе: `await expect(firstValueFrom(source$)).rejects.toMatchObject({ status: 404 })` или
`expect.fail(message)` там, где строка просто недостижима.

### `no-floating-assertion` — три раннера, три разных вида молчания {#no-floating-assertion-—-three-runners-three-different-silences}

Те же два теста — `expect()` в `.then()`, которого никто не дождался, и `async`-хелпер, вызванный без
`await`, — в трёх конфигурациях:

|                                                     |          тесты           | что рапортует раннер                                          |
| --------------------------------------------------- | :----------------------: | ------------------------------------------------------------- |
| zoneless                                            |     **2 прошли**         | 2 `Unhandled Rejection`, код 1, ни один не приписан тесту     |
| zone.js                                             |     **2 прошли**         | 1 ошибка — второй реджект zone.js слил в `console.error`      |
| zone.js + `setupAutoSpy({ strayRejections: true })` | **1 упал \| 1 прошёл**   | проглоченный теперь именованное падение на нужном тесте       |

Читайте среднюю колонку сверху вниз: ассерт ложен в каждой строке, а тест зелёный в каждой, кроме
последней. `strayRejections` — это то, что превращает случай, которого не увидит ни один селектор —
`expect()`, припаркованный в `setTimeout` внутри `.then()`, — обратно в падение с именем теста.

### `no-shared-module-level-mock` — один модуль, два файла {#no-shared-module-level-mock-—-one-module-two-files}

Фикстура несёт стабильный id, так что спорить о том, общий ли модуль, не приходится:

```ts
// пробная фикстура, импортируемая двумя файлами спек
export const analytics = { sent: [] as string[], track: vi.fn((e: string) => analytics.sent.push(e)) };
export const moduleLoadId = `${Date.now()}-${Math.random().toString(36).slice(2, 8)}`;
```

```text
isolate: true    file 1: load=…-mdncyn     file 2: load=…-ywp3q0   sent=[]
isolate: false   file 1: load=…-n0v4yh     file 2: load=…-n0v4yh   sent=[from-file-1]
```

Один и тот же id, значит, одно вычисление, и файл 2 читает то, что положил файл 1. Обратите внимание,
**что** утекло: не вызовы спая — `clearMocks: true` до `vi.fn()` уровня модуля действительно дотягивается
и действительно их чистит, об этом сказали три отдельные пробы. Утекает всё остальное, что фикстура
держит рядом со своими спаями, — поэтому починка это фабрика, а не `beforeEach`, который чистит усерднее.
Какой файл пойдёт первым, решает раннер, так что падение приходит как флакающее.

### `no-object-define-property` — дескриптор никто не возвращает {#no-object-define-property-—-nothing-puts-the-descriptor-back}

Один файл патчит глобал так, как это обычно делает спека, и затем вызывает всё, что раннер предлагает
для отката:

```ts
Object.defineProperty(navigator, 'onLine', { value: false, configurable: true });

vi.restoreAllMocks();
vi.resetAllMocks();
vi.unstubAllGlobals();
```

```text
after every restore the runner offers: onLine=false   ← same file
onLine=false                                          ← the next file
after restoreMockedProps: onLine=true                 ← mockValueProp, run on its own
```

Третья строка — это починка, и измерена она отдельно не просто так: запустите её **после** файла с
`defineProperty` в том же воркере, и она тоже прочитает `false`. Исходный дескриптор пропал раньше, чем
правильный хелпер вообще увидел свойство, — от такого сюита не может оправиться по файлу за раз, и
поэтому это `error`, а не `warn`.

### Три правила `prefer-*` — расхождение и одна строка, отменяющая провайдера {#the-three-prefer-rules-—-drift-and-one-line-that-undoes-a-provider}

Написанный руками дубль корректен в тот день, когда его написали. Потом у класса появляется метод:

```text
F1  hand-written { total: vi.fn() }        → TypeError: cart.applyPromo is not a function
F2  createSpyFromClass(CartService)        → follows the class, no edit
```

И система типов тут не помогает, потому что дубль изначально не удовлетворял классу, — а прячет это как
раз стоящий перед ним `as unknown as CartService`:

```text
TS2741: Property 'rate' is missing in type '{ total: Mock<Procedure>; add: Mock<Procedure>; }'
        but required in type 'CartService'.
```

`no-mocked-for-spy` — то же сообщение шагом в сторону. `Mocked<T>` требует приватных полей, которых у
спая нет, и говорит об этом словарём класса, а не словарём ошибки:

```text
TS2322: Type 'Spy<CartService, SpyOptions>' is not assignable to type 'Mocked<CartService>'.
        Type 'Spy<CartService, SpyOptions>' is missing the following properties
        from type 'CartService': http, cache
```

Ничто в этом не называет `Mocked` — поэтому правило чинит объявление, а не объясняет ошибку.

`prefer-inject-spy` — самое острое из трёх, потому что это одна строка, тихо отменяющая провайдера:

```ts
TestBed.configureTestingModule({ providers: [provideAutoSpy(BillingPlansService)] });

const service = TestBed.inject(BillingPlansService);
vi.spyOn(service, 'getPlans'); // ← заменяет метод auto-spy обычным vi.fn()

injectSpy(BillingPlansService).getPlans.nextWith(['PRO']);
// TypeError: spy.getPlans.nextWith is not a function
```

Провайдер по-прежнему auto-spy; метод на нём — уже нет, так что все observable- и promise-хелперы на нём
пропали. Прочитайте ту же зависимость через `injectSpy(BillingPlansService)` — и `nextWith` работает: это
вторая проба, и она эмитит `["PRO"]`.
