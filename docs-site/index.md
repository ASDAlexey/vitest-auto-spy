features:
  - icon: 🎯
    title: Every method, from the real prototype
    details: createSpyFromClass reads the class, so the double has the methods the class has — including the overloads a generated API client would otherwise collapse onto the last signature, the one nobody calls — and each method's only call signature is its own, so a call the real method rejects does not compile on the double, where a Mock-based surface used to accept any arguments at all. A deep Proxy answers every property, so a typo in a mocked method name never fails there; onlyMethodsToSpyOn here reports a name that is not on the prototype. strict, per double or per suite, turns the forty-first method nobody configured from an undefined that fails three frames later into a throw naming the class, the method and the arguments. Every double is Disposable, so using spy = createSpyFromClass(X) retires the afterEach that existed only to reset it. No class to read? createAutoMock&lt;T&gt;() and recursive mockDeep&lt;T&gt;() work from the type alone, and createMock&lt;T&gt;() returns the spy-free data shape a test only reads — with createFixtureFactory&lt;T&gt;() for the one a whole suite shares, checked once as a complete T and stamped into a fresh copy per test. And where the object already exists and other code already points at it — a service a factory built, a third-party client, a half-real TestBed.inject(X) — createSpyFromInstance patches that object in place instead of building a rival, so every closure, container and subscription that captured it first sees the spies; every write is journaled, so restoreSpiedInstance(client) hands the real methods back mid-test and using restores rather than resets. vi.mockObject is Vitest-only, sinon.createStubInstance builds a new object from a constructor rather than patching the one you hold, and bun:test and node:test have nothing.
    link: /core/create-spy-from-class
  - icon: 🎛️
    title: Helpers that follow the return type
    details: A method returning a Promise gets resolveWith / rejectWith, one returning an Observable gets nextWith / throwWith, and every method gets calledWith, mustBeCalledWith and failWith. failWith is the throw the runner cannot express; Vitest 4.1's mockThrow covers a whole spy, Bun and node:test have nothing, and no runtime can make one set of arguments throw while the rest answer — cart.checkout.calledWith(BAD_ID).failWith(err) does, and it supersedes whatever resolveWith or nextWith configured before it, so the outcome never depends on line order. Only jest-auto-spies has the rest of this, and it is Jest-only — the deep-Proxy libraries hand you one mockReturnValue for all three cases and no argument dispatch at all. A mustBeCalledWith mismatch prints both sides, with every configured call listed and its matchers shown, because the diagnosis is the comparison and not either half of it. That fires on the call that breaks; explainSpy, on the /diagnostics entry, answers the same question on demand while the test is red for some other reason — every configured argument list numbered next to every recorded call, each call attributed to the config it hit or to the default it fell through to, and the two states a reader most often arrives in said outright rather than left to be inferred — nothing configured, and N calls with none matched. No runner has this; vi.fn() hands back mock.calls and nothing joins it to the configuration, and the deep-Proxy libraries have no configuration to join it to.
    link: /core/control-helpers
  - icon: 🔀
    title: One core, three runtimes, five frameworks
    details: The core never imports your runner. vi.fn() and its equivalents sit behind a MockAdapter that each entry point registers on import, so the same spec code runs on Vitest, bun:test and node:test — only native mock methods stay the runner's own. Angular, NestJS, React, Vue / Pinia and Svelte have their own entry points on top of it, and rxjs stays opt-in behind a subpath, in the declarations as well as at runtime. On NestJS, createNestUnit builds the class under test from the metadata Nest already emits, with every unprovided token spied and expose for collaborators built for real — the solitary and sociable model of @suites/unit, over a spy that reads the real prototype.
    link: /runtimes/vitest
  - icon: 🧹
    title: node:test stops retaining every spy
    details: Node's own runner pushes every mock.fn() onto the private array of one process-wide MockTracker and never removes an entry — reset() is the only method that empties it, and it restores and forgets the mocks your spec made by hand along with the library's. So a dropped spy stays reachable for the life of the process, and so does every argument it recorded. This project's docs used to say there was no library-side fix because the tracker is global; that was wrong, and trackNodeMocks() is the correction. MockTracker is an ordinary class reachable as mock.constructor, and the adapter already took its tracker as a parameter, so the library creates its spies on a tracker it owns and replaces that tracker after every test — the retired one is collected with everything in it. Measured on Node v24.19.0 with forced collections, 20 000 spies of a 10-method class across 20 tests, dropped — 124.5 MB retained before, 5.9 MB after, against a 5.4 MB baseline. It is opt-in, idempotent and reversible, it never calls mock.reset(), and because mock.constructor is not documented API the constructed tracker is probed before a single spy is routed at it — on any runtime that will not give the class up it is a no-op and spies keep going exactly where they go today.
    link: /runtimes/node
  - icon: ⚙️
    title: Getter and setter spies, including where Bun refuses
    details: bun:test's own spyOn(obj, 'prop', 'get') throws — "does not support accessor properties yet", verified on Bun 1.4.0. And no library that generates a double from a class or a type has accessor spies at all, on any runner — not ng-mocks, spectator, @testing-library/angular, vitest-mock-extended, @golevelup or Suites. @testing-library/angular is the readable case — its /vitest-utils createMock, the direct overlap with createSpyFromClass, assigns a mock only where typeof descriptor?.value is 'function', and a getter's descriptor has no value, so accessors are dropped without a word while its Mock&lt;T&gt; type still declares them callable; re-read in the 19.4.2 tarball on 2026-09-02. accessorSpies never calls the runner's spyOn. It redefines the property with a mock built by the adapter and preserves the half it is not replacing, so getters and setters behave identically on Vitest, Bun and node:test.
    link: /comparison#_1-accessor-spies-on-bun
  - icon: 🅰️
    title: Angular's TestBed under bun test
    details: Bun ships no DOM and cannot resolve templateUrl, so Angular specs simply do not run there — no other library in the field claims otherwise. One preload installs a DOM, inlines external templates and styles through a Bun.plugin hook, and boots a zoneless TestBed. provideAutoSpy, injectSpy and the zoneless waits come from one bun-angular entry point and read the same as they do on Vitest.
    link: /runtimes/bun-angular
  - icon: 📏
    title: Nineteen lint rules, underlined as you type
    details: Nineteen flat-config rules versioned together with the API they recommend, each message linking to its recipe. Ten of them catch a test being wrong rather than verbose — an expect() inside subscribe(), an expect() in a .then() nobody awaits, a bare spy.m.calledWith(x); that configures a stub and asserts nothing (no-bare-called-with) — the trap Vitest 4.1's chai-style expect(fn).to.have.been.calledWith made likely, same word, opposite meaning — an Object.defineProperty nothing restores, a module-level mock shared across files, a done callback that makes a test pass having run almost none of its body, a jasmine spyOn whose rename silently starts calling the real method. Three rewrite the source under --fix and seven offer the rewrite as a suggestion, because a fix that silences the rule while the type gate still fails is worse than no fix. No editor plugin of their own — WebStorm runs them natively, VS Code, Cursor and Windsurf through the ESLint extension.
    link: /utilities/eslint-plugin
  - icon: 🧭
    title: Signals and resources a spec can drive
    details: mockSignalProp replaces a signal-valued property with a real WritableSignal and hands back the writable half, so a computed downstream recomputes and an effect runs. runEffect() runs one effect body on demand when its trigger is now static. httpResource() and resource() need a different wait each — measured on 21.2.17, an httpResource settles one tick plus one microtask after its response is flushed, a plain resource() takes two rounds, and neither has issued a request until something ticks. Get it wrong and nothing fails — the spec asserts the resource's default value and passes. settleResource() is the one wait both converge under, mockResourceProp drives a resource with no HTTP in flight at all, and toHaveResourceValue refuses to compare an unresolved resource even when its default happens to match.
    link: /adapters/angular#resources-httpresource-and-resource
  - icon: 🌐
    title: httpResource in two lines
    details: httpResource() is Angular's flagship data primitive and nothing in the field has an answer for it — no helper in ng-mocks, none in Spectator, none in @testing-library/angular. What a spec has instead is a six-step dance whose order is not guessable; tick, because a resource created in an injection context has issued nothing until something does, inject the HttpTestingController, expectOne, flush, let one microtask run so the response reaches the resource, tick again so the view reading it is current. Miss the first and expectOne reports a request that was never sent; miss the fifth and the assertion reads the resource's default value and passes, proving nothing until the day the default changes. await expectRequest('/api/products').flush([product]) is all six, and products.value() reads on the next line — with no tick, no await Promise.resolve() and no detectChanges() of the spec's own. provideHttpTesting() is provideHttpClient() and provideHttpClientTesting() in one spread, and it fails by default any test that ends holding a request nothing answered, naming it instead of letting it leak into the next test. Match by URL, by pattern or by a predicate over the request, and read the requests that were actually made off the failure when nothing matched. It lives behind its own 2.2 kB subpath because it is the only part of the package that imports @angular/common — an optional peer, so vitest-auto-spy/angular keeps loading in a project that does not have it.
    link: /adapters/angular-http
  - icon: ⚡
    title: Less TestBed, and proof of what was injected
    details: renderShallow collapses the shallow-TestBed copy-paste into one call, and what that saves is however much markup the component owns. It is flat in the number of children because it never builds the subtree, while TestBed.createComponent scales linearly with it — so a table or a dashboard gains, and a childless leaf has nothing to give up, where the per-test overrideComponent can cost more than it saves. A whole spec file also pays for imports, the module and the assertions, none of which shallow rendering touches, so a per-render ratio is the upper bound on what a file can gain rather than a prediction of it — enableTestBedDiagnostics() is how to find the files where that bound is worth chasing. keepTemplate true is the middle rung for a spec that needs a viewChild or content projection — the component's own template with every child in it resolving to nothing under NO_ERRORS_SCHEMA. On Vitest 4.1, extendWithAutoSpies turns the let + beforeEach + configureTestingModule block into one statement of typed test.extend fixtures — a test that never names a dependency never builds it, and on an older Vitest the call refuses up front instead of handing every test undefined. createWithAutoSpies builds a class through DI with every unprovided token spied, while spies.get(token) refuses one the instance never asked for — the base class, or a service a refactor removed — instead of minting a spy the instance never sees, so the wrong stub fails at the stub rather than three frames into the code under test. overrideComponentProvider reaches a dependency a component declares in its own providers, which a testing module cannot, and it verifies on the next fixture that the override actually applied rather than silently doing nothing. Two assertions cover the AOT test bundle that makes all of this necessary — assertNgModuleScopes for an imported NgModule whose runtime scope the bundler stripped, and assertComponentDefIntact for a component whose own providers were baked with a hole in them because the barrel chunk holding one of them had not run yet — which Angular otherwise reports half an hour later as Cannot read properties of undefined (reading 'provide'), from inside its own provider resolution, in a spec nobody touched. trackInjections answers the question most vi.mock() calls were really asking, which collaborators the entry point actually asked for, by registering them as provider factories and reading back the ones that fired — an assertion that survives a bundler removing the module boundary a mock would have needed.
    link: /adapters/angular#shallow-component-rendering
  - icon: 🩺
    title: Four Angular failures that pass quietly
    details: enableAngularDiagnostics() turns four silences into failures in one setup line — a testing module importing an NgModule that contributes nothing at all, schemas sitting next to a standalone component where they can never apply, injectSpy handed a real instance instead of a spy, and a test that ends with unflushed HttpTestingController requests. The third is the one nothing else looks for. injectSpy already warns once per token, naming the token and the provideAutoSpy call that is missing, and the group raises that warning to a failure — where spectator declares inject&lt;T&gt;(token) as SpyObject&lt;T&gt; whether the token was mocked or not, so the compiler hides the mistake until a real method meets .mockReturnValue somewhere else entirely.
    link: /adapters/angular-diagnostics
  - icon: 📡
    title: Assertions that fail on silence
    details: expectEmission / expectEmissions / expectNoEmission replace the expect() inside a subscribe callback that never runs — the assertion is the await, so a stream that stays quiet fails the test instead of passing it. Duck-typed, so no rxjs is pulled in. assertMocked does the same job one level up, where a vi.mock() specifier did not match under a bundler and the spec has been asserting against the real module all along, and moduleNamespace gives a factory the shape an interop probe recognises.
    link: /core/observable-assertions
  - icon: 🫥
    title: When a green suite is lying
    details: zone.js replaces the global Promise and drains a rejection nobody handled into console.error and no further — it never reaches the channel Vitest listens on, so the runner is never told and the file still exits 0. strayRejections fails the test the rejection surfaced in. strayTimers cancels the setTimeout a file left running so it cannot fire inside the next one, and with Vitest 4.1's --detect-async-leaks on it says how many it took away — cancelling in afterAll would otherwise empty that leak report silently — while onStrayTimers hands the count to the spec, so expect(cancelled).toBe(0) is one line. One migrated monorepo of 1688 spec files and 11 587 tests, green, was hiding six real defects of that shape, two of them assertions that were simply false. npx vitest-auto-spy doctor reads the other half — a tsconfig include pattern that matches no file, so it type-checks nothing while tsc --noEmit still reports success. On the suite that motivated it, nine of 152 spec tsconfigs still covered their specs. It also names the coverage settings that cost without announcing it; the docs carry the provider wrapper that took one real shard from 229.59 s to 22.88 s with a byte-identical report, because @vitest/coverage-v8 caches the verdict of isIncluded and never the compiled matcher. Read-only, zero config, exit 1 in CI.
    link: /utilities/setup#_8-failing-on-a-rejection-zone-js-swallowed
  - icon: 🔀
    title: A jasmine suite that runs before it is rewritten
    details: jasmine-auto-spies and jest-auto-spies are siblings over one core, so every option name already matches — methodsToSpyOn, observablePropsToSpyOn, gettersToSpyOn, settersToSpyOn — and so does every helper. Exactly one thing differs, and it lands on every async line of every spec — upstream installs the helpers on functionSpy.and. vitest-auto-spy/jasmine puts .and, .calls and .withArgs back, adds createSpyObj and an importable jasmine namespace with the eight asymmetric matchers Vitest has no twin for, so changing the import specifier is the whole first step. Then the codemod takes the suite off it — thirteen transforms — and it refuses to blindly rename the one construct both dialects spell identically with opposite defaults, because jasmine's spyOn stubs the method where vi.spyOn calls through, so that rename silently leaves the real implementation running and the spec passes on whatever it returned. Two upstream defects are simply gone here — a write-only setter its discovery counts as a method and overwrites, and nextWithValues silently dropping a value of 0, null or empty string. The layer registers through the shared-state registry, so a suite that never asks for it pays one undefined check per spy and ships none of the code. And where the suite came through Angular's own refactor-jasmine-vitest schematic instead — an object literal of one vi.fn() per method for every double, and a TODO comment on every createSpyObj it could not expand — createSpyFromClass(Api) closes all three TODO categories at once, because it reads the prototype and never sees a method list.
    link: /migrating-jasmine
  - icon: 🚪
    title: A way off @ngneat/spectator
    details: 739 852 downloads a month on a package whose repository returns 404, whose last release was 2025-11-02, and which does not resolve on a clean Angular 22 install — it imports BrowserDynamicTestingModule from @angular/platform-browser-dynamic/testing while declaring that package in neither dependencies nor peerDependencies. The migration page verifies each of those against the published tarball instead of repeating it, and corrects three claims that do not hold — the ngneat org still resolves, the deprecated Angular package still ships and still exports the symbol, and the @openng/spectator fork is neither byte-identical nor fixed on Angular 22; it carries the same undeclared import. createSpyObject becomes createSpyFromClass, mockProvider becomes provideAutoSpy, and spectator.inject becomes injectSpy — which reports a token you forgot to provide, where SpyObject&lt;T&gt; types every token as a spy whether it was mocked or not and hides the mistake until a real method meets .mockReturnValue somewhere else.   - icon: 🧪
    title: The 52 lines of @testing-library/angular that overlap
    details: The one migration page here that tells you to keep the library you came from. render, screen and the query set are a different discipline and none of that should move; what overlaps is a single secondary entry point, @testing-library/angular/vitest-utils, whose four exports fit in 52 lines. createMock becomes createSpyFromClass, provideMock becomes provideAutoSpy, and createMockWithValues maps onto the overrides seed rather than onto returns, because those values replace the member instead of configuring it. The page quotes that entry point in full — short enough that every claim on it can be checked in a REPL — and two defects come out of the quote. Its walk assigns a mock only where typeof descriptor?.value is 'function', so a getter is dropped without a word while Mock&lt;T&gt; still types it callable; and it recurses past Object.prototype, so hasOwnProperty, toString and valueOf come back on the double as vi.fn(). Verified against the published 19.4.2 tarball on 2026-09-04, by importing the module and printing what came back rather than by reading the code and predicting it.

  - icon: 🚚
    title: A migration you can verify
    details: Counters cannot answer whether a port lost a test — a file can lose a whole suite while a flake elsewhere starts passing, and the totals still match. compareTestRuns, on vitest-auto-spy/diagnostics, diffs the two sets of names from the JSON report both runners write, and diffByField turns a collapsed "…(8) to deeply equal" into the field that actually differs. npx vitest-auto-spy codemod does the edit half and declines the rest — it splits the legacy import across the entry points read off the installed package's own exports map rather than a table typed into the tool, transposes jest.Mock&lt;void, [Order]&gt; into the call signature Vitest takes instead of renaming it into the reverse meaning, and leaves every span it cannot decide byte-for-byte as it was, with a file and a line. Dry run by default, and --verify then checks the result by matching what should be gone, which still works on a file somebody migrated by hand. --from picks the dialect — jest-auto-spies, jasmine-auto-spies, or the default auto, which reads each file and applies the set that file needs.

  - icon: 📐
    title: Half the type-checker work, no runtime dependencies
    details: Deep-Proxy mocking is paid for at tsc time and nobody publishes the bill. On one fixture — an 80-member class, 30 mock declarations, 600 member touches — Spy&lt;T&gt; costs 2 656 type instantiations against @golevelup/ts-vitest's 5 092 and vitest-mock-extended's 5 614, while carrying more helpers on each method. Spies are lazy at runtime too, so a 40-method class costs 6.04 µs against 11.50 µs eager. Above roughly twenty methods lazySpies 'proxy' drops the placeholder per method for one trap object — an untouched 100-method double retains 4 097 B instead of 25 601 B, and under isolate false that is another 12% off a whole run's peak RSS, seven measured rounds out of seven. Zero runtime dependencies, with an in-tree arg serializer and opt-in subpaths keeping rxjs, zone.js and Angular out of your bundle — and, since 4.0.0, out of your type-checker as well; no published declaration names an rxjs type, which took 189 rxjs .d.ts files out of every React, Vue, Svelte and Node consumer's program, 303 files down to 114 on the same fixture, while a suite that has rxjs still gets rxjs's own Subject back from returnSubject(). 100% test coverage, on Node 22, 24 and 26 and on Bun 1.4.

  - icon: 🧰
    title: The rest of the toolbox
    details: The helpers that are not the headline but are why a suite stops flaking — setupFakeTimers / advanceTimers, which drain the microtasks a bare advanceTimersByTime leaves pending; flushEventLoop and settleDynamicImport for the queue the clock does not reach at all; fakeAsync and waitForAsync patched onto Vitest, behind their own specifier so a zoneless project never sees zone.js; mockConstructor / stubConstructor for a double the code under test calls with new, which vi.fn(() => instance) is not; IntersectionObserver, ResizeObserver, MutationObserver, media-element and AbortController stubs for the DOM the runner does not ship, behind vitest-auto-spy/dom-stubs since 4.0.0 so a Node service never evaluates them — measured at 0.159 ms of every spec file that does not import them; narrow / withOverrides / asInstances / captureArg for fixtures without casts, and createFixture / createFixtureFactory for the model eight specs would otherwise each keep a hundred-line copy of; console spies; and one setupAutoSpy() call for the hygiene a shared environment needs — including the guard that puts back an implementation another file's vi.resetAllMocks() dropped off a shared double, the cross-file failure that never reproduces on the file that caused it. And when CI moves to a new Node and eleven unrelated specs die on localStorage, restoreWebStorage() has already put it back — Vitest copies a DOM environment's globals behind a filter that lists Storage and neither localStorage nor sessionStorage, and they arrived only because Node put neither on globalThis; Node's own Web Storage made the key exist, so the filter started answering no and the environment's storage stopped arriving — setItem is not a function on Node 25.9, undefined on Node 26.7, under jsdom and happy-dom alike because the filter runs before either. Nothing else in this field repairs it, and no runner does. The repair decides by using the storage rather than by inspecting it — a namespaced key written, read back and removed — because Node 25 hands out a setItem that throws and the next runtime is free to invent a third shape; a storage that survives that is left exactly as it is, so a spec's own stub is safe, and a node environment gets nothing at all, which is what it is supposed to have. Every wait here is bounded and names its own cause.

  - icon: 📊
    title: Numbers you can re-run, including the ones it loses
    details: Nothing in this field publishes benchmarks at all — not sinon, not testdouble, not tinyspy, not jest-mock-extended, not ts-mockito, and there is no official Vitest-against-Jest figure from either team. This one publishes a dated table with every competitor version pinned, measured head-to-head in one process on one machine so the runner cancels out, and it publishes the rows it loses. Since 4.1 every micro-benchmark table is this package's, the narrowest margin 2.19× on the row where a test calls every method of the class it doubled — six of those rows were losses in 4.0, and what changed is that a method spy is no longer a vi.fn(), which also took a materialised method from 5 445 B of retained heap down to 1 929 B against the runner's own 5 169 B — and the row it still loses is published in the same table, because hand-written vi.fn() doubles are still cheaper across a whole suite under normal isolation — about three per cent at the median on the 4.1 build, where it used to be ten to fifteen. Roughly one and a half times faster than jest-auto-spies at suite scale, in every one of the fourteen measured rounds, on suites of a thousand to ten thousand tests and on both a twenty- and a hundred-method class — and jest-auto-spies, jasmine-auto-spies and the BugSplat fork are each measured directly rather than argued about, landing within a few per cent of one another because all three wrap the same core. Where it wins outright is memory once isolation is off, the setting that is itself worth about four times the wall-clock of any library choice — a hand-written double of a hundred-method class peaks at 6366 MB against 2103 MB for the default and 1851 MB with proxy-mode lazy spies, which is the difference between a job that finishes and one the kernel kills. The engine that made that possible is a switch, not a fork — setSpyEngine('runner') on vitest-auto-spy/setup puts the whole run back on vi.fn() per method, getSpyEngine() reports which one is armed, and the benchmark arm that proves the win is the same switch flipped; every other library in the table (jest-auto-spies 3.0.1, vitest-mock-extended 5.1.1, @golevelup/ts-vitest 4.0.0, @bugsplat/vitest-auto-spies 1.0.0) builds its doubles on the runner's own mock, so there is nothing there to switch. Two commands reproduce all of it, a monthly CI run re-measures it, and a Dependabot bump re-runs it the day a competitor ships.
