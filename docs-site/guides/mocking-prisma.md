# Mocking Prisma Client in Vitest

The usual recipe for unit-testing code that talks to Prisma is a deep mock of `PrismaClient`:
`prisma.user.findMany` is two property reads and a call, and a deep mock makes every hop exist without
writing it down. [`mockDeep`](/core/auto-mock-by-type#recursive-deep-mocks-—-mockdeep) is exactly that,
with the helpers each Prisma method earns from its return type — so a query answers with a typed
value, and a failure is one call rather than a hand-written implementation.

Everything below was run against a client generated by Prisma 7.10 from this schema:

```prisma
model User {
  id    Int     @id @default(autoincrement())
  email String  @unique
  name  String?
  posts Post[]
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  authorId Int
  author   User   @relation(fields: [authorId], references: [id])
}
```

## The service, and its seam

```ts
import type { PrismaClient } from './generated/client';

export class UserService {
  constructor(private readonly db: PrismaClient) {}

  async listNames(): Promise<string[]> {
    const users = await this.db.user.findMany({ orderBy: { id: 'asc' } });
    return users.map((user) => user.name ?? user.email);
  }

  async register(email: string): Promise<number> {
    try {
      const user = await this.db.user.create({ data: { email } });
      return user.id;
    } catch {
      return -1;
    }
  }
}
```

The client arrives through the constructor — a NestJS provider, a factory argument, anything that is
not a module-level singleton the code imports. That is the one design choice this recipe asks for,
and it is what lets the spec hand in a double without a `vi.mock` at all.

## The spec

```ts
import { asInstance, mockDeep, resetAutoSpy } from 'vitest-auto-spy';

import type { PrismaClient } from './generated/client';
import { UserService } from './users';

const prisma = mockDeep<PrismaClient>();

describe('UserService', () => {
  let service: UserService;

  beforeEach(() => {
    resetAutoSpy(prisma);
    service = new UserService(asInstance(prisma));
  });

  it('lists names, falling back to the email', async () => {
    prisma.user.findMany.resolveWith([
      { id: 1, email: 'ada@example.test', name: 'Ada' },
      { id: 2, email: 'bob@example.test', name: null },
    ]);

    await expect(service.listNames()).resolves.toEqual(['Ada', 'bob@example.test']);
    expect(prisma.user.findMany).toHaveBeenCalledWith({ orderBy: { id: 'asc' } });
  });

  it('reports a failed insert', async () => {
    prisma.user.create.rejectWith(new Error('Unique constraint failed on the fields: (`email`)'));

    await expect(service.register('ada@example.test')).resolves.toBe(-1);
  });
});
```

What each line is doing:

- **`mockDeep<PrismaClient>()`** — no generated mock file, no list of models. `prisma.user`,
  `prisma.post` and every delegate method come into being on first read, and each method is a spy
  with the full helper surface.
- **`resolveWith(rows)`** is typed by what the method returns. The value must be the rows Prisma
  would hand back, so a stale fixture — a renamed column, a string where the schema says `Int` — is a
  compile error in the spec, not a green test against data the database would never produce.
- **`rejectWith(error)`** makes the query reject. No `mockImplementation`, no cast.
- **`resetAutoSpy(prisma)`** in `beforeEach` walks the whole tree — every delegate, every method
  touched — and drops both recorded calls and configuration. One double for the file, clean for every
  test. [`using`](/core/create-spy-from-class#using) does the same at the end of a block, if you
  would rather build the double inside the test.
- **`asInstance(prisma)`** hands the double to code typed against the real `PrismaClient`; the deep
  mock's own type is a mapped type and is not assignable to it as written.

## A different answer per call

```ts
it('answers per call', async () => {
  prisma.user.findMany.resolveWithPerCall([{ value: [{ id: 1, email: 'ada@example.test', name: 'Ada' }] }, { value: [] }]);

  await expect(service.listNames()).resolves.toEqual(['Ada']);
  await expect(service.listNames()).resolves.toEqual([]);
});
```

`resolveWithPerCall` hands the n-th call the n-th entry — the shape of a poll, a retry or a
pagination loop — and is typed the same way `resolveWith` is.

## An answer keyed on the arguments

```ts
it('only the conflicting email fails', async () => {
  prisma.user.create.calledWith({ data: { email: 'taken@example.test' } }).rejectWith(new Error('Unique constraint failed'));
  prisma.user.create.resolveWith({ id: 7, email: 'new@example.test', name: null });

  await expect(service.register('taken@example.test')).resolves.toBe(-1);
  await expect(service.register('new@example.test')).resolves.toBe(7);
});
```

The rejection happens for that argument and no other, so the test can only pass if the code sent the
query it was supposed to — see [cause and effect](/core/control-helpers#cause-and-effect-why-calledwith-and-not-mockreturnvalue)
for why that is a stronger test than a blanket answer plus a `toHaveBeenCalledWith` at the end.
Arguments are compared by value with sorted keys, and asymmetric matchers work at any depth:
`calledWith({ where: { email: expect.stringContaining('@') } })`.

## Interactive transactions — `$transaction`

The callback form of `$transaction` hands the callback a transaction client, and the code under test
runs its queries through that. In a unit test the transaction client should be the same double, so
the queries land where the spec configured and asserts:

```ts
async moveTitle(fromId: number, toId: number): Promise<void> {
  await this.db.$transaction(async (tx) => {
    const post = await tx.post.delete({ where: { id: fromId } });
    await tx.post.create({ data: { title: post.title, authorId: toId } });
  });
}
```

```ts
it('runs the transaction callback against the same double', async () => {
  prisma.$transaction.mockImplementation((callback) => callback(asInstance(prisma)));
  prisma.post.delete.resolveWith({ id: 1, title: 'Hello', authorId: 1 });

  await service.moveTitle(1, 2);

  expect(prisma.post.create).toHaveBeenCalledWith({ data: { title: 'Hello', authorId: 2 } });
});
```

`mockImplementation` is typed against the callback overload, so `callback` needs no annotation.
The array form — `$transaction([query, query])` — takes promises the code already built from the
double; answer it with `resolveWith([...results])`.

## A query nobody mocked

By default a query the spec did not configure answers `undefined`, and the code under test fails
somewhere after it. To make it fail at the call instead, pass `fallbackMockImplementation` — in the
**second** argument, next to the other options:

```ts
const prisma = mockDeep<PrismaClient>(
  {},
  {
    fallbackMockImplementation: () => {
      throw new Error('query not mocked');
    },
  },
);
```

The option name is `vitest-mock-extended`'s, but there it goes in the first argument; the migrated
`mockDeep<PrismaClient>({ fallbackMockImplementation })` is a compile error here, because the first
argument is the seed. The fallback answers a member **nobody configured**. Once `calledWith` is set on
a query, an argument list that matches no rule answers `undefined`, not the fallback;
[`mustBeCalledWith`](/core/control-helpers) is the form that fails on any other `where`. With a
throwing fallback, a configured `$transaction` still runs its callback, and every query inside it
meets the fallback unless the spec configured it. `resetAutoSpy(prisma)` drops what the test
configured, so the fallback applies again.

Two smaller points. `findMany.resolveWith([row])` stays the way to answer with rows: a `mockDeep`
member read by index becomes a real array, but that is for reading array members off the double,
not for query results. And `vi.spyOn(prisma.user, 'findMany')` works on a member nobody has read yet
— it hands back that member's own spy.

## Compared with `vitest-mock-extended`

Prisma's own testing series uses [`vitest-mock-extended`](https://github.com/eratio08/vitest-mock-extended),
and the structure of a spec is the same: a deep mock of `PrismaClient`, reset before each test. What
changes is the helper layer on top:

|                                 | `vitest-mock-extended`                                            | `mockDeep` from `vitest-auto-spy`                                           |
| ------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Resolve a query                 | `mockResolvedValue(rows)`                                         | `resolveWith(rows)`                                                         |
| Reject a query                  | `mockRejectedValue(error)`                                        | `rejectWith(error)`                                                         |
| A throw from a non-async member | `mockThrow(error)` on Vitest 4.1+, `mockImplementation` before it | `failWith(error)`, on every runner                                          |
| A value per call                | chained `mockResolvedValueOnce`                                   | `resolveWithPerCall([...])`                                                 |
| Answer by arguments             | `calledWith(…).mockResolvedValue(…)`                              | `calledWith(…).resolveWith(…)`, `mustBeCalledWith` to fail on anything else |
| Reset between tests             | `mockReset(prisma)`                                               | `resetAutoSpy(prisma)`, or `using`                                          |
| Fail an unmocked query          | `mockDeep({ fallbackMockImplementation })`                        | `mockDeep({}, { fallbackMockImplementation })`                              |
| Vitest range                    | peer `vitest >=4.0.0`                                             | peer `vitest >=2.1.0`; also runs on `bun:test` and `node:test`              |

If `vitest-mock-extended` is already doing the job, the move is mostly a rename. The reasons to make
it are the ones in the table: the helpers that describe a query's outcome in one call, and one
dependency that also covers the classes, streams and framework adapters in the rest of the suite.
The field-by-field comparison is on [Comparison](/comparison#the-double-itself).

## Where this stops

A mocked client tests _your_ code's use of Prisma — which query it sent, and what it did with the
answer. It does not test the query: a `where` that matches nothing in a real database, a relation that
needs an `include`, a constraint the schema enforces. Keep a small integration suite against a real
database for those, and let the unit tests stay fast.
